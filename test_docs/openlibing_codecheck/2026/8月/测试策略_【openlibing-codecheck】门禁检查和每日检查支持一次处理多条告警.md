# 代码检查模块-门禁检查和每日检查支持一次处理多条告警 测试策略设计说明书

## 1. 基本信息

* **需求链接**: https://gitcode.com/openlibing/openlibing-codecheck/issues/183
* **对应task(issueID)链接**: https://gitcode.com/openlibing/openlibing-codecheck/issues/183
* **需求名称**: 门禁检查和每日检查-支持一次处理多条告警（屏蔽申请"全部处理"）
* **核心目标**:
  在现有 5 个屏蔽写接口（提交/审批/转审/待审撤销/通过后撤销）上增加「全部处理」能力：调用方不传 `detailsId`，改为传列表查询条件 `query` + 条数 `count`；后端按「列表条件 ∩ 操作硬条件」count 比对一致后，经 Redis 占用（SET NX，TTL 2 小时 + 续租）并入 RabbitMQ 异步分批（每批 100 条，`_id` 升序）执行。门禁（type=inc）与版本级检查（type=full）共用同一套写接口，不新增路径、不改分页查询接口。
* **设计文档**: `openlibing-docs/spec/openlibing-codecheck/task_design/shield-process-all/design.md`
* **开发责任人**: 谢志强
* **测试责任人**: 徐愚冰

## 2. 测试维度确认

* [x] **功能自检测试**
> * **测试重点:** 分流规则（detailsId 有值走现网批量 / 空且有 query 走全部处理 / 空且无 query 返回 50002）、入参校验（type/uuid+taskId/summaryId/query/count 必填、count 非负整数）、5 种操作的「全部处理」功能正确性（提交全部/审批全部/转审全部/待审撤销全部/通过后撤销全部）、响应契约（仅 code/message，不新增成功数/失败数）。
> * **目的:** 确保全部处理与现网批量处理在同一 URL 上正确分流，且各操作异步执行结果正确。
> * **触发条件:** 强制执行。

* [ ] **体验测试**
* [x] **集成测试**
> * **测试重点:** RabbitMQ 入队 → 消费者分批调用现有写方法（shieldSubmit/shieldAudit/shieldReferral/shieldRevoke/shieldPassRevoke）→ DB 落库 → 通知/待办端到端链路；inc 与 full 两场景各测；门禁全部批次结束后按 uuid 刷新一次汇总缓存。
> * **目的:** 验证异步链路各环节衔接正确，通知与待办按整次合并不重复。
> * **触发条件:** 需求标签含 `need_itest`。

* [ ] **安全与隐私测试**
* [x] **可靠性与韧性测试**
> * **测试重点:** Redis 占用生命周期（SET NX 创建 TTL 2h、每批前续租剩余 TTL<1h 回 2h、终态主动 DEL、进程崩溃 TTL 兜底释放）；某批非 200（429/5xx）时已成功批次保留、停止后续批次、打错误日志；失败不自动重试；MQ 重投不重复插入（defectStatus 硬条件兜底）。
> * **目的:** 确保长时间大批量任务（3~4 万条 >2 小时）占用不失效、异常中断后可恢复且不产生重复数据。
> * **触发条件:** 涉及核心 Core 服务变更，且架构设计含可靠性与韧性设计。

* [ ] **可服务性与可观测性测试**
* [x] **性能与伸缩性测试**
> * **测试重点:** 3~4 万条告警「全部处理」端到端耗时；同步阶段仅 count 不加载全量文档；每批 100 条 `_id` 升序 limit 查询不用 skip 的批推进性能。
> * **目的:** 验证大批量场景下异步分批处理可在可接受时间内完成，同步接口不被拖垮。
> * **触发条件:** 涉及核心 Core 服务变更，且架构设计含性能与伸缩性设计。

## 3. 专项验证设计和执行详情

### 3.1 功能测试专项

**1. 分流规则验证**:
* 前置条件: 门禁与版本级检查详情页均有可处理告警数据
* 测试步骤:
    1. 带 `detailsId`（非空）调用 5 个写接口，验证走现网批量逻辑、同步返回、响应与现网完全一致
    2. 不传 `detailsId` 且带 `query`+`count` 调用，验证走全部处理、校验通过后立即返回 200
    3. 不传 `detailsId` 且不带 `query` 调用，验证返回 `50002`（度量类 cmetrics 提交仍走原逻辑不受影响）
* 预期结果: 三种分流路径正确，同一 URL 靠 `detailsId` 是否传入分流

**2. 入参校验验证**:
* 前置条件: 系统运行正常
* 测试步骤:
    1. 分别缺失 `type` / 门禁 `uuid`+`taskId` / 版本级 `summaryId` / `query` / `count` 提交全部处理
    2. 传入 `count` 为负数或非整数
    3. 提交全部/转审全部时缺失审核人、原因等业务字段
* 预期结果: 任一必填字段缺失或非法均返回错误，不入队

**3. count 条数校验验证**:
* 前置条件: 详情列表存在可处理告警
* 测试步骤:
    1. 传入与「列表条件 ∩ 硬条件」一致的 count，验证入队成功返回 `200 success`
    2. 传入与库内实际 count 不一致的值（模拟别人刚处理过），验证返回 `409 条数已变化，请刷新后重试`，不入队
    3. 传入未叠加硬条件的列表总数（硬条件已排除部分行），验证返回 409
    4. count 双方都为 0，验证与现网空结果一致（提交 `50001 No problem found`，撤销类 `200`），不入队
* 预期结果: count 校验口径为「列表条件 ∩ 操作硬条件」，不一致返回 409 不入队

**4. 五种操作全部处理功能正确性验证**:
* 前置条件: inc 与 full 各准备待提交/待审批/待转审/待撤销/已通过数据
* 测试步骤:
    1. 提交全部：验证本批文件路径合并后一次 Committer 校验；整次每审核人 1 条待办（message_apply）、结束后一条汇总通知
    2. 审批全部：验证或签先抢占成功者生效；每批按硬条件（待审、审核中、未抢占、当前用户是审核人）推进
    3. 转审全部：验证每批清理旧待办、新待办整次共用一条、结束一条汇总通知
    4. 待审撤销全部：验证仅「待审且当前用户是申请人」的记录被处理
    5. 通过后撤销全部：验证仅 `reviewerStatus = 2` 的记录被处理
* 预期结果: 五种操作全部处理结果正确，硬条件叠加生效，不漏不重

**5. 响应契约验证**:
* 前置条件: 系统运行正常
* 测试步骤:
    1. 校验全部处理各场景响应码（200/409/50001/50002/500）
    2. 验证全部处理仅返回 code/message，不新增成功数/失败数
    3. 验证未新增 `submit-all` 等路径，`shield-all-result` 本期不删
* 预期结果: 响应与设计契约一致，接口路径无新增

### 3.2 集成测试专项

**6. 异步分批执行端到端链路验证（inc/full 各测）**:
* 前置条件: RabbitMQ、Redis、MongoDB 正常，准备上万条告警数据
* 测试步骤:
    1. 发起提交全部，验证 HTTP 立即返回 200、请求成功入队
    2. 观察消费者每批 100 条按 `_id` 升序 limit 查询推进，已处理记录退出硬条件后自然滚动到下一批
    3. 验证全部批次结束后门禁按 uuid 刷新一次汇总缓存
    4. 分别在门禁（inc）与版本级检查（full）场景重复验证
* 预期结果: 异步链路各环节正确衔接，不漏不重，门禁缓存整次任务只刷新一次

### 3.3 可靠性与韧性测试专项

**7. Redis 占用互斥与生命周期验证**:
* 前置条件: 系统运行正常
* 测试步骤:
    1. 同一用户对同一任务同一操作连续两次发起全部处理，验证第二次返回 `409 正在处理中，请稍后再试`
    2. 占用期间同一用户改用勾选提交（带 detailsId），验证同样返回 409，不绕开互斥
    3. 验证占用键初始 TTL 2 小时，消费者每批前续租（剩余 TTL < 1h 时回到 2h）
    4. 模拟消费者崩溃停止续租，验证 TTL 到期自动释放后可再次发起，新发起按当前 count 重新校验入队，旧任务残留批次不再跑
    5. 两人几乎同时点全部处理（count 都是旧值），验证两人均入队各自处理（多申请可接受，不少条），待办按审核人合并不重复
* 预期结果: 占用互斥正确，续租/主动释放/TTL 兜底三层生命周期符合设计

**8. 批次失败处理与重复提交窗口验证**:
* 前置条件: 可构造外部 429 限流或 5xx 异常
* 测试步骤:
    1. 某批返回 429 等非 200，验证已成功批次保留、停止后续批次、打错误日志，HTTP 已返回 200，调用方以刷新列表为准
    2. 验证失败不自动重试，重试需调用方刷新后重新发起
    3. MQ 重投同一批次，验证详情已改为审核中的记录因 `defectStatus` 变化退出硬条件，不会二次插入屏蔽表
    4. 任务结束后再次发起，验证已审核中的行不重复处理
* 预期结果: 失败批次保留已成功记录、可安全重入，不产生重复申请数据

### 3.4 性能测试专项

**9. 大批量全部处理性能验证**:
* 前置条件: 准备 3~4 万条可处理告警
* 测试步骤:
    1. 发起全部处理，记录端到端完成耗时
    2. 验证同步阶段只 count 不加载全量文档、不预取全量 ID
    3. 验证每批 `_id` 升序 limit=100 查询（不用 skip）推进平稳
* 预期结果: 3~4 万条可在可接受时间内跑完，同步接口响应不受影响
