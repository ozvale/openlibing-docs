# 代码仓管理模块-跨仓分支列表查询 测试策略设计说明书

## 1. 基本信息

* **需求链接**: https://gitcode.com/openlibing/openlibing-coderepo/issues/109
* **对应task(issueID)链接**: https://gitcode.com/openlibing/openlibing-coderepo/issues/109
* **需求名称**: 跨仓分支列表查询（分支管理-查询跨仓分支信息）
* **核心目标**:
  新增两个接口：`POST /openlibing-coderepo/repo/branch/list`（跨仓分支列表，支持按仓库、分支名、平台、指标等条件筛选与排序）与 `POST /openlibing-coderepo/repo/branch/filter-meta`（筛选元数据）。多平台分支拉取抽象为 `PlatformBranchClient`（GitCode / Gitee / Github 三平台统一适配）；按用户角色过滤可访问仓库（项目/产业/系统管理员全量可见，仓库角色仅可见授权仓）；同步分支提示按 `syncUser` 区分文案；过滤空值统一归一化为空串。前端菜单：代码仓管理服务 → 分支管理。
* **设计文档**: 未找到独立设计文档（Issue #109 正文含接口契约与改造要点，本策略以 Issue 正文为设计基线）

## 2. 测试维度确认

* [x] **功能自检测试**
> * **测试重点:** `/repo/branch/list` 跨仓分支列表查询（仓库/分支名/平台/指标筛选、排序、分页）、`/repo/branch/filter-meta` 筛选元数据返回、`PlatformBranchClient` 三平台（GitCode/Gitee/Github）分支拉取与合并、`syncUser` 区分文案、空值归一化为空串。
> * **目的:** 确保两个新接口功能正确、三平台分支数据完整。
> * **触发条件:** 强制执行。

* [ ] **体验测试**
* [x] **集成测试**
> * **测试重点:** 前端分支管理页面与两个新接口的端到端链路；三平台外部 API 调用链路（accessToken 走请求头 `Authorization: Bearer`、显式连接/读取超时）；权限 URL（`/openlibing-coderepo/repo/branch/list`、`/openlibing-coderepo/repo/branch/filter-meta`）注册与鉴权链路。
> * **目的:** 验证前后端与外部平台集成链路正确。
> * **触发条件:** 需求标签含 `need_itest`。

* [x] **安全与隐私测试**
> * **测试重点:** 角色权限过滤——项目/产业/系统管理员可见全量仓库、仓库角色仅可见授权仓、无权限用户不可见未授权仓数据；接口鉴权（未登录/越权访问被拒）；令牌不回显。
> * **目的:** 确保跨仓分支数据不越权泄露。
> * **触发条件:** 新增对外接口且涉及权限过滤。

* [x] **可靠性与韧性测试**
> * **测试重点:** 单个平台 API 失败/超时时的降级表现（不阻断其余平台分支返回）；分支数据量大时批量拉取稳定性；空值/异常数据（分支名为空等）归一化处理。
> * **目的:** 确保外部平台异常不导致接口整体不可用。
> * **触发条件:** 依赖三个外部代码托管平台 API。

* [ ] **可服务性与可观测性测试**
* [ ] **性能与伸缩性测试**

## 3. 专项验证设计和执行详情

### 3.1 功能测试专项

**1. 跨仓分支列表查询验证**:
* 前置条件: 项目下已录入多平台代码仓（GitCode/Gitee/Github），各仓有多个分支
* 测试步骤:
    1. 调用 `POST /openlibing-coderepo/repo/branch/list` 不带筛选条件，验证返回项目内各仓分支列表
    2. 分别按仓库、分支名（模糊）、平台筛选，验证结果正确
    3. 按指标条件筛选与排序，验证结果正确
    4. 验证分页行为正确
* 预期结果: 各筛选/排序/分页组合结果正确

**2. 筛选元数据接口验证**:
* 前置条件: 项目下已录入多平台代码仓
* 测试步骤:
    1. 调用 `POST /openlibing-coderepo/repo/branch/filter-meta`，验证返回各筛选维度选项
    2. 将元数据选项与列表实际数据比对，验证选项覆盖完整
* 预期结果: 筛选元数据准确反映当前可选范围

**3. 三平台分支拉取验证（PlatformBranchClient）**:
* 前置条件: GitCode/Gitee/Github 三平台令牌已配置且 API 可用
* 测试步骤:
    1. 分别验证三平台仓库的分支拉取结果（分支名、保护状态等字段完整）
    2. 验证多平台分支合并后来源平台标识正确
    3. 验证 `syncUser` 区分文案（不同同步人提示语正确）
    4. 构造分支名/指标为空的数据，验证统一归一化为空串
* 预期结果: 三平台分支数据完整、合并正确、空值归一化一致

### 3.2 集成测试专项

**4. 前后端端到端链路验证**:
* 前置条件: 前端分支管理页面已上线
* 测试步骤:
    1. 进入代码仓管理服务 → 分支管理菜单，验证页面正常加载列表
    2. 页面操作各筛选条件，验证与接口行为一致
    3. 验证权限 URL 已注册，有权限用户正常访问
* 预期结果: 端到端链路正确，菜单/权限/接口贯通

**5. 外部平台调用链路验证**:
* 前置条件: 各平台公共账号令牌已配置
* 测试步骤:
    1. 抓包/日志验证 accessToken 仅出现在请求头 `Authorization: Bearer`
    2. 验证 HTTP 客户端显式设置连接/读取超时
* 预期结果: 调用链路符合安全与超时约束

### 3.3 安全与隐私测试专项

**6. 角色权限过滤验证**:
* 前置条件: 准备项目/产业/系统管理员、仓库角色、无权限用户等账号
* 测试步骤:
    1. 项目/产业/系统管理员查询，验证可见全量仓库分支
    2. 仓库角色用户查询，验证仅可见授权仓的分支
    3. 无权限用户/未登录访问接口，验证被拒
* 预期结果: 权限过滤边界精确，不越权泄露未授权仓数据

### 3.4 可靠性与韧性测试专项

**7. 外部平台异常降级验证**:
* 前置条件: 可模拟单平台 API 失败/超时
* 测试步骤:
    1. 模拟 Gitee 平台 API 超时，验证 GitCode/Github 分支正常返回、整体接口不 500（或按设计返回明确错误提示）
    2. 模拟令牌失效，验证错误提示明确、不泄露令牌信息
    3. 大仓多分支（数百分支）拉取，验证批量拉取稳定
* 预期结果: 外部异常不影响其余平台数据，错误提示友好且安全
