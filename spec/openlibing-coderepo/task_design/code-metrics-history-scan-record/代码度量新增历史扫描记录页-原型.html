代码仓库管理 / 代码度量总览 / 扫描记录定期清理新增
改造前痛点
  • 无任何清理机制，扫描记录与 OBS 上传文件持续累积，存储不断增长；
  • 用户对数据可追溯范围没有预期——不知道多久之前的记录还能查到。
切换到「改造后」查看定期清理方案。
实现位置
openlibing-coderepo 后端，XXL-JOB 定时任务 codeMetricsRecordCleanHandler，每日低峰执行；Redisson 分布式锁保证同一时刻仅一个实例运行
保留策略
默认保留 90 天（code-metrics.retention-days，按环境配置），以扫描完成时间为基准（失败记录无扫描完成时间，按入库时间 create_time 判定）；每个分支始终保留最新一条记录，保证列表指标入口可下钻
删除范围
数据库三张表（记录主表、文件明细、重复代码块，按 record_id 关联）与 obs.action.buckets 桶集合（openlibing-gitcode-action、openlibing-github-action，GitCode/GitHub 来源分别落桶）中 code-metrics-action/{owner}/{repo}/{pipelineRunId}/ 前缀下的上报 JSON 对象（逐桶删除，删除前校验同前缀无共存记录）
执行流程
  1. XXL-JOB 触发，获取 Redisson 分布式锁
  2. 首次上线先以 dry-run 模式预跑：只统计命中记录数与 OBS 对象数并输出日志、不执行删除，人工核对量级后再开启真实删除；单次删除量超过阈值时中止并告警
  3. 读取保留天数配置，按 detection_completed_at（为空的失败记录按 create_time）分批查询过期记录，并排除每个分支最新一条
  4. 按 record_id 分批删除 code_metrics_duplication_block（重复代码块）
  5. 按 record_id 分批删除 code_metrics_file_detail（文件明细）
  6. 分批删除 code_metrics_record（记录主表）
  7. 由记录的 git_url 解析 owner/repo（解析算法以插件 extractOwnerRepo 为唯一参照实现：剥 .git、多级 group 整体作为 owner/repo 段），连同 pipelineRunId 推导前缀，按桶集合（obs.action.buckets：gitcode + github）逐桶分批删除 OBS 对象；删除前先按（git_url、pipeline_run_id）确认数据库无共存记录（同前缀可能被其他分支记录共用，直接删会连带销毁共存记录的上报对象），存在共存则本批仅删数据库、跳过该前缀 OBS；解析失败或前缀层级不全时跳过该记录并告警（禁止回退更短前缀）
  8. 兜底清理：按桶集合逐桶前缀列举 code-metrics-action/ 下超过保留期的对象，按 key 解析出的「owner/repo 段 + pipelineRunId」三元组在数据库确认无对应记录后删除（兼容插件历史 key 变体：多级 group 按「末段文件名、倒数第二段 runId、中间段整体为 owner/repo」解析，unknown 兜底 3 段 key 按 runId 全局核对；解析失败跳过并告警，不做删除）——覆盖上报成功但入库失败的残留
  9. 记录清理执行日志，释放锁
补充说明
删除顺序为先数据库后 OBS：页面明细数据在数据库，删除后即刻查询不到过期数据；OBS 残留对象不影响页面展示，由后续批次或兜底清理回收。已过保留期的记录被访问时，后端校验拦截并返回明确错误提示。分批删除避免大事务与长锁。
