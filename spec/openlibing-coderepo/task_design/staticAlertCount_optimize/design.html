分支列表 staticAlertCount 落表优化

分支管理页告警数：从「每次查询实时跨服务聚合」到「落表 + 写时推送」的性能优化方案
一页概览 现状与问题 方案总览 写入侧设计 查询侧改造 实施计划 风险与对策 评审关注点

1一页概览

问题一句话：分支管理页的告警数（staticAlertCount）每次查询都要实时跨服务聚合 codecheck 的 Mongo 数据，且排序被迫全量取回 + 内存排序，页面越用越慢。

方案一句话：把告警数落表到 coderepo 的 repo_branch 表——codecheck 在告警变化时（扫描完成 / 屏蔽 / 处理）实时重算并推送，coderepo 秒级落库；查询侧直接 SQL 排序分页，并保留定时兜底对账保证数据最终正确。

查询性能

列表接口消除每次查询的跨服务 Feign 调用；告警数排序从「全量取回 + 内存排序」变为数据库 ORDER BY 分页，大数据量下耗时与内存占用同步下降。

数值秒级更新

扫描完成、屏蔽、处理告警后，数值秒级推送到分支表——优于现状「只在查询时现算」，用户操作后立即可见。

对外零感知

接口出入参、字段语义、排序口径（含空值显示 -- 与 0 的区分）完全不变，前端无需改造；统计口径仍为「未处理告警数 OPEN + PENDING_REVIEW」。

1查询路径重

每次列表查询都发起一次跨服务 Feign + Mongo 聚合，与页面访问量线性相关。

2排序被迫全量取回

告警数不是本地数据库列，无法 ORDER BY；按告警数排序时必须把筛选后的全部分支行取回内存排序后再分页，数据量放大耗时与内存。

3非告警排序也要回填

即使按更新时间等字段排序，当前页数据仍需实时调 codecheck 回填告警数用于展示。

3方案总览

openlibing-codecheck（数据源头）
Mongo static_alarm_issue
告警明细集合（计数数据源）
▼三个变更点完成后，各触发一次
BranchAlertCountPushService（新增）
SARIF 解析完成 / 屏蔽与解除屏蔽 / 告警状态流转 → 对该 (仓库, 分支) 重算一次未处理数
MQ：static_alert_count_refresh 队列（推送重算后的全量数值，非增量）
openlibing-coderepo（展示侧）
StaticAlertCountRefreshConsumer（新增）
坐标反查仓库 → UPDATE repo_branch.static_alert_count（秒级落库）
StaticAlertCountRefreshHandler（新增 XXL-Job）
定时兜底对账（默认 2h）+ 历史数据一次性回填（full 模式）
▼
查询侧：SQL 排序分页
ORDER BY IFNULL(static_alert_count, 0)，移除查询链路的实时 Feign 回填与内存排序
核心正确性设计：推送的是"推送时点重算出的全量数值"而非增量差值——消息乱序、重复、丢失的最坏结果只是短暂旧值，不会累积错账；任何埋点遗漏由定时兜底对账收敛。定时对账是正确性的最终防线，写时推送只负责实时性。

4写入侧设计：三条通道

通道 1 · 主通道

写时推送

  • codecheck 三个变更点埋点：扫描解析完成、屏蔽/解除屏蔽、告警状态流转
  • 推送前对该 (仓库, 分支) 重算一次未处理数（口径与现有批量接口同源）
  • coderepo 消费者坐标反查仓库后单行 UPDATE，秒级生效
秒级 覆盖日常变更
通道 2 · 防线

定时兜底对账

  • XXL-Job 低频（默认 2h，可配）增量刷新：只刷超龄 / 从未刷新的行
  • 复用现有批量计数接口，分批限流
  • 覆盖埋点遗漏、消息丢失、发布窗口缺口
小时级 正确性最终防线
通道 3 · 一次性

历史数据回填

  • 上线后手动触发一次 full 全量模式
  • 复用通道 2 同一任务，无需额外开发
  • 此后常态化低频增量运行
一次性 零额外成本

关键设计决策

决策点结论与理由
推全量值 vs 推增量 推全量值。同分支可能并发解析多个扫描、屏蔽与解析交错，增量差值在并发下必然错账且无法自愈；全量值覆盖写天然幂等、可乱序。
MQ 推送 vs 同步调用 MQ 异步推送。推送失败不应污染解析主流程（扫描记录状态）；削峰（批量扫描时可堆积）；消费端重试可控。同步调用的唯一优势（零延迟）对本场景非必需。
屏蔽是否覆盖 覆盖。屏蔽（shield）与解除屏蔽（unshield）完成后均触发重算推送——屏蔽后数值即时减少，恢复后即时增加。
为何保留定时兜底 埋点遗漏、消息丢失、任一方发布窗口期的更新缺口，都需要一条低成本自愈路径；正确性不依赖埋点枚举的完备性。

数据语义（与现状完全对齐）

存储值含义前端展示
NULL从未成功取数：坐标解析失败、新分支尚未扫描、服务长期不可用--
0聚合明确返回该 (仓库, 分支) 无未处理告警0

5查询侧改造：前后对比

改造前
  1. 查总数
  2. 按告警数排序时：全量取回所有分支行
  3. 实时 Feign 调 codecheck 聚合 Mongo
  4. 内存排序 + 内存分页
  5. 非告警排序时也要对当前页实时回填
改造后
  1. 一条 SQL：条件过滤 + ORDER BY IFNULL(static_alert_count, 0) + LIMIT 分页
  2. 告警数列随行直出，零跨服务调用
  3. metrics 类排序字段保持现有内存排序路径，不受影响
  4. 接口出入参、排序语义（空值按 0）、前端展示完全不变
口径一致性说明：排序用 IFNULL(static_alert_count, 0)，与现内存排序中空值按 0 的行为一致；统计口径仍为「未处理告警数 OPEN + PENDING_REVIEW」，且刷新范围不区分分支是否接入代码检查，与现查询口径完全一致（atomgit / gitcode 双域名坐标解析已兼容）。

6实施计划

上线步骤

  1. 数据库变更 —— repo_branch 表加两列（static_alert_count、static_alert_count_synced_at），NULL 默认，无锁风险低
  2. 发布 codecheck —— 推送埋点 + MQ 队列声明（先于 coderepo 发布亦安全，消息暂存队列）
  3. 发布 coderepo —— 查询侧切 SQL + 消费者上线
  4. 历史回填 —— XXL-Job 控制台手动触发一次 full 全量模式
  5. 常态运行 —— 启用低频增量兜底（2h），并观察消费者成功率、数据新鲜度、接口 P95、batch 接口调用量（应显著下降）

7风险与对策

风险影响对策
推送消息乱序 / 重复 / 丢失短暂旧值推全量值覆盖写幂等；兜底对账定期收敛，最坏误差窗口 = 兜底周期
埋点遗漏（新增变更路径未接入推送）该路径变更后数值延迟推送收口到统一组件；兜底对账自愈
同分支并发推送互覆可能短暂回退覆盖写幂等，最终写者胜；兜底收敛
MQ 积压（批量扫描风暴）数值延迟上升消费逻辑极轻（一次反查 + 单行 UPDATE），必要时调大消费并发
坐标解析失败行恒为空个别分支显示 --与现状行为一致（现查询同样解析失败保持空）

8评审关注点（请领导重点确认）

#待确认事项说明
1数值延迟容忍度常规变更秒级（写时推送）；极端场景（消息丢失）最坏延迟 = 兜底周期（默认 2h，可调）。是否可接受？
2兜底频率默认 2h。若希望更激进可调 30min，代价是 codecheck 批量聚合调用量上升（轻聚合，可控）。
3仓库 tab 是否同步改造本期范围仅分支管理页；仓库管理 tab 的整仓告警数仍走现有实时接口。若希望同批落地（由分支表 SUM 派生），可纳入本期或二期，请定夺。
4跨服务队列新增新增一条 MQ 队列（static_alert_count_refresh），沿用现有 RabbitMQ 配置风格，需要平台侧知会。
