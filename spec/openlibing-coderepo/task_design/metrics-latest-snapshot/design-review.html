代码度量：分支表快照列 + 指标更新时间增量

业务 PR #353（openlibing-coderepo） 文档 PR #1435（openlibing-docs） 仓库：openlibing-coderepo 模式：Standard

分支管理列表 5 个度量指标落分支表快照列（主体设计），并追加各指标独立更新时间 updateTime（第 8 节增量）的设计串讲。

一、需求背景

阶段诉求现状痛点（改造前）
主体分支列表 5 个指标（代码规模 / 平均代码行数 / 平均圈复杂度 / 总代码重复率 / 总文件重复率）快速展示与排序每次查询全量拉取历史记录 + 内存拼接、内存排序分页
增量（第 8 节）每个指标展示各自的更新时间快照列只存值，无时间；5 个指标值来源可能不同，单一时间列语义不成立
主体方案对齐 UT 行覆盖率先例：值落 repo_branch 快照列，查询零拼接、排序下推 SQL；code_metrics_record 与 metrics_data_json 原文不动。

二、总体流程设计（三条链路，职责分离）

写入（refreshBranchMetricsSnapshot，O(1)）：本次快照恒等于最新一条成功记录

reportMetrics 主记录入库后 → selectLatestByGitAndBranch（status=0 最新 1 条，含本条） → 解析 5 值（变体键 average* fallback）→ gitUrl 反查 repoId → UPDATE repo_branch 5 值列 + 5 时间列（branch_type='0'） → 失败仅 warn 不阻断上报主链路；失败/部分成功记录不刷列

刷数（BranchMetricsSyncJob，存量清洗）：从新到旧先到先得，幂等可反复刷

倒序取全历史成功记录 → 逐条解析，缺键向上补齐（先到先得、5 键集齐提前收敛） → 单条 JSON 失败 warn 跳过继续 → 至多 1 次 UPDATE（多项目 IN 批量）

查询（两入口收敛同一构建方法）：

单仓 queryRepoBranchInfo → buildBranchMetricsVo(entity) 跨仓 queryProjectBranch → buildProjectBranchInfoList → buildBranchMetricsVo(row) → MetricItemVO{ value, pipelineRunId=null, updateTime } 排序：sortField 白名单枚举映射列名 → SQL ORDER BY 下推

三、核心决策点串讲：为什么推翻「不落时间列」

原判定（主体设计时）：不落来源 runId / 时间列。理由是当时认为详情接口 locateMetricsRecord 兜底可反查、无不可替代消费点——时间列暂无消费方。
推翻的触发（PR #353 增量需求）：分支管理列表要求每个指标展示更新时间。而快照列写入语义有两条路径——正常写入 5 值同源最新记录（同刻）；刷数补齐从新到旧先到先得，各指标值可能来自不同历史记录。单一「分支级时间」无法表达「指标级来源」，必须 5 列各配 1 个时间列。
现方案：repo_branch 5 个快照列各配一个 DATETIME 时间列（Liquibase changeSet 20261125_add_metrics_snapshot_update_time_to_repo_branch，含对称回滚），语义为「该指标当前值来源记录的 detection_completed_at」。第 4 节原「不落时间列」结论已在 design.md 同步修正，DDL 补齐 20261125 增量块。
不变量——值列与时间列同写同空：值 null 则时间 null；哨兵值（如 not_applicable，issue #295）是真实值，同样携带来源时间。写入侧缺键写空时间保持 null（与刷数路径先到先得语义一致）。
updateTime 的 null 语义：null = 无快照或来源时间未知（detection_completed_at 本身可为空——空完成时间的记录不参与「最新」竞争，仅全历史均无时间时可能胜出）。前端以 value 判空判断「无快照」，updateTime 仅展示用途、不承载判据。
历史扫描记录页（scan-record/page）不改：每行即一条扫描记录，行上 scanTime 与 5 个指标值天然同源同刻，语义无缺口。

四、数据模型与 API 影响

DDL（20261125 增量，5 个时间列，语义均为「值来源记录的 detection_completed_at」）：

ALTER TABLE repo_branch ADD COLUMN code_scale_update_time DATETIME DEFAULT NULL, ADD COLUMN avg_function_loc_update_time DATETIME DEFAULT NULL, ADD COLUMN avg_cyclomatic_complexity_update_time DATETIME DEFAULT NULL, ADD COLUMN total_code_duplication_rate_update_time DATETIME DEFAULT NULL, ADD COLUMN total_file_duplication_rate_update_time DATETIME DEFAULT NULL;

API：对外接口（/repo/branch/list、/project-repo/query-repo-branch、/repo/branch/filter-meta）路径 / 入参零变化；出参 metrics[key] 新增 updateTime（String，yyyy-MM-dd HH:mm:ss），仅增字段向后兼容；pipelineRunId 恒 null（跳转走详情接口兜底，前端零改动）。

类变更
RepoBranchInfoEntity / ProjectBranchRowEntity+5 值字段、+5 时间字段（Date）
MetricItemVO+updateTime（BranchMetricsVO 结构不变）
CodeMetricsServiceImpl写入/刷数共用 syncBranchSnapshotColumns，时间参数透传

五、兼容性与验证

兼容性：响应仅在既有 metrics[key] 对象上新增字段；历史存量数据时间列为 NULL（刷数任务重跑即可回填，漏显非错值）；新上报分支由写入链路自动自愈。
项结果
单测（缺键同写同空、哨兵携带时间、未知负哨兵防御分支等）全量 175 个测试类通过
增量覆盖率（可执行改动行，ignore-absent 口径）122 / 125 = 97.60%（三个核心类 100% / 100% / 85%）
安全面：排序白名单枚举映射、SQL 全参数化、刷数任务无用户上下文不暴露 HTTP 入口、写列失败降级不阻断主链路。
