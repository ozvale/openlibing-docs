分支列表 UT 覆盖率排序修复 — 设计评审方案

前端传 sortField=utCoverage 排序被静默回退为更新时间排序。根因是排序链路两层白名单均未纳入该字段——数据侧本已具备排序条件（快照列已 SELECT），修复仅需在两层白名单补齐合法映射 + 一个 SQL 渲染契约测试防回归。

1问题现象

用户按 UT 行覆盖率排序分支列表，列表实际仍按更新时间排序，且无任何报错——静默失败。
项内容
接口POST /gateway/openlibing-coderepo/repo/branch/list（项目维度分支列表）
现象前端传 sortField=utCoverage&sortOrder=desc，列表未按行覆盖率排序，实际仍按更新时间排序
请求示例{"projectId":3,"pageNum":1,"pageSize":10,"sortField":"utCoverage","sortOrder":"desc"}
修复分支fix-ut-coverage-sort（基于 master）

2根因链路

排序参数在链路上经两层白名单校验，两层均无 utCoverage 条目，getOrDefault 与 otherwise 双双静默回退。
▎静默回退链路
QueryProjectBranchDTOsortField = "utCoverage"
→
resolveProjectBranchSortField白名单 ① 无该条目PROJECT_BRANCH_SORT_FIELD_MAP 无 "utCoverage" → getOrDefault 回退 update_at
→
projectBranchOrderBy白名单 ② 无该分支RepoBranchInfoMapper.xml <choose> 无 ut_line_coverage 分支 → <otherwise>b.update_at</otherwise>

关键事实：数据侧已具备排序条件

queryProjectBranchByLimit 本就 SELECT 了 repo_branch 分支表的 UT 覆盖率快照列 b.ut_line_coverage（与 code_scale、static_alert_count 等度量快照列同表同模式），仅排序白名单遗漏该字段。白名单双重校验的设计目的是防 SQL 注入（用户输入不直接拼列名），因此修复不是放开透传，而是在两层白名单中补齐合法映射。

3修复方案

共 2 行生产代码 + 1 个 SQL 渲染契约测试。

① Java 服务层白名单补映射

RepoServiceImpl#PROJECT_BRANCH_SORT_FIELD_MAP 补齐 "utCoverage" → "ut_line_coverage" 映射（紧跟 staticAlertCount 条目）。

DTO 驼峰字段名归一为数据库裸列名，sortField 从「静默回退 update_at」变为按预期排序。

② Mapper XML ORDER BY 补 when 分支

RepoBranchInfoMapper.xml <sql id="projectBranchOrderBy"> 新增 <when test="info.sortField == 'ut_line_coverage'">b.ut_line_coverage</when>（位于 static_alert_count 分支之后、otherwise 之前）。

<choose> 精确匹配 OGNL 常量，白名单归一后才进入 ORDER BY，无注入面扩大。

③ SQL 渲染契约测试防回归

RepoBranchInfoMapperSqlTest 新增用例 projectBranchOrderBy_RendersBareColumn_ForUtLineCoverage：断言该 when 分支渲染为裸列 b.ut_line_coverage。

防止被误删或改写成 IFNULL 包裹（NULL 按 0 参与排序会导致未上报分支与 0 覆盖率分支混排）。

4关键设计决策

决策点方案理由与备选
裸列排序 NULL 语义ut_line_coverage 使用裸列排序，依赖 MySQL 原生 NULL 语义：desc 时无 UT 覆盖率（未上报）的分支恒排最后，asc 时恒排最前与 static_alert_count 及其余度量快照字段口径完全统一（staticAlertCount 排序定案时的既定口径）。禁止：IFNULL 包裹会把 NULL 当 0 参与排序，导致未上报分支与 0 覆盖率分支混排
白名单补齐而非放开透传sortField 仍经两层白名单归一后才进入 ORDER BY，仅补合法映射条目防 SQL 注入是白名单存在目的，用户输入永不直接拼列名；放开透传会扩大注入面
契约测试锁排序语义SQL 渲染断言锁定裸列形态（projectBranchOrderBy_RendersBareColumn_ForUtLineCoverage）白名单双重校验是纯配置式修复，最易被后续改动误删/误包 IFNULL；契约测试以最低成本锁死回归点

5影响范围与风险

维度评估
改动面2 行生产代码（白名单映射 + ORDER BY 分支）+ 1 个轻量契约测试用例，无接口契约 / DDL / MQ 变化
兼容性纯增量：utCoverage 从「静默回退 update_at」变为按预期排序；其余字段行为不变
SQL 注入sortField 仍经白名单归一后才进入 ORDER BY（<choose> 精确匹配 OGNL 常量），无注入面扩大
性能ORDER BY 列与既有度量列同表同模式，无新增 join / 子查询；如需可后续评估 ut_line_coverage 索引
数据无 DDL、无数据迁移；UT 覆盖率快照列由上报链路写入 / 维护（分支最新一次成功解析的行覆盖率），排序值与详情页展示值同源，无一致性风险

6验证方式

RepoBranchInfoMapperSqlTest：2/2 通过（static_alert_count + ut_line_coverage 裸列断言）。
联调验证：projectId=3 下传 sortField=utCoverage&sortOrder=desc，确认列表按行覆盖率降序、无覆盖率的分支排尾部；sortOrder=asc 时无覆盖率分支排头部。
