UT 覆盖率历史扫描记录 — 设计评审方案

分支级 UT 覆盖率从「仅展示最新一次」升级为「历史可回溯、结果可唯一定位、数据有保留边界」：用户可回看分支每次扫描结果，流水线输出链接精确指向当次记录，扫描数据按保留周期自动清理。

openlibing-coderepo · 后端 openlibing-web · 前端 upload-ut-action · 插件 设计评审稿 v1.0
现状与痛点方案总览三大能力 关键设计决策交付范围风险与对策验收标准

1现状与痛点

扫描数据已逐次入库（code_ut_record），但入口与治理缺失，数据"存了看不见、看不准、存到哪没数"。
痛点 ①

历史数据不可见

分支管理 UT 指标只展示最新一次扫描结果；历史记录虽已入库，用户无法查看，回看历史流水线时指标对不上当次构建。

痛点 ②

结果链接指向不准

插件仅输出 result，无结果链接；且流水线 ID 定位的是"最新记录"，历史流水线的输出链接跳到的是别次数据。

痛点 ③

存储无限增长

扫描记录（含文件明细大字段）持续累积且无清理机制，存储成本不可控，用户对"能追溯多久"没有预期。

2方案总览

不新建业务表，全部能力基于存量 code_ut_record；上报链路零破坏，兼容旧链接与旧插件版本。
▎上报与结果链接（openlibing-coderepo + upload-ut-action）
upload-ut-action覆盖率报告上传
→
/ut/coverage/report响应扩展MQ 异步入库；响应直接返回 recordId + report_url（recordId 预生成，无查询接口）
→
setOutput report_url流水线输出固定指向当次记录
▎历史回溯（openlibing-web + openlibing-coderepo）
分支列表 UT 指标点击直进最新详情（行为不变）
→
详情页历史入口新增「查看历史扫描记录」按钮
→
/ut/coverage/history新增历史记录分页列表（含保留天数提示）
→
/ut/coverage/file-detail + recordId扩展按记录唯一定位，URL 可分享/刷新
▎数据治理（openlibing-coderepo）
xxl-job 定时任务新增utCoverageCleanupHandler
→
按 retention-days 分批删除单批 500 条 + 时间索引，夜间低峰执行
→
连带清理 OBS JSON新增按 original_report_obs_url 批删源桶对象（NULL 跳过 / 失败告警不回滚）

3三大能力

① 历史扫描记录查看

UT 指标点击保持直进最新详情（用户高频路径不变）；详情页新增「查看历史扫描记录」入口，进入按扫描时间倒序的历史列表（扫描时间、来源（流水线名 #编号 可跳转）、行覆盖率、状态；commitId 挪至详情页展示），点击记录进入文件级明细详情，URL 携带记录 ID，刷新/分享仍定位同一条记录。

默认路径服务高频场景（看最新），历史回溯为详情页内的次级入口——行为零突变。

② 插件结果链接唯一定位

上报接口响应直接返回指向当次扫描记录的链接（recordId 受理时预生成），插件直接输出 report_url。历史流水线输出从此固定指向当次结果，不再随新扫描漂移。

零额外查询、零重试逻辑；MQ 消费延迟仅短暂影响 URL 可用性（消费重试自愈）；拿不到链接仅告警，不影响流水线成败。

③ 保留周期与自动清理

默认保留 90 天（配置可调，≤0 关闭）；每日低峰定时清理过期记录（含文件明细大字段），并连带清理 OBS 上的原始报告 JSON，分批执行防锁表；分支列表"最新指标"快照不清理，展示不受影响。

页面同步提示保留范围；访问已清理记录时明确提示并引导返回历史列表。

4关键设计决策

6 个决策项（含 2 条评审对齐结论），均以"零破坏 + 低成本"为原则。
决策点方案理由与备选
记录唯一定位键以 记录 ID（雪花 ID，全链路 String） 为唯一定位键；流水线 ID 降级为兼容定位（recordId > pipelineRunId > 最新一条兜底）流水线 ID 与记录是 1:N（重跑），只有记录 ID 能唯一定位；String 防前端 JS 精度截断。备选：新造短码——无必要，雪花 ID 已够用
插件链接生成位置链接由后端生成（report 响应直接返回完整 URL，recordId 受理时预生成，不新增查询接口），插件只透传输出web 域名 / repoId 映射在后端侧，插件免配置域名、双平台一套逻辑；省去查询 RT 与重试复杂度。已裁剪：record-url 查询接口（评审对齐去除）
清理策略按 detection_completed_at 统一清理（成功+失败记录），新增单列时间索引，xxl-job 分批删除走新索引避免长事务锁表；repo_branch 最新指标快照不清理，分支列表展示不受影响。备选：归档表——当前量级不必要，引入复杂度
链接格式兼容前端 URL 由 pipelineRunId 迁移为 recordId，临时保留旧格式解析，待看板组适配新格式后移除存量分享链接/看板引用零破坏，双格式过渡期可控。备选：一次性切换——外部引用全部失效，不可接受
OBS 原始报告文件清理 已对齐方案 A（已定）：xxl-job 删 DB 记录后按 original_report_obs_url 级联批删源桶对象；防护 = 删除凭证最小化（仅 ut-coverage-action 前缀）+ 删除前二次时间校验；NULL 跳过、失败告警不回滚单一配置源（retention-days），DB 与存储同步收敛。备选 B（生命周期规则）曾为倾向项，评审对齐选 A；B 的漂移窗口缺点不复存在，代价是引入受控的删除权限
commitId 展示位置历史列表不展示提交列，commitId 挪至详情页顶部信息区展示列表保持轻量（时间/来源/覆盖率/状态），完整上下文在详情承载。备选：列表+详情双展示——列数冗余，评审对齐去除

6风险与对策

风险影响对策
MQ 消费延迟/失败窗口内 report_url 短暂不可用低消费侧 MQ 重试自愈（最终一致）；前端对窗口内未入库 recordId 展示「处理中」过程态（雪花时间戳 ≤5 分钟启发式），超窗口转「不存在/已清理」终态；响应缺失仅告警降级，流水线不失败
明细大字段（LONGTEXT）批量删除锁表中时间索引 + 单批 500 条 + 低峰执行；删除量摘要日志可观测
雪花 ID 前端精度截断高全链路 String 传递（后端已返回 String，前端禁止 Number 化）
看板/外部链接仍用 pipelineRunId低后端定位优先级兼容三种入参，过渡期零破坏
OBS 级联删除误删或失败中删除凭证最小化（仅 ut-coverage-action 前缀）+ 删除前二次时间校验；失败仅告警不回滚，不阻塞 DB 清理

7验收标准

分支管理 UT 指标点击保持直进最新详情（行为不变）；详情页历史入口可见该分支全部历史扫描记录（扫描时间倒序，含失败记录标注），保留天数横幅与配置一致；历史列表不展示提交列，commitId 在详情页信息区展示。
点击任一记录进入详情，URL 携带记录 ID；刷新、分享、直接粘贴 URL 均定位到同一条记录。
插件在每次流水线输出 report_url（上报响应直接返回，无额外查询），打开即当次扫描详情；历史流水线输出可准确回溯当次结果。
超过保留期的记录及其 OBS 原始报告 JSON 被自动清理（NULL 跳过、失败告警不阻塞）；访问已清理记录返回明确提示并引导返回历史列表。
旧格式链接（pipelineRunId）与旧版插件（无 report_url）在过渡期行为零变化。
