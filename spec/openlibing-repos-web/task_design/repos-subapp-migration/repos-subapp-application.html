01

背景：为什么必须拆

Repos 已经不是"宿主里的一个页面"，而是一个完整业务域。继续留在宿主内，代码定位、问题定位、修复、发布和迭代的成本会随着每次需求持续放大。这个问题不是靠更努力地搜索或更谨慎地评审能解决的，它需要一次结构性的调整。

1.1 现状规模：一个页面长成了一个业务系统

21个文件
15,659行代码
215KBindex.vue 单文件
60个接口函数
5处跨应用 / 跨路由跳转

今天的 Repos 已覆盖：仓库列表与同步、分支管理、标签管理、仓库成员、GitCode 角色映射、全局配置、重复代码、UT 覆盖率、指标详情、接口扫描结果、操作日志。无论是功能数量还是代码体量，它都已经达到一个独立系统的规模，却仍然以单个路由的形式寄居在宿主 web-openlibing 内。

与宿主强耦合

路由、鉴权 store、标签页 store、公共组件、单体 api/api.ts 五处耦合，任何调整都要评估宿主影响。

与主工程共用一条发布流水线

Repos 与 openlibing-web 主工程共用同一条构建与发布流水线，发布节奏互相牵制，职责边界不清晰。

仍在宿主主包里

整块业务常驻宿主构建产物，主包与首屏体积持续膨胀，构建和热更新变慢。

1.2 代码仓定位：先找得到，才改得动

现状在宿主里找代码

  • 215 KB 单文件，template / script / style 全在一处，搜索命中后还要人工判断上下文
  • 42 个 Repos 接口散在单体 api/api.ts，与项目等其它业务域混排
  • 仓库域与宿主其它业务域边界不清，新人接入要先"认地图"
  • 搜索结果混入宿主其它模块，噪音高、确认慢
→

拆分后一个仓就是一个域

  • 目录即地图：views/repo、api/repo 一眼看到全部职责
  • 60 个接口按域拆为 7 个模块，URL 统一收敛到 api/repo/url.ts
  • 搜索只在目标仓内进行，不再排除宿主噪音
  • 新人按"仓库 / 分支 / 成员 / 标签 / 扫描 / 日志"直接定位
定位效率的差异是结构性的：不是靠更努力的搜索，而是靠"一个仓对应一个业务域"的物理隔离。仓的边界一旦清晰，代码审查、缺陷归属和新人上手都会同步变简单。

1.3 发布与迭代：两条业务线被绑在同一辆车上

发布节奏互相牵制

Repos 改一行，也要等宿主整包发布窗口；主工程的紧急上线，又会被仓库域的未完成改动拖住。

构建与热更新变慢

整块业务常驻主包，本地启动、热更新、生产构建都要为它付出时间成本，且随代码量继续增长。

冲突面持续扩大

单体 api/api.ts 被两个业务域共同修改，合并冲突与回归范围同步扩大。

一个真实的工作流

仓库域提测 → 等宿主发版 → 宿主同时带着其它业务域的改动 → 回归范围被迫覆盖多个域 → 出问题难以判断是谁引入的。

拆分的本质

把"发布单元"和"业务域"重新对齐：谁改的谁发，谁发的谁回滚，回归范围收敛到本域。

1.4 问题定位与快速修复：一次修复，全量回归

① 归属难判断

线上问题出现时，先要判断是仓库域、宿主公共层还是后端——模块边界不清，定位链路变长。

② 修复必须随宿主发版

即使只改一行，也要走宿主完整构建、测试、发布链路，无法当天闭环。

③ 回滚只能整包回退

没有独立回滚能力，一个局部缺陷可能迫使整个宿主版本回退，影响无关业务。

结果是：小问题修得慢，大问题不敢改。团队会本能地"绕着代码走"，技术债继续累积，最终反过来限制迭代速度。

拆分后的问题定位

前端错误可按子应用维度采集与告警；问题归属一眼可见，必要时独立镜像回滚，不影响宿主。

拆分后的修复闭环

子应用独立构建、独立发布、独立回滚；修复从"等发版"变成"当天可验证"。

1.5 拆分后，直接拿到四个能力

01

定位快

一仓一域，目录即地图；接口按域拆分，URL 统一收敛。

02

修复快

独立构建与发布，不再等待宿主发布窗口。

03

迭代快

Repos 需求独立排期，与宿主主工程解耦。

04

风险低

独立镜像 + 独立回滚，缺陷不扩散到宿主。

宿主主包减负

整块 views/Repos 移出后，对应约 215 KB 源码块不再进入宿主主包；宿主首屏与构建时间同步收益。

责任边界清晰

仓库域的问题、发布、值班、回滚都在自己的仓里闭环；跨域协作从"改同一份代码"变成"约定接口"。

这四项能力不是新增功能，而是现有功能"更可控"：同样的业务，用更小的发布单元、更短的反馈链路去承载。
02

方案：怎么拆

方案不做创新，直接参考已经跑通的 openlibing-cicd-web：wujie 子应用形态，宿主只改 2 条路由，对外 URL、路由 name 与权限完全不变，后端接口契约不动。

同一子应用复用实例

两条路由共用一个 wujie 实例 key，切换时只下发 wujieRoute，不重复加载。

2.4 迁移范围：搬什么、怎么搬，边界先划清

页面：21 个文件全量迁出

index.vue、分支、成员、标签、角色映射、扫描结果、6 个弹窗、3 个业务组件、useSigSync 与单测。

接口：60 个按域拆分

原 api/api.ts 42 个 + api/Repos/api.ts 18 个，拆为 repo / branch / member / tag / scan / role / log 7 个模块。

跳转：5 处收敛到适配层

检测中心、接口管理、代码检查、项目管理 4 个跨应用目标页，加操作日志内部路由，统一走 navigateToHost 白名单。

公共依赖处理

首次迁移：ContactInformation、BatchAddMemberDialog 复制到新仓；BatchOperation / Empty / NoPermissionPopover 以 cicd-web 为基线 Diff 后取较新版本；CategorySearch / DateRangePicker 直接复用 cicd-web，避免第三份副本。

明确不做的三件事

不改后端接口契约；不做 UI 改版与组件化重构；不在本期抽公共组件包。迁移与优化不叠加，保证回归可定位。

已知代价：公共组件在两个前端仓各有一份，缺陷需双仓同步修。这是本期主动接受的成本，用来换取迁移风险最小。

2.5 分期落地：六个阶段，每阶段独立验收

P0

搭空壳

参考 cicd-web 初始化工程、流水线与三环境配置

P1

路由接入

宿主 2 条路由接 wujie，子应用路由映射打通

P2

页面迁移

页面与业务组件迁出，标签页、跳转改造

P3

接口与组件

60 个接口按域拆分，公共组件与工具落位

P4

灰度与演练

按角色灰度，演练"开 → 关 → 开"回滚

P5

下线旧实现

观察满一个发布周期后清理宿主旧代码

P5 之前，旧实现始终留在宿主包内。任何阶段发现问题，都可以不改代码直接切回，风险可控。
每阶段独立验收：P1 验路由、P2 验功能、P3 验接口参数一致、P4 验回滚时延与指标、P5 验主包减负。
P5 必须改一次代码，菜单配置做不到。宿主是前端静态路由，菜单不驱动组件；"把旧菜单下掉"只会收回权限，不会改变页面加载哪套实现，甚至会把新页面一起挡掉。正确动作是：① 先发一版宿主，把 2 条路由的 component 从 ReposEntry 直连 WujieMiddleware，分流逻辑与 LegacyRepos 引用一并移除（旧文件暂留）；② 观察一个完整发布周期，无回滚需求后再单独发一版删除旧代码文件；③ 最后清理 repos_subapp 菜单记录，repo_manage 必须保留。
顺序不能反：一旦旧文件删除，L1 开关即失效，回滚只剩 L2 镜像与宿主版本回退。因此"删文件"和"切直连"建议拆成两次交付，把不可逆动作尽量后移。

2.6 回滚设计：三层回滚，互不依赖

L1主开关

同名按钮记录授权切换 + 入口代码兜底

菜单管理新增一条同名「代码仓管理」记录（标识 repos_subapp，按钮类型）。它不是新增菜单：不生成路由、不进导航，本质是一个临时开关标识；同名只是为了运营侧能对口识别。角色勾选即走子应用，取消勾选即回旧实现；组件分流由入口 ReposEntry 按该标识判定，权限未就绪时一律回旧实现。不改代码、不发版。

刷新后生效
L2镜像回滚

子应用版本回退

某次发布引入缺陷、但路由形态正常时，用 kubectl rollout undo 或发布平台回退上一镜像。

3–5 分钟
L3单用户兜底

单用户强制走旧实现

localStorage.reposSubapp = '0' 后刷新，仅影响当前浏览器，用于个别用户被阻断的应急场景。

立即
默认值必须是旧实现：权限未就绪、接口失败或返回空列表时，一律回旧实现。宁可灰度没生效，也不能让"取消授权"失效。
为什么必须有代码兜底：宿主是前端静态路由（accessMode: 'frontend'），菜单只下发权限标识、不生成路由也不指定组件，所以"切菜单"最终仍要落到 ReposEntry 的判断上。菜单负责"谁走新实现"，代码负责"没授权就一定走旧实现"。
03

决策点：需要评审拍板什么

以下四项需要在本次评审拍板。每项都给出推荐选项与理由，避免实施阶段反复讨论、反复返工。

01

回滚开关是同名按钮记录（临时标识），不是新增菜单

对应设计文档 §8.2 · 一票否决项：必须可回滚
否决：复用 meta.auth = repo_manage

路由守卫的语义是"无权限即拦截"。取消它会把旧页面一起挡掉，开关变成"要么都不可用，要么都可用"。

推荐：同名按钮记录 + 独立标识 + 入口兜底

新增一条同名「代码仓管理」按钮记录（标识 repos_subapp），只做权限开关，不生成路由与导航项。角色勾选即开启、取消即回滚；ReposEntry 按该标识分流，不写入任何路由的 meta.auth。

请明确两点：① repos_subapp 不替代 repo_manage——路由能否进入仍由守卫判断 meta.auth，只授新标识不授旧标识会被挡在路由外，因此必须成对授权；② 宿主为前端静态路由（accessMode: 'frontend'），菜单不生成路由、不指定组件，组件分流必须由 ReposEntry 判定。
请评审确认：同意"同名按钮记录（临时开关标识）授权 + 入口代码兜底"作为回滚主开关。
02

URL 与路由 name 不变，入口内部分流

对应设计文档 §2.6 / §8.5 · 兼容性策略
深链、收藏、标签页零迁移

/apps/repos 与 /apps/repoOperationLog 路径不变，历史链接、书签、外部系统跳转全部继续可用。

周边调用方零改造

其它模块按路由 name 跳转 Repos（如 PR 管理），name 不变即无需改动调用方；回滚只换组件，不影响已打开页面。

代价是宿主保留 ReposEntry.vue 与旧实现代码，直到 P5 清理——这是可控且有用明确下线时间的成本。
请评审确认：接受"入口组件 + 双实现共存"的过渡形态，过渡期不少于一个发布周期。
03

只迁移不重构，公共组件本期不抽包

对应设计文档 §2.3 / §2.4 · 范围控制
迁移与重构不叠加

本期不改 index.vue 的组件拆分粒度，不做 UI 改版。避免"迁移 + 重构"双重变更导致回归问题无法定位到具体原因。

公共组件先复制 / 同源

不新建公共组件仓。抽包会引入版本、发布、兼容三套机制，超出本次立项范围。

代价：公共组件在两个前端仓各一份，缺陷需双仓同步修。待两个子应用稳定后，再单独立项抽公共包，届时是纯粹的增量收益。
请评审确认：同意本期范围仅限"迁移"，重构与公共包抽取另行立项。
04

灰度路径与回滚触发阈值

对应设计文档 §8.4 / §8.6 · 验收标准
灰度路径：beta 演练 → gamma 小范围 → prod 分批

beta 完整演练"开 → 关 → 开"并记录生效时延；gamma 先覆盖内部角色观察一个工作日；prod 按角色分批授权，任一指标越线即执行 L1 回滚，不等待定位根因。

指标阈值
前端 JS 错误率> 1%，持续 5 分钟
加载失败 / 白屏> 0.5%
首屏 P95> 3s，持续 10 分钟
阻断性功能异常列表 / 同步 / 成员 / 权限任一不可用
验收清单：功能回归、4 个跨应用跳转、按钮权限与申请引导、构建产物 base=/repos/、三环境可访问、迁移后单测与适配层单测通过。
请评审确认：认可上述灰度路径与四个回滚阈值。
04

申请事项：拆分后需要申请的部署资源

拆分后新增 1 个前端服务与 1 个 nginx location，不改变网关与后端。容器资源按华为云容器实例申请（4.1），其余配套项全部参考 openlibing-cicd-web 已落地的机制（4.2），无新增平台能力要求。
