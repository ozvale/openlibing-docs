一、目标与总体链路（README 1.1.1 / 1.2.1）

① 目标 1 · 统一口径告警三分类可执行定义，所有项目、所有工具共用一套判别标准，统计结果不因项目漂移
② 目标 2 · 自动分类告警入库时自动完成分类，不依赖人工打标；每条告警的分类依据可随时反推验证
③ 目标 3 · 可统计看板统计安全静态告警（alert_type = 'security' AND status = 'open'），支撑项目 / 语言 / 工具 / 规则 / CWE / 类型 / 时间维度报表
④ 目标 4 · 可扩展新工具接入仅注册工具 +（必要时）补规则映射（docs 仓 MR），不改分类引擎代码
分层职责（README 1.2.1.1）：采集层（CI 产出 SARIF 上报，分类逻辑全在平台侧）→ 接入层（唯一入口，解析归一化按指纹去重）→ 分类引擎（三层判别流水线输出 alert_type，纯查表 + 元数据判断，无机器学习重依赖）→ 存储层（告警库仅存事实数据，口径定义由 docs 仓承载）→ 统计层（口径以 README 定义为准）。

三、三分类语义与统计口径（README 1.1.2）

alert_type语义定义（判别问题）
security 安全可能被攻击者利用的安全风险（注入、密钥泄露、弱加密、不安全反序列化等）—— 代码可能被利用吗？
bug 缺陷运行时大概率出错的正确性 / 可靠性问题 —— 代码确凿或大概率有错吗？
code_smell 坏味道功能正常但有改进空间：格式、命名、复杂度、重复、性能、拼写、文档等 —— 其余全部（兜底）
三分类对齐 SonarQube 质量模型三值简化版（Vulnerability 与 Security Hotspot 统一归 security）。MECE 设计要点：① 互斥单值——一条告警只有一个 alert_type，统计占比之和恒 100%，GROUP BY alert_type 直接可用；② 完备无兜底桶——三类覆盖全部告警空间，拼写 / 文档 / 格式类告警均属典型 code_smell，纯度量类输出（圈复杂度数值等）不属于告警不进表；③ 冲突裁决——规则同时命中多类信号按 security > bug > code_smell 优先级取主类型。

判别决策树（README 1.1.2.2，映射表编写与评审统一依据）

2. 运行时确凿/大概率出错？  ──►  bug
3. 其余                      ──►  code_smell   // 完备兜底

2. 口径缓存与刷新

本节将缓存形态调整为单机进程内缓存（volatile 引用）、刷新机制明确为 @Scheduled 每 5 分钟轮询（不依赖 Redis / webhook / MQ）——口径常驻 JVM，基础设施故障不影响判定主链路；多实例各刷各的，≤5 分钟版本偏斜可接受。限流评估：每实例 288 次/天轻量 GET（3 实例约 864 次/天），远低于 GitCode 阈值 50 次/分钟、4000 次/小时。
环节设计
缓存：进程内直查口径数据（L1 工具注册 + L3 规则映射，构建为前缀树 / 哈希结构）整体存进程内存，volatile 引用持有，刷新时整体替换引用（读侧无锁，原子可见）；引擎每次判定直查本地内存：零网络 RTT（微秒级），且口径常驻 JVM——Redis / MQ / webhook 任一基础设施故障都不影响判定主链路（最多用旧口径，符合「存量定型、新告警按新口径」的宽容语义）；无实例间共享：各实例独立加载独立刷新，实例间存在 ≤5 分钟的口径版本偏斜窗口，结合「存量告警保持入库时值、仅新告警按当前口径定型」语义偏斜影响可忽略（同一次扫描任务内口径一致）；启动对齐：ApplicationReady 时异步发起一次远端刷新（不阻塞启动），口径唯一来源为远端仓库，不打包本地兜底 yml——远端不可用期间新告警兜底 code_smell 入库（窗口期落库值无自动纠偏路径，见第九章风险表），轮询恢复后仅对新告警生效
刷新：定时轮询每实例 @Scheduled 每 5 分钟调 1 次目录级 API 取 docs 仓 alert-type 目录最新 commit SHA，与进程内已加载 SHA 比对：一致 → 跳过（绝大多数轮询命中此分支，仅 1 个轻量 GET，288 次/天/实例）；不一致 → 经 GitCode v5 contents API 拉取 yml 全量（web /raw/ 路由返回 HTML 不可用；支持 blobs 二次获取的模式 B，Nacos 开关默认关闭）→ 解析校验（tool 唯一性、aliases 冲突、多维度 AND 组合、精确形 literal 同工具内唯一、正则合法性）→ 校验失败拒绝刷新、保留旧口径并告警（口径错误比口径过期危害大）；429/5xx/无响应最多 3 次指数退避重试（404 等语义响应不重试）；校验通过后 volatile 原子替换缓存引用 + 更新已加载 SHA → 下次扫描起对新告警生效（存量不变）。刷新体统一在专用单线程执行器执行，@Scheduled 与启动回调仅提交任务（在途去重）；token 四级链路：配置直供密文 > 项目公共账号 > 全局 token > 匿名
口径版本：目录 commit SHA不设 version 字段，口径版本由 alert-type 目录 git commit SHA 承担：进程内记录已加载 SHA，每 5 分钟轮询时与目录最新 SHA 比对决定是否刷新；SHA 基线由启动对齐后的首次成功刷新建立；SHA 取目录最后一次变更的 commit（docs 仓其他目录变更不影响比对结果，SHA 不变则不刷新，天然按路径免疫）

3. 三层判别流水线（README 1.2.2.1 ~ 1.2.2.3）

# 分类伪代码（v6，判定流程唯一依据）
def classify(alert, tool_registry, rule_mapping):
    tool = tool_registry.resolve(alert.tool)   # 正名精确匹配，未命中按小写归一 aliases 别名回落
    if tool is None:
        return "code_smell"                  # 未注册工具（新工具首报 / 落位表遗漏）兜底，不抛异常

    # L1: 工具级定型（固定类型工具全量同型，短路后续层级）
    if tool.default_alert_type != "mixed":
        return tool.default_alert_type

    # L2: SARIF 元数据（仅判安全；四判据任一命中即 security）
    tags = [t.lower() for t in alert.rule_tags or []]
    if "security" in tags or alert.security_severity is not None \
       or has_cwe(tags) or alert.cwe_tags:    # ① tags security ② security-severity 键 ③ cwe-* ④ 落库 cwe_tags 非空兜底
        return "security"                    # CWE 编号同步提取入库 cwe-?(\d+) 不区分大小写

    # L3: 规则映射表（四维度可 AND 组合，精确形 ^literal$ 哈希直查；
    #     多条命中按 security > bug > code_smell 取序，行顺序无关；
    #     level 维度匹配源 = 入库生效级别 raw_severity，见数据模型节）
    hit = rule_mapping.match(alert)
    if hit:
        return hit.alert_type

    # 兜底
    return "code_smell"
层判别内容（README 1.2.2.2）说明
L1工具级（固定类型短路）：注册数据 default_alert_type 为固定值的工具全部告警直接定型；工具名匹配先精确匹配 tool 正名，未命中按小写归一的 aliases 别名回落正名（生产 SARIF 上送名与注册名存在大小写/格式差异，精确匹配下会静默兜底）security：安全专用工具；bug：缺陷检测专用；code_smell：格式化 / 拼写 / 风格类（落位见第五章）
L2元数据级（仅判安全）：满足任一即归 security——① tags 含 security ｜ ② 存在 security-severity 键 ｜ ③ tags 含 cwe-* / external/cwe/cwe-* ｜ ④ 落库 cwe_tags 非空（tags 为空的存量回填场景兜底判据，v6 新增）CWE 编号同步提取入库；非安全元数据（如 CodeQL 的 maintainability / correctness 标签）一律不参与本层判别，统一落入 L3；CodeQL correctness → bug 定型规则已外置至 mappings/codeql.yml（调整），L2 保持纯「仅判安全」语义
L3规则级：rule_pattern 为正则（前缀写 ^S、精确写 ^S608$）；severity 维度（ShellCheck / Cppcheck）level_pattern 匹配级别（优先 rules[].defaultConfiguration.level，缺失取 results[].level，v6 明确）；category 维度（PMD）ruleset_pattern 匹配 rules[].properties.ruleset；富元数据工具（CodeQL）tags_pattern 匹配 tags 任一标签；一条映射可多维度组合（AND 语义，全部命中才生效）；精确形 ^literal$ 提取 literal 做哈希 O(1) 直查（v6 新增）多条同时命中按 security > bug > code_smell 优先级取序，映射行顺序无关（CodeQL 查询同时带 security 与 correctness 标签时，L2 已先行判 security，L3 仅处理非安全部分）
兜底全部未命中 → code_smell完备性保证：alert_type 永不为空（验收 #1）

3. SARIF 解析入库（存量稳定语义，README 1.2.2.6）

入库解析 result → tool + ruleId → 引擎 classify（口径直查进程内存）→ 写 alerts 表 alert_type；不阻塞入库，增量成本 < 1%
存量稳定口径变更仅对新告警生效：存量告警的 alert_type 保持入库时的值不变（为空时补写本次分类，空值不算既有值，v6 明确），指纹与状态不受影响——已修复的历史告警不会因口径变化被重新拉回，统计趋势稳定
新规则兜底映射未覆盖的新 ruleId → 兜底 code_smell 入库；工具版本入库，升级时比对规则集差异并补映射（MR），下次扫描起生效

八、性能与安全

项评估
引擎判定 ◉ 补充口径直查进程内存：零网络 RTT + 前缀树 / 正则匹配微秒级；相对 SARIF 解析、指纹计算、Mongo upsert 现有成本，增量 < 1%（缓存形态调整说明见第四章第 2 节）
缓存刷新 ◉ 补充@Scheduled 每 5 分钟比对 alert-type 目录 commit SHA（见第四章第 2 节），每实例 288 次/天轻量 GET（3 实例约 864 次/天），无限流风险（429/5xx 指数退避重试兜底）；启动对齐：ApplicationReady 异步远端刷新，不打包本地兜底 yml（v6 调整）
列表 / 计数 / 导出alertTypes 为 $in 等值条件追加现有查询，基数 3 复用现有索引结果集，单次增量 < 10ms
看板聚合GROUP BY alert_type 与现有按 severity 聚合同构，复用现有统计链路
存量回填 ◉ 补充游标全量扫描 + 万级组合批量 UPDATE，低峰执行，幂等可重跑（见第四章第 4 节）
安全分类数据非敏感；不打印 SARIF 原文与源码片段日志；无新增凭证依赖；口径审计由 git 历史天然承担，报表页脚注明口径版本（README 1.2.4）

九、风险与验收（README 1.2.4 / 1.2.5）

风险与应对

风险影响应对
映射表误判（规则错标类型，或漏标）统计口径失真映射变更走评审（安全团队 + 工程团队），下次扫描起自动修正
bug 与 code_smell 边界争议映射评审反复决策树与边界规则为裁决基准，争议案例沉淀进边界规则表
工具升级新增 / 更名规则新规则落入兜底（code_smell）工具版本入库；升级时比对规则集差异并补映射
SARIF 质量参差（无元数据、无指纹）L2 判别失效、去重漂移转换器统一补齐指纹；L3 映射兜底
海量告警性能入库与查询变慢批量 upsert、分区表、聚合预计算
远端不可用窗口期误定型 ◉ v6 新增口径未加载期间新告警被兜底 code_smell 落库（成为既有值，回填只写空值，无自动纠偏路径），窗口内 security 告警可能少计发布前置顺序强制确认首轮刷新成功（日志出现 catalog refreshed）；刷新失败告警监控；如需自动纠偏属实现层增强，走 codecheck 仓另行立项
口径理解不一致各团队统计对不上README 为唯一口径来源，报表页脚注明口径版本

验收标准

#标准
1分类覆盖率：入库告警 alert_type 非空比例 = 100%
2工具级正确性：Bandit、Gosec、Gitleaks、Detect-Secrets 告警 100% 归为 security；Mypy、ErrorProne 告警 100% 归为 bug
3抽样准确率：人工抽查 200 条分类结果，三类型合计准确率 ≥ 95%（每类不少于 50 条）
4口径一致性：报表数值与统计口径 SQL 完全一致
5存量稳定性：映射表变更后，存量告警的 alert_type 与状态（open/fixed）不受影响，新扫描告警按新映射分类
