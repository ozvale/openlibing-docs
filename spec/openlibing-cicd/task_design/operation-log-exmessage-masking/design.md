# operation-log-exmessage-masking: 工程设计

## 1. 方案设计

`ex_message` 是自由文本，不能沿用 JSON 按敏感键名掩码的思路。备选方案：

| 方案               | 做法                           | 问题                                        |
| ------------------ | ------------------------------ | ------------------------------------------- |
| 不返回 `exMessage` | 查询出参直接置空               | 破坏排障能力，前端"失败信息"列失去价值      |
| 结构化改写异常     | 要求各业务方在抛异常前自行脱敏 | 覆盖面不可控，存量与第三方 SDK 异常无法约束 |
| 模式掩码           | 对文本按凭证形态做正则替换     | 需要处理误伤（普通英文）与长文本性能        |

本方案选模式掩码：在查询出参出口统一收口，业务方无需改造，且与既有 `mask()` 的 JSON 路径共用 `MASK` 常量。

关键取舍是"宁可漏掩也不误掩"：认证方案后的凭据要求长度 ≥6 且含数字/大写/符号，键值形态排除 `yes|no|true|false`，避免把 `bearer token`、`password: true` 这类诊断文本打码。

## 2. 实现逻辑设计

1. `mask(value)`：
   - 空值 → 原样返回
   - JSON 解析成功 → `maskNode`
   - JSON 解析失败 → `maskText(value)`（新增）
2. `maskText(value)`：空/空白原样返回；依次执行四条正则替换，顺序不可交换：
   - `URL_USERINFO_PATTERN` 先跑，避免 URL 中的 `:`、`@` 干扰后续键值匹配
   - `AUTH_HEADER_PATTERN` 处理 `Bearer`/`Basic`
   - `RAW_AUTH_HEADER_PATTERN` 处理裸 `Authorization`/`Cookie`
   - `maskKeyValues` 处理键值形态
3. `maskKeyValues`：用 `Matcher.appendReplacement` 逐段重建，引号包裹的值替换为 `"***"` / `'***'`，保留原引号
4. `maskNode` 增强：
   - 对象中非敏感键的字符串值：若是 JSON 则递归，否则 `maskText`
   - 数组中字符串元素：`maskText`；非字符串元素继续递归
   - 敏感键名命中仍整段替换为 `MASK`，保持原有行为
5. `LoggingServiceImpl` 查询出参组装处对 `exMessage` 调用 `maskText`

## 3. 类设计

| 类                            | 职责                                       |
| ----------------------------- | ------------------------------------------ |
| `OperationLogSensitiveMasker` | 统一出口：JSON 结构化掩码 + 纯文本凭证掩码 |
| `LoggingServiceImpl`          | 查询出参组装，`exMessage` 接入掩码         |

`maskText` 为 `public static`，供其他纯文本日志/出参场景复用；工具类为 `final` + 私有构造，无可变状态。

## 4. 数据模型设计

无表结构、无实体、无字段变更。仅改变 `ex_message` 在查询出参中的呈现值，数据库存储值不变（写入侧明文属既有架构，另立项处理）。

## 5. 性能设计

- 四条正则均为 `static final` 预编译，无运行期编译开销
- `maskText` 只对文本长度做线性扫描，正则设计上避免了灾难性回溯：认证凭据使用定长字符类与前瞻断言，键值形态值段使用否定字符类
- 仅作用于操作日志查询出参单行字段，不在写入主链路引入额外成本

## 6. API 接口设计

接口契约不变。`exMessage` 字段名、类型、可空性均保持原样，仅返回值内容被掩码替换为 `***`。

影响面提示：前端"数据详情"弹窗与"失败信息"列展示的异常文本会出现 `***`，属预期变化。

## 7. 安全设计

- 覆盖威胁：CWE-532（日志/审计信息暴露敏感数据）
- 缓解点：出参出口统一收口，不依赖业务方逐个改造
- 误伤控制：长度/字符组成门槛 + 布尔值排除，降低正常文本被打码的概率
- 边界：只处理查询出参，不改变落库内容；Issue 中"落库前掩码"与"超长截断"两项子要求未在本次实现
- 残余风险一：落库内容仍为原文，具备库表直读权限的角色可见明文
- 残余风险二：`openlibing-coderepo` 的 `LoggingServiceImpl.maskRow`（第 420 行）同类漏 `exMessage`，跨仓缺口仍在
- 残余风险三：非标准形态凭证（如自定义 token 前缀）无法穷举，模式覆盖不完整时仍可能漏
- 残余风险四：已落库的历史 `ex_message` 明文未刷洗，是否刷洗需按影响范围单独评估
- 评审整改：PR 评审指出"JSON 分支仅按键名判定敏感，非敏感键值可绕过"，已确认为真问题。修复为"非敏感键值统一过 `maskText` + 数组字符串元素同样处理"，并补 3 条用例覆盖，风险面从"键名白名单"收敛为"全字段文本扫描"
