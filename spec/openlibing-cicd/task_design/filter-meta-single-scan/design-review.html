filter-meta 组合扫描合并（方案一）

Issue #569 cicd + coderepo 两仓同构 零 DDL Standard 模式

前置：operation-log-query-perf 阶段一缓存（PR !714 / !364）。本变更解决其遗留根因——首查仍对同一批行做 5 次独立全扫描。

一、总体流程

现状（首查）本方案（首查）
userName / resourceName / ip / logResult / moduleId 各发一条 GROUP BY + COUNT
→ 同一批 WHERE 命中行被全量扫描 5 次（前 4 次回表 + temporary + filesort） 		① 1 次 combo 扫描：GROUP BY user_name, resource_name, ip, log_result LIMIT 10000（仅当请求含 ≥2 个值维度时启用；单值维度直走旧路径）
② 1 次 moduleId 专用查询（不变，走索引前缀，最便宜）
③ 4 个值维度候选列表在应用侧从 combo 行拆分聚合
5 次扫描 → 2 次，首查 DB 耗时近似降为 2/5

二、语义保真（与现状逐项对齐）

现状行为combo 方案等价实现
skipDimension：候选列表不被自身 selectedValues 过滤，但受其他维度过滤combo SQL 不带任何维度过滤；拆分维度 d 时对其他三个维度应用严格 IN 过滤（存在 selectedValues 则行值必须命中 HashSet，null / 空串天然不命中即跳过）
自身列 IS NOT NULL AND != ''拆分时跳过自身列空值行；该行仍计入其他维度（不变）
ORDER BY selected 优先, count DESC, value + LIMIT 1000应用侧三级 comparator 排序 + 截断 1000（toFilterMetaItems 增强）
logResult 零值枚举补齐、selected 零值补齐、fillMenuNames全部保留不变
30s TTL 缓存 / cacheKey / 权限前置 / 失败闭门全部不动（combo 属缓存未命中路径内部优化）

三、决策点

#决策结论与理由
D1moduleId 是否并入 combo不并入。并入会使组合数再乘以模块数（白名单可达数十），截断风险显著上升；module_id 单查走索引前缀、成本最低（用户已确认）
D2截断熔断阈值常量 10000；返回行数 == 阈值即自动回退旧逐维度路径——最坏退化为现状性能，结果始终正确，避免配置化过度设计（用户已确认）
D3旧 selectFilterMetaGroupBy 去留保留。moduleId 维度与熔断回退路径共用
D4两仓实现方式各自同构实现，不抽公共库（跨仓共享需 common SDK 发版，超范围）
D5combo 启用条件仅当请求含 ≥2 个值维度时启用；单值维度直走 selectFilterMetaGroupBy（单维度无归并收益，combo 反而传输放大）
D6超限校验时机selectedValues >1000 的 paramError 校验前移到任何 DB 查询之前统一预检；语义不变，避免无效查询开销
D7collation 归一化IN 匹配、归并 key、排序 value 均按 Locale.ROOT 小写比较，对齐 MySQL utf8mb4_*_ci；重音不敏感未实现（注释注明）；展示值经 displayNames 保留原文

四、风险与对策

风险对策
组合基数异常大（超 10000）→ combo 结果不完整行数 == 阈值即熔断回退旧路径；正确性不劣于现状，仅性能退化
网络传输组合行（≤10000×5 列）大于 4 份聚合行典型项目组合数千级，净收益为正；异常项目被熔断兜底
拆分聚合引入回归（排序 / 空值 / skip 语义）单测逐项覆盖语义对齐表中的每一行；BETA 同参数首查结果与现状 diff 比对

五、验收要点

  • 缓存未命中时：4 值维度仅 1 次 combo SQL + moduleId 1 次专用 SQL（可从 SQL 日志/mapper mock verify 断言）
  • combo 行数达 10000 时自动回退，返回结果与旧路径一致
  • 候选值列表内容、排序、截断、零值补齐与现状完全一致
  • 接口路径/出入参/权限语义零变化，前端无需适配
  • 增量行覆盖率 ≥ 80%
注：此前 Issue #569 评论中「moduleId 候选值来自白名单不走 DB」表述不准确——moduleId 维度实际走 DB（GROUP BY module_id + menu_info 补名称），交付时在 PR/Issue 中更正。
