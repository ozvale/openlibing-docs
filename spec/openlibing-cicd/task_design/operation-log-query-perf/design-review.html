操作日志查询性能优化 — 评审串讲

业务 Issue: openlibing/openlibing-cicd#569 · 涉及仓: openlibing-cicd / openlibing-coderepo / openlibing-framework · 依据: task_design/operation-log-query-perf/design.md

1. 问题与根因（一句话版）

五个日志查询接口「首查慢、后续快」= filter-meta 每维度 GROUP BY 无覆盖索引（回表+temporary+filesort） + 每请求 Feign 远程拉白名单无缓存 + 冷启动开销。后续变快是 buffer pool / JIT 热身，不是问题被解决。

2. 总体流程设计

2.1 阶段一：查询侧缓存（cicd + coderepo）

queryFilterMeta / list 查询请求 │ ├─ ① 权限校验 checkProjectMember（不变，先于缓存） │ ├─ ② 白名单 listAllowed() │ ├─ TTL 内 → 内存快照（0 次远程调用） │ └─ 过期 → Feign 拉取；仅「成功且非空」才入缓存 │ 失败/空 → 当次闭门失败（语义与现状一致） │ └─ ③ queryFilterMeta 专属： ├─ 构建 cacheKey = projectId + 维度集合 + 规范化过滤值 │ + selectedValues + 时间区间按分钟取整 ├─ 30s TTL 命中 → 直接返回缓存副本 └─ 未命中 → 原有 5 维度 GROUP BY 循环 → 结果写缓存

2.2 阶段二：存储侧覆盖索引（framework）【已撤销，未交付】

原方案: 三合一替换（先建 idx_project_module_time_user_resource → 后删 idx_project_module_time） 撤销（PR !560 检视发现，commit 9f347e43）: ① P0 阻断: 6 列索引键长 = 5×1020(utf8mb4 VARCHAR(255)) + 5(DATETIME) = 5105 字节 > InnoDB 3072 上限 → CREATE INDEX 必报 ERROR 1071， changeSet 随启动重放、每次阻断应用启动 ② P3 列序: user_name / resource_name 位于范围列 operation_end_time 之后， GROUP BY 仍走 temporary/filesort，尾列仅覆盖扫描、收益存疑 ③ 反证: 既有 idx_project_module_time 已达 3065 字节贴上限， 当前列宽（VARCHAR(255) × utf8mb4）下不存在可行的超集覆盖索引 最终交付: 仅阶段一缓存；framework 无任何 DDL 变更，索引总数维持 6 个

2.3 与既有链路的衔接

五个接口路径、入参、出参、权限语义全部不变；明细脱敏链路（OperationLogSensitiveMasker）不动；白名单写入链路不受影响（写入不调用 OperationLogWriteModules）。framework 侧无需任何 Java 改动。

3. 决策点

D1 缓存实现：手写轻量 TTL，不引入 Caffeine/Guava。 两仓 pom 均无缓存框架依赖，新增依赖属过度工程；白名单与 filter-meta 两个场景用不上高级特性。
D2 白名单失败语义：仅缓存「成功且非空」，失败/空不入缓存。 若把失败结果缓存 60s，一次网络抖动会放大成全局 60s 闭门——比现状更差。不缓存则保留每请求可重试的恢复能力。
D3 filter-meta 缓存 key：时间区间按分钟取整。 提升命中率；筛选候选值列表是元数据，分钟级精度无业务影响。权限校验先于缓存读写，命中不绕过鉴权。
D4 索引只上 user_name / resource_name 两个，ip / log_result 不建。【随阶段二撤销而失效】 log_result 基数仅 3；ip 过滤低频。该决策以「可建索引」为前提，覆盖索引经检视否决后不再成立。
D5 阶段二覆盖索引方案：经 PR !560 检视否决，整体撤销（commit 9f347e43）。 检视证据链：6 列索引键长 5105 字节超 InnoDB 3072 上限（5×VARCHAR(255) utf8mb4 单列 1020 + DATETIME 5），CREATE INDEX 必报 ERROR 1071，changeSet 随启动重放阻断启动；既有 idx_project_module_time 已达 3065 字节贴上限，无追加余量；且 GROUP BY 分组列位于范围列后无法免 temporary/filesort。曾评估的替代方向（窄索引 (project_id, module_id, user_name)=3060 字节贴上限且失去时间下推、缩列宽 schema 变更）均有明确代价，留待 BETA 实测数据后再评估。历史决策记录：最初「新增 2 个独立索引」因写放大 +33% 否决 → 改为「三合一替换」→ 检视发现键长硬阻断后整体撤销。
D6 framework 白名单端不做缓存。 瓶颈在调用频次而非单次库内查询耗时，调用方缓存已消除频次问题。

4. 风险与回滚

风险缓解回滚
缓存导致元数据短时陈旧（最长 30s/60s）TTL 可经 Apollo 调整，≤0 即禁用；筛选候选值场景可接受Apollo 配置置 0，即时生效
filter-meta 首查仍走原执行计划（回表+temporary+filesort），首查耗时改善有限索引优化经检视否决（键长超 InnoDB 上限），本期以同参数重复查询命中缓存为主要收益；首查优化留待列宽/窄索引评估不涉及 DDL，无索引回滚项

5. 验收要点

  • filter-meta 同参数重复查询 TTL 内命中缓存、不触达 DB（首查执行计划不变）
  • 白名单 Feign 调用频次 = 每 TTL 窗口至多 1 次
  • 权限校验先于缓存（行为不变）
  • log_operation 无任何 DDL 变更，索引总数维持 6 个
  • cicd / coderepo 增量行覆盖率 ≥80%
