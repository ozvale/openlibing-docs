# GitCode数据采集服务 - 架构设计文档

## 1. 架构概述

本项目采用**微内核架构(Microkernel Architecture)**,也称为插件架构。这种架构模式将系统分为两部分:

- **核心系统(Core System)**: 提供最小功能集,负责插件管理和任务调度
- **插件模块(Plugin Modules)**: 独立的功能组件,可动态加载和扩展

### 1.2 设计原则

1. **开闭原则(OCP)**: 对扩展开放,对修改关闭
2. **单一职责原则(SRP)**: 每个插件只负责一种数据类型的采集
3. **依赖倒置原则(DIP)**: 核心系统依赖抽象接口,不依赖具体实现
4. **接口隔离原则(ISP)**: 定义细粒度的插件接口

## 2. 核心模块设计

### 2.1 插件管理器 (PluginManager)

**职责**: 管理插件的生命周期(加载、初始化、启动、停止)

**核心功能**:
- 动态加载插件模块
- 插件注册和注销
- 插件生命周期管理
- 插件类型分类管理

### 2.2 任务调度器 (TaskScheduler)

**职责**: 创建、执行和管理采集任务

**核心功能**:
- 任务创建和参数封装
- 任务执行和重试机制
- 任务超时控制
- 执行结果统计

### 2.3 配置管理器 (ConfigManager)

**职责**: 加载和验证配置文件

**核心功能**:
- YAML配置文件解析
- 环境变量替换
- 必需配置验证

### 2.4 日志管理器 (LogManager)

**职责**: 管理日志输出和脱敏

**核心功能**:
- 独立日志文件
- 日志轮转
- 结构化日志
- 敏感信息脱敏

### 2.5 API客户端 (APIClient)

**职责**: 封装HTTP请求,处理速率限制和重试

**核心功能**:
- HTTP请求封装
- 速率限制控制
- 自动重试机制
- 请求头构建

### 2.6 数据转换器 (DataTransformer)

**职责**: 转换API返回的原始数据为标准格式

**核心功能**:
- Issue数据转换
- 评论数据转换
- 时间戳格式化
- 数据验证

## 3. 插件系统设计

### 3.1 插件接口定义

**基础插件接口**:
- `plugin_type`: 插件类型
- `plugin_name`: 插件名称
- `plugin_version`: 插件版本
- `initialize()`: 初始化插件
- `start()`: 启动插件
- `stop()`: 停止插件
- `execute()`: 执行插件功能

**采集器插件接口**:
- 继承基础插件接口
- `collect()`: 采集数据方法
- 支持增量采集参数 `since`
- 返回标准化的数据列表

**存储器插件接口**:
- 继承基础插件接口
- `save()`: 保存数据方法
- `get_max_updated_at()`: 获取最大更新时间(用于增量采集)

### 3.2 采集器插件实现

系统提供以下采集器插件:
- **IssueCollectorPlugin**: 采集Issue数据
- **IssueCommentCollectorPlugin**: 采集Issue评论数据
- **PRCollectorPlugin**: 采集Pull Request数据
- **CommitCollectorPlugin**: 采集Commit数据

### 3.3 存储器插件实现

**DorisStoragePlugin**:
- 使用Doris Stream Load批量导入数据
- 支持JSON格式导入
- 自动去重和更新
- 高性能批量写入
- 支持UNIQUE KEY模型的自动更新
- 提供增量采集支持(通过get_max_updated_at方法)

## 4. 多Token并行采集设计

### 4.1 设计背景

GitCode API对每个访问令牌有速率限制:
- 每小时请求数: 5000次/token
- 并发请求: 1个/token

为提高采集效率,系统支持多Token并行采集。

### 4.2 实现机制

**配置方式**:
```yaml
repositories:
  - owner: org1
    repo_name: repo1
    auth:
      access_token: ${REPO1_TOKEN}

  - owner: org2
    repo_name: repo2
    auth:
      access_token: ${REPO2_TOKEN}
```

**并行执行流程**:
```
┌─────────────────────────────────────┐
│        任务调度器                    │
└─────────────────────────────────────┘
              │
              ├─────→ 仓库1 (Token1) ──→ 独立速率限制
              │
              ├─────→ 仓库2 (Token2) ──→ 独立速率限制
              │
              └─────→ 仓库3 (Token3) ──→ 独立速率限制
```

**关键特性**:
- 每个仓库使用独立的访问令牌
- 每个token独立计算速率限制
- 多个仓库可以并行采集
- 整体采集效率线性提升

### 4.3 性能提升

| 场景 | 采集速度 | 说明 |
|------|---------|------|
| 单Token | 约50条/分钟 | 受API速率限制 |
| N个Token | N×50条/分钟 | 线性提升 |

**优化建议**:
- 为每个仓库配置独立的访问令牌
- 避免多个仓库共享同一个token
- 根据仓库数量合理配置token数量

## 5. 数据流设计

### 5.1 完整数据流

```
命令行参数 → 配置加载 → 插件初始化 → 任务创建
    ↓
任务执行循环:
    采集器插件 → GitCode API → 数据转换 → 存储器插件 → Doris数据库
    ↓
结果输出
```

### 5.2 增量采集流程

```
是否指定since参数?
    ├─ Yes → 使用指定时间
    └─ No  → 查询数据库max(updated_at)
              ├─ 有历史数据 → 使用max(updated_at)
              └─ 无历史数据 → 执行全量采集
```

## 6. 扩展性设计

### 6.1 添加新的采集器

**步骤**:
1. 创建新的采集器插件类,继承 `ICollectorPlugin` 接口
2. 实现 `collect()` 方法
3. 在 `config.yaml` 中注册插件

### 6.2 添加新的存储器

**步骤**:
1. 创建新的存储器插件类,继承 `IStoragePlugin` 接口
2. 实现 `save()` 和 `get_max_updated_at()` 方法
3. 在 `config.yaml` 中注册插件

## 7. 性能优化设计

### 7.1 批量导入优化

使用Doris Stream Load进行批量导入:
- 高性能批量导入
- 支持JSON格式
- 自动去重

### 7.2 速率限制优化

使用令牌桶算法控制API请求速率,避免触发API限制。

### 7.3 增量采集优化

基于 `updated_at` 时间戳的增量采集:
- 减少API调用次数
- 提高采集效率
- 降低系统负载

## 8. 安全设计

### 8.1 日志脱敏

自动脱敏敏感信息(token、password、secret等)。

### 8.2 环境变量管理

敏感配置通过环境变量管理,避免硬编码。

### 8.3 SQL注入防护

使用参数化查询,防止SQL注入攻击。

## 9. 监控和运维设计

### 9.1 结构化输出

为DolphinScheduler提供结构化输出,包含任务状态、数据统计、执行时长等信息。

### 9.2 日志管理

- **独立日志文件**: 每个任务独立日志文件
- **日志轮转**: 自动轮转,避免日志文件过大
- **日志归档**: 保留最近10个日志文件

### 9.3 错误处理

- **自动重试**: 失败任务自动重试3次
- **错误告警**: 记录错误日志,触发告警
- **优雅退出**: 捕获异常,清理资源

## 10. 总结

本架构设计具有以下优势:

1. **高扩展性**: 插件化设计,易于添加新的采集器和存储器
2. **高可维护性**: 模块化设计,职责清晰
3. **高性能**: 批量导入、速率限制、增量采集、多Token并行
4. **高安全性**: 日志脱敏、环境变量、SQL注入防护
5. **高可靠性**: 自动重试、错误处理、优雅退出

这种架构设计使得系统具有良好的扩展性和可维护性,能够快速适应新的需求变化。
