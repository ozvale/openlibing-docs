# 安全设计：产品质量-质量策划模块

## 0. 安全目标与实施映射

本设计将威胁模型转换为编码和验证约束。`SEC-n` 是 `tasks.md` 中安全任务的稳定编号，编码后由代码安全审查复核。

| 编号 | 约束 | 实现位置 | 验证方式 |
|---|---|---|---|
| SEC-1 | 新模块只接受 token Cookie 身份，匿名默认拒绝 | `UserUtil` 新 token-only 方法、`ProductQualityUserAdapter` | 无 token、伪造 query `userId`、无效 token 测试 |
| SEC-2 | 读、写、负责人管理分别鉴权，查询失败默认拒绝 | `ProductQualityPermissionService` 及新权限 Mapper | 完整权限矩阵单元测试、Controller 403 测试 |
| SEC-3 | 所有数据访问限定项目/策划/记录范围 | Domain Service、Mapper/XML | 两项目 IDOR、跨策划修改/删除测试 |
| SEC-4 | 初始化和批量写操作事务化、原子化 | App/Domain Service、唯一键 | 并发初始化、部分失败回滚测试 |
| SEC-5 | 主动内容清理、大小限制、URL 白名单 | DTO 校验、内容服务 | XSS、伪协议、超大/深层 JSON 测试 |
| SEC-6 | SQL 参数化、分页/批量上限、固定排序 | Mapper/XML、分页请求 | 注入输入、页大小和批量边界测试 |
| SEC-7 | 写操作记录白名单前后快照，不记录凭证 | `ProductQualityLogHandler`、快照适配器 | 六类写操作日志及敏感字段扫描测试 |
| SEC-8 | 新依赖最小化并固定版本 | `pom.xml` | 依赖树、漏洞和许可证检查 |
| SEC-9 | 部署验证 Cookie/CSRF/TLS/数据库最小权限 | 现有网关和部署配置 | beta/生产上线检查，不写入秘密到仓库 |
| SEC-10 | 错误和依赖故障均失败安全 | 权限服务、统一异常、事务 | 权限查询异常、日志异常、DB 异常测试 |

## 1. 资产与信任边界

### 决策

- 资产、数据流和 STRIDE 详见同目录 `threat-model.md`。
- 外部请求、路径 ID、请求体、富文本、思维导图和 URL 全部视为不可信输入。
- OPS 不因为调用来自网关或内网而省略业务权限和归属校验。
- `projectId`、`planId`、审计人由服务端绑定，客户端提交的同名字段不具信任性。

### 理由与替代方案

采用“网关认证 + OPS 业务授权 + 数据层范围条件”的纵深防御。仅依赖网关或 Controller 注解无法防止模块内部调用、错误注解和资源 ID 越权，因此否决单层防护。

## 2. STRIDE 威胁控制

| 威胁 | 必须落地的控制 | 验证 |
|---|---|---|
| 身份伪造（S） | SEC-1；不信任 query 身份；无效 JWT 拒绝 | query 中带其他用户 ID 仍匿名/按 token 用户处理 |
| 数据篡改（T） | SEC-3/4/5/6；归属链、事务、白名单和参数化 SQL | 跨项目更新、半批删除、XSS 和注入用例 |
| 抵赖（R） | SEC-7；每个写操作记录 actor/action/resource/result/前后快照 | 日志回放能定位操作者和资源 |
| 信息泄露（I） | SEC-2/3/7/10；统一错误、最小响应、日志无凭证 | 越权响应不返回资源内容，异常不返回 SQL/堆栈 |
| 拒绝服务（D） | SEC-5/6；页大小、批量、内容大小、JSON 深度限制 | 超限请求 400，不执行大查询/大写入 |
| 权限提升（E） | SEC-2/3；只有管理员维护负责人，负责人不能自授权 | 质量负责人调用维护接口返回 403 |

## 3. 认证与授权设计

### 3.1 认证

**方案**：沿用 OPS 现有 JWT Cookie 和 `JwtUtils`，在 `UserUtil` 增加公开 token-only 方法，`ProductQualityUserAdapter` 只调用该方法。原 `currentUserId` 保留给存量模块，避免无关行为变化。

**凭证生命周期**：签发、过期、吊销和 Cookie 属性继续由现有认证/网关负责，本模块不签发、不刷新、不存储 JWT，也不新增凭证。解析失败、缺失或空用户 ID 都抛出权限异常。

**会话与 CSRF**：写请求使用 Cookie 时必须依赖现有网关 CSRF 防护和 Cookie `Secure + HttpOnly + SameSite=Lax/Strict`。SEC-9 要求上线前验证；不能用 CORS 代替 CSRF，也不能将 token 放入 URL 或日志。

### 3.2 授权

**模型**：RBAC（全局/项目角色）+ ABAC（项目归属、质量负责人、资源归属链），默认拒绝。

| 操作 | 决策 |
|---|---|
| 读里程碑/目录/策划 | 有效身份且通过现有项目归属检查 |
| 写里程碑/初始化/策划内容 | 项目管理员、全局管理角色或本项目质量负责人 |
| 维护质量负责人 | 仅项目管理员或全局管理角色 |
| 设置质量负责人 | 目标用户必须先具备本项目成员资格 |
| 访问记录 | 用户权限通过后，仍须满足 `projectId + planId + id + deleted` |

**角色来源**：复用 `user_role_info` / `role_type_info`。全局管理角色与现有 SQL 一致；项目管理员沿用当前 project 类型语义。普通 product/repo 归属用户只读。权限 SQL 只读，失败或返回空均拒绝。

**选择理由**：复用现有角色数据避免双权限源；新增质量负责人表只承载模块授权，避免修改全局角色。替代方案“所有项目成员可写”违反最小权限，“每个策划单独授权”超出 Issue，均不采用。

## 4. 输入与输出安全

### 4.1 边界与业务双重校验

- Controller：正整数路径 ID、Bean Validation 必填、字符串长度、分页 `page >= 1`、`1 <= pageSize <= 200`、批量 ID `1..200`。
- Domain：策划和记录归属、执行里程碑同项目、进展 `0..100`、批量完整性、已初始化里程碑不可删除。
- 服务端忽略请求体中的 `projectId/planId/id/createBy/updateBy/deleted/createTime/updateTime`，防止 mass assignment。

### 4.2 富文本与 JSON

- 版本摘要：使用 OWASP Java HTML Sanitizer 固定策略。允许基本标题、段落、粗斜体、列表、表格及安全链接；不允许 `script/style/iframe/object/embed/form/input`、事件属性、内联脚本和危险协议。清理结果才入库和进入日志。
- 思维导图：JSON 解析验证，最大 200,000 字符，限制节点数与嵌套深度；不执行表达式、脚本或模板。响应按 JSON 数据返回。
- 普通文本：trim、长度限制；不拼接到 SQL、Shell、HTML 或日志模板表达式。
- `resource_link`：仅 http/https；OPS 不发起重定向、抓取或预览请求，因此不会把该字段变成 SSRF 入口。

### 4.3 输出

统一 `Result` / 强类型 DTO，不返回数据库实体中的逻辑删除和内部适配器字段。错误不携带 SQL、堆栈、内网地址或目标资源内容。后续前端仍需对富文本、普通文本、URL 和思维导图做上下文编码。

## 5. 数据保护

### 分类与最小化

- 策划内容为内部数据，角色和负责人配置为敏感数据，JWT/数据库凭证为机密。
- 只收集 Issue 明确要求的人员文本，不额外收集手机号、邮箱、身份证等信息。
- 数据库不保存 token、Cookie、密码或密钥；接口和日志也不返回这些资产。

### 传输与存储

- 外部传输复用现有 HTTPS；数据库连接复用 OPS MySQL 配置。不得在仓库写入真实 JDBC URL、账号或密码。
- 本期数据不需要新增字段级加密；项目隔离、最小权限、受控日志和数据库现有加密/访问控制是主要保护。若后续纳入个人敏感信息或商业秘密，需重新分类并评估字段加密。
- 业务表逻辑删除；操作日志按现有日志平台权限和保留策略管理，部署要求审计保留不少于 180 天或遵循更严格公司规范。

### 日志脱敏

快照使用白名单业务字段。允许必要的姓名/工号用于 Issue 要求的审计，但不记录认证信息、完整请求/响应报文或无关人员信息。日志访问权限不低于业务数据权限。

## 6. 依赖与供应链

- 复用 Spring Boot、MyBatis-Plus、`openlibing-common`，不新增外部服务 SDK。
- 仅为富文本服务端清理新增 `com.googlecode.owasp-java-html-sanitizer:owasp-java-html-sanitizer`，在 `pom.xml` 固定版本，禁止动态版本。
- 选择理由：服务端 HTML 白名单是防止存储型 XSS 的必要控制；自写正则清理不可靠，信任前端清理不满足纵深防御。
- 编码任务必须检查依赖树、已知漏洞和许可证；如果版本审查不通过，停止引入并重新选择受维护版本，不能退回“原样保存 HTML”。
- 不新增私有仓库、凭证、动态下载脚本或本地快照依赖。

## 7. 部署与运行时安全

### 配置与网络

- 复用现有环境变量/配置中心，不新增秘密配置，不修改容器基础镜像和端口暴露。
- 数据库账号只需要本模块表的读写及现有权限表只读能力；禁止 DDL 账号作为应用运行账号。
- 继续保持现有网关/TLS/网络隔离，本模块不开放绕过网关的新端点。

### Cookie、CSRF 与上线门禁（SEC-9）

上线检查必须证实：

1. token Cookie 为 `Secure`、`HttpOnly`、`SameSite=Lax` 或 `Strict`。
2. 网关对 Cookie 会话的状态变更请求具备 CSRF 防护，且不会信任外部传入的 `userId` query/header。
3. HTTPS 证书有效，OPS 不暴露绕过网关的匿名写路径。
4. 日志平台访问受控，保留周期满足公司要求。

缺少任一项时先修复现有入口配置，不能靠本模块文档假设安全。

### 可观测性

- 业务日志最小字段：UTC 时间、actor、action、projectId、planId/resourceId、decision/result、reason、traceId/requestId；IP 由现有 Recorder 补充。
- 记录写操作和授权拒绝；不记录 token、Cookie、完整 HTTP 报文。
- 复用现有日志采集与告警，不新建 SIEM/Kafka 链路。后续可在现有指标中增加授权拒绝和初始化冲突计数，不属于本期必需交付。

## 8. 失败模式与应急

| 故障/攻击场景 | 默认行为 | 恢复与取证 |
|---|---|---|
| token 缺失、无效或权限查询异常 | 拒绝访问，返回 403，不降级为 query 用户 | 记录拒绝元数据和 traceId，排查认证/权限库 |
| 项目/策划/记录不存在或跨项目 | 不返回内容，按统一资源/权限错误处理 | 保留授权拒绝事件，不泄露其他项目数据 |
| 初始化目录任一步失败 | 整事务回滚 | 修复后重试显式初始化；唯一键保证幂等 |
| 批量删除部分失败 | 整事务回滚 | 返回安全错误，日志保留失败结果，核对请求 ID 列表 |
| 日志快照补数失败 | 遵循现有 Recorder 策略，不暴露日志内部错误；不得伪造新快照 | 使用业务审计字段和 traceId 排查；安全审查确认日志缺失可告警 |
| 富文本/JSON 超限或含危险内容 | 拒绝或按白名单清理，绝不原样执行 | 返回参数错误，不保存危险原文 |
| 数据库异常 | 事务回滚，统一 500 业务错误，不返回 SQL | 保留应用错误日志，按现有回滚流程恢复服务 |
| 凭证泄露 | 本模块无法自行吊销；立即走现有 token/数据库凭证吊销轮换流程 | 检查日志确保无凭证，必要时回滚版本并审计访问记录 |

应用代码回滚不自动删除 `pq_*` 表，避免二次数据损失。Schema 回滚必须由 DBA 单独评审。

## 9. 验证计划与事后闭环

### 编码阶段

- SEC-1/2/3：匿名、伪造身份、权限矩阵、跨项目 IDOR 测试。
- SEC-4：初始化并发、目录失败、质量负责人替换和批量删除回滚测试。
- SEC-5/6：XSS 样本、危险 URL、深层 JSON、超限分页/批量、SQL 注入字符串测试。
- SEC-7：全部写操作前后快照及敏感字段扫描测试。
- SEC-8/9/10：依赖检查、部署检查、权限/数据库/日志异常测试。

### 编码后审查

代码交付后由代码安全审查逐项验证：

1. 是否存在 query 身份信任、缺失鉴权或只在前端控制的权限。
2. Mapper 是否全部带项目/策划/逻辑删除条件，是否存在 SQL 拼接。
3. 批量和初始化事务是否真实覆盖全部写入，唯一键异常是否被误吞。
4. 富文本是否先清理再入库，JSON/URL 是否有可执行或 SSRF 行为。
5. 日志是否含 token、Cookie、完整报文、数据库凭证或不必要人员信息。
6. 新依赖版本、漏洞和许可证是否合规。

安全设计中的 SEC-9 部署项需要 beta/生产证据，不能仅以单元测试通过代替。任何高风险偏离必须在业务 PR 前重新设计并获得用户确认。
