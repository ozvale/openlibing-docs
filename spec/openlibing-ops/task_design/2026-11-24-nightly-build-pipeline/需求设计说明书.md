## 1. 需求背景与目标

### 1.1 背景

现有 Nightly 统计只覆盖 Nightly 版本级 / 组件级**测试**流水线。业务新增 Nightly 专用**构建**流水线，当前有两个前缀：

- `Nightly-Version-build_pipeline`（前缀）
- `Nightly-Component-build_pipeline`（前缀）

后续会在前缀后追加自定义内容（如 `Nightly-Version-build_pipeline-xxx`），因此按**前缀匹配**识别。

这类流水线只做编译构建，不执行测试用例。如果按现有 NIGHTLY 口径直接纳入，会出现两个问题：

1. 它们没有测试用例，`is_version_available` 恒为 0，会拉低项目级版本可用度；
2. 现有“版本级优先、无版本级回退组件级”的集合判定会把两者区别对待（`Nightly-Version-build_pipeline` 命中 `nightly-version%`，`Nightly-Component-build_pipeline` 不命中）。

### 1.2 需求目标

| #   | 目标                                                                |
| --- | ------------------------------------------------------------------- |
| 1   | build 流水线（含后续自定义后缀）被正确识别为 Nightly 专属构建流水线 |
| 2   | 参与**编译成功率**计算                                              |
| 3   | **不参与版本可用度**计算（不是置 0，而是从集合/分母/Avg 中剔除）    |
| 4   | build 流水线不区分版本级/组件级，两者口径完全一致，只是命名不同     |
| 5   | Nightly 流水线看板、工程能力运营看板均正确展示                      |

### 1.3 涉及看板与指标

| 看板               | 关键指标                                                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| Nightly 流水线看板 | 流水线级汇总（编译成功率、版本可用度）、趋势图（版本可用度、编译任务时长）、项目级汇总、运行明细、版本可用度下钻 |
| 工程能力运营看板   | 项目主表 Nightly 编译成功率 / Nightly 版本可用度、Nightly 明细与 KPI 卡片                                        |

### 1.4 涉及计算任务（DolphinScheduler）

1. `[workflow][base]项目与流水线关联关系生成`
2. `[job][dwi->dwr][codearts]Nightly流水线测试用例执行事实表（每条执行记录一行）`
3. `[job][dwr->dm][codearts]nightly流水线每日汇总`（2 个 job）
4. `[job][dwr->dm]nightly逻辑流水线计算`（2 个 job）

### 1.5 不在本期范围

- 资源类看板（资源运营、项目资源、环境资源）不做特殊处理，build 流水线按现有 NIGHTLY 口径自然计入资源消耗；
- 前端不新增“build 流水线”标签；
- build 流水线内的测试任务指标不做额外约定（正常纳入现有测试统计，实际应为空）。

## 3. 口径定义

### 3.1 识别口径

```sql
-- Nightly 专属构建流水线（前缀匹配，后缀允许自定义内容）
LOWER(TRIM(pipeline_name)) LIKE 'nightly-version-build_pipeline%'
   OR LOWER(TRIM(pipeline_name)) LIKE 'nightly-component-build_pipeline%'
```

- 两条前缀仅为命名区别，指标口径**完全等价**，不区分版本级/组件级；
- 后续新增的 `nightly-version-build_pipeline-xxx` / `nightly-component-build_pipeline-xxx` 会自动识别为 build 流水线；
- 每条 build 流水线同时满足：
  - `pipeline_type = 'NIGHTLY'`
  - `is_build_pipeline = 1`
- `pipeline_type` 取值保持不变（`PR` / `NIGHTLY` / `OTHER`），**不新增** `NIGHTLY_BUILD` 枚举。

### 3.2 指标口径

| 指标                      | 取数集合                                                | 说明                                         |
| ------------------------- | ------------------------------------------------------- | -------------------------------------------- |
| 编译成功率                | `pipeline_type='NIGHTLY'`，**含** `is_build_pipeline=1` | 后续 avg 包含 build 一条样本                 |
| 版本可用度                | `pipeline_type='NIGHTLY' AND is_build_pipeline=0`       | build 从集合、分母、AVG 中完全剔除           |
| 版本级/组件级回退         | 只在 `is_build_pipeline=0` 内判定                       | build 不参与回退                             |
| 看板流水线列表            | NIGHTLY 全量（含 build）                                | build 的版本可用度返回 `NULL`，前端展示 `--` |
| 运行次数 / NPU / CPU 均值 | 保持现状（含 build）                                    | 决策 4                                       |

### 3.3 术语

| 术语       | 含义                                                                      |
| ---------- | ------------------------------------------------------------------------- |
| 测试流水线 | 执行 Nightly 测试用例的流水线（版本级 / 组件级）                          |
| 构建流水线 | 仅做编译构建的 Nightly 专用流水线（本次新增）                             |
| 版本可用度 | 按天去重后 `is_version_available=1` 的天数 / 总运行天数，再按流水线求 AVG |
| 编译成功率 | `SUM(build_pass_count) / SUM(build_count)`，按流水线计算后再 AVG          |

## 5. 总体方案

### 5.1 设计原则

1. **`pipeline_type` 不动**，新增正交标识 `is_build_pipeline`，让所有“应包含 build”的既有链路自动兼容；
2. **只在版本可用度上做减法**，编译成功率、资源、列表保持全量；
3. **事实表/汇总表不加字段**，看板查询通过 relation 关联标识，避免改 4 张表结构；
4. **前缀匹配两个固定前缀**（`nightly-version-build_pipeline%` / `nightly-component-build_pipeline%`），不使用宽泛的 `%build_pipeline%`，避免误伤其他流水线；
5. **测试驱动约束**：新增 CTE 命名需规避现有 XML 结构测试的字符串计数与 `NOT LIKE` 禁令。

### 5.2 方案选型

| 方案      | 做法                                                    | 结论                                                                                           |
| --------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| A（推荐） | relation 新增 `is_build_pipeline`，`pipeline_type` 不变 | 改动面小、既有链路自动兼容                                                                     |
| B         | 新增 `pipeline_type='NIGHTLY_BUILD'`                    | 所有“应包含 build”的链路都要改 `IN (...)`，易漏，不推荐                                        |
| C         | 查询内用名称内联判定，不加字段                          | 6+ 个 mapper 重复名称逻辑；且 `OpsNightlyDetailMapperXmlTest` 禁止 `NOT LIKE 'nightly`；不推荐 |

### 5.3 改造后链路

```
relation(NIGHTLY + is_build_pipeline)
   ├── is_build_pipeline = 0 ──> 版本可用度集合 / 版本级回退
   ├── is_build_pipeline = 0 ──> 版本可用度下钻
   └── 全量（含 1）        ──> 编译成功率集合、看板列表、运行明细、资源统计
```

## 6. 数据模型设计

### 6.1 relation 表变更

表：`dm_rd_efc_project_pipeline_relation`

```sql
ALTER TABLE dm_rd_efc_project_pipeline_relation
  ADD COLUMN `is_build_pipeline` tinyint NOT NULL DEFAULT '0'
  COMMENT '是否Nightly专用构建流水线：1是 0否';
```

| 项       | 说明                                                                      |
| -------- | ------------------------------------------------------------------------- |
| 是否可空 | 否，默认 0                                                                |
| 位置     | 追加在最后                                                                |
| 唯一键   | 不变（`product_id, project_id, platform, pipeline_project, pipeline_id`） |
| 在线变更 | 表已开启 `light_schema_change`，可在线加列                                |
| 存量数据 | 默认 0；base 任务下次全量刷新后准确                                       |

### 6.2 不新增 DWR/DM 字段的理由

- 事实表 `dwr_rd_efc_build_fact_nightly_test_case_pipeline_run`、DM 日汇总表、逻辑流水线宽表均按 `pipeline_id` 组织；
- 看板查询可以通过 `dm_rd_efc_project_pipeline_relation` 关联出 `is_build_pipeline`；
- 避免 4 张表加稀疏列、避免 ETL 多写字段、避免历史数据回刷。

### 6.3 兼容性

- 旧查询不感知新列，行为不变；
- 新列为 `0` 时等价于“非 build”，所有新逻辑对存量流水线无影响；
- 前后端接口字段仅**新增** `isBuildPipeline`，无破坏性变更。

### 7.2 `[dwi->dwr] Nightly流水线测试用例执行事实表`

文件：`.../[dwr]dwr_rd_efc_build_fact_nightly_test_case_pipeline_run.sql`

**改动 1：`filtered_pipelines` 带出 build 标识**

```sql
WITH filtered_pipelines AS (
    SELECT
        u.platform,
        u.project_id,
        u.pipeline_id,
        u.pipeline_run_id,
        u.run_number AS pipeline_run_number,
        u.pipeline_name,
        u.status AS pipeline_status,
        u.start_time AS pipeline_start_time,
        u.end_time AS pipeline_end_time,
        u.duration_ms AS actual_duration_ms,
        rel.is_build_pipeline
    FROM dwr_rd_efc_pipeline_run_unified u
    INNER JOIN (
        SELECT pipeline_id, MAX(is_build_pipeline) AS is_build_pipeline
        FROM dm_rd_efc_project_pipeline_relation
        WHERE pipeline_type = 'NIGHTLY'
        GROUP BY pipeline_id
    ) rel ON rel.pipeline_id = u.pipeline_id
    WHERE u.status IN ('COMPLETED', 'CANCELED', 'FAILED')
      AND u.platform IN ('codearts', 'gitcode')
),
```

> 子查询按 `pipeline_id` 聚合，避免 relation 多行导致运行记录翻倍。

**改动 2：build 的 `is_version_available` 置 NULL**

最终 SELECT 第 34 列（当前 L181-L191）：

```sql
CASE
    WHEN fp.is_build_pipeline = 1 THEN NULL
    WHEN fp.pipeline_end_time >= '2026-09-04' THEN
        CASE WHEN tcs.case_run_pass_count = tcs.valid_run_count
                  AND NULLIF(tcs.valid_run_count, 0) != 0
                  AND fp.pipeline_status = 'COMPLETED'
             THEN 1 ELSE 0 END
    ELSE
        CASE WHEN js.build_pass_count = js.build_count
                  AND tcs.case_run_pass_count_p0 = tcs.valid_run_count_p0
                  AND NULLIF(tcs.case_run_pass_count_p0, 0) != 0
                  AND NULLIF(tcs.case_release_count_p0, 0) / NULLIF(tcs.case_total_count_p0, 0) >= 0.9
             THEN 1 ELSE 0 END
END AS is_version_available
```

> 置 `NULL` 是语义修正；**不能替代**查询侧剔除，因为可用度分母仍是 `COUNT(*)`。

### 7.4 `[dwr->dwr] nightlyl逻辑流水线计算`

文件：`.../[job][dwr-dwr]nightlyl逻辑流水线计算.sql`

**改动：`pipeline_binding` 带出 build 标识，alias 对 build 不生效**

```sql
WITH pipeline_binding AS (
    SELECT
        project_id,
        pipeline_project,
        platform,
        pipeline_id,
        MAX(pipeline_type)      AS pipeline_type,
        MAX(is_build_pipeline)  AS is_build_pipeline
    FROM dm_rd_efc_project_pipeline_relation
    GROUP BY project_id, pipeline_project, platform, pipeline_id
)
...
LEFT JOIN dm_rd_efc_nightly_pipeline_alias a
       ON a.project_id        = b.project_id
      AND a.pipeline_project  = b.pipeline_project
      AND a.platform          = b.platform
      AND a.pipeline_id       = f.pipeline_id
      AND COALESCE(b.is_build_pipeline, 0) = 0
WHERE f.pipeline_run_endtime IS NOT NULL
  AND (
        (a.pipeline_id IS NOT NULL
         AND a.valid_from <= f.pipeline_run_endtime
         AND a.valid_to   >  f.pipeline_run_endtime)
     OR (a.pipeline_id IS NULL AND b.pipeline_type = 'NIGHTLY')
  );
```

> 目的：防止 build 流水线被历史别名合并进测试逻辑流水线，污染版本可用度。

## 8. 看板后端详细设计

### 8.1 Nightly 流水线看板

#### 8.1.1 流水线列表返回 build 标识

文件：`openlibing-ops/src/main/resources/mapper/DmRdEfcProjectPipelineRelationMapper.xml`（`selectNightlyPipelines`）

```sql
SELECT
    r.project_id,
    r.platform,
    r.pipeline_id,
    MAX(r.pipeline_name)     AS pipeline_name,
    MAX(r.pipeline_project)  AS pipeline_project,
    MAX(r.is_build_pipeline) AS is_build_pipeline
FROM dm_rd_efc_project_pipeline_relation r
WHERE r.pipeline_type = 'NIGHTLY'
  AND r.project_id = #{projectId}
  AND r.platform <> 'github'
GROUP BY r.project_id, r.platform, r.pipeline_id
ORDER BY pipeline_name
```

### 15.4 版本可用度计算公式（不变）

```text
单流水线可用度 = available_days / total_days
               = SUM(is_version_available = 1 的天数) / COUNT(DISTINCT 运行日期)
项目级可用度   = AVG(单流水线可用度)   -- build 不进入集合，因此不参与平均
```
