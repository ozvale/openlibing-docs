## 2. 新建数据表与清洗（ETL）逻辑

现有表均为小时切片，无法支撑 5 分钟粒度。**新建 1 张时刻维表 + 2 张 5 分钟数据表**，小时表保持不动（现有看板零回归）。

### 2.1 新表 DDL

```sql
-- 表0：时刻维表（1分钟粒度，全天1440行，一次性灌入；通用时刻维表，后续 sdi_base_time2m 也可切换到本表）
CREATE TABLE `sdi_base_time` (
  `time` time NOT NULL COMMENT '时刻（1分钟间隔）'
) ENGINE=OLAP
UNIQUE KEY(`time`)
COMMENT '1分钟粒度时刻维表'
DISTRIBUTED BY HASH(`time`) BUCKETS 1;

-- 表1：任务 × 5分钟切片明细（在小时表 dwr_rd_efc_resource_npu_detail 基础上增加 pipeline_name）
CREATE TABLE `dwr_rd_efc_resource_npu_detail_5m` (
  `platform` varchar(16) NOT NULL COMMENT '平台（codearts/gitcode/github）',
  `pipeline_id` varchar(32) NOT NULL COMMENT '流水线id/workflowId',
  `pipeline_name` varchar(255) NULL COMMENT '流水线名称（ETL 从源表随行带入，后端直接取用）',
  `pipeline_run_id` varchar(32) NOT NULL COMMENT '流水线运行id/workflowRunId',
  `job_id` varchar(64) NOT NULL COMMENT '任务id',
  `slot_time` datetime NOT NULL COMMENT '切片开始时间（5分钟切片）',
  `job_name` varchar(1024) NULL COMMENT '任务名称',
  `job_type` varchar(32) NULL COMMENT '任务类型',
  `job_start_time` datetime NULL COMMENT '任务开始时间',
  `job_run_start_time` datetime NULL COMMENT '任务开始运行时间',
  `job_end_time` datetime NULL COMMENT '任务结束时间',
  `job_pending_duration` int NULL COMMENT '任务排队时长(s)',
  `assign_npu_second` varchar(32) NULL COMMENT '分配的npu卡时（秒，按切片内运行时长比例分摊）',
  `server_ip` varchar(16) NULL COMMENT '服务器ip',
  `job_current_slot_pending_seconds` int NULL COMMENT '当前时间切片排队时长（秒）',
  `job_current_slot_running_seconds` int NULL COMMENT '当前时间切片运行时长（秒）'
) ENGINE=OLAP
UNIQUE KEY(`platform`, `pipeline_id`, `pipeline_run_id`, `job_id`, `slot_time`)
COMMENT 'NPU使用5分钟切片数据'
DISTRIBUTED BY HASH(`platform`, `pipeline_id`, `slot_time`) BUCKETS 20;

-- 表2：服务器 × 5分钟分配资源聚合（与 dm_rd_efc_server_assign_resource_hour 同构）
CREATE TABLE `dm_rd_efc_server_assign_resource_5m` (
  `statistic_period` datetime NOT NULL COMMENT '统计周期（5分钟整点）',
  `server_ip` varchar(16) NOT NULL COMMENT '服务器ip',
  `assign_npu_hours` double NULL COMMENT '分配的总npu卡时',
  `run_job_num` int NULL COMMENT '当前时间切片运行任务数',
  `pending_job_num` int NULL COMMENT '当前时间切片排队任务数'
) ENGINE=OLAP
UNIQUE KEY(`statistic_period`, `server_ip`)
COMMENT '服务器5分钟粒度分配NPU资源信息'
DISTRIBUTED BY HASH(`statistic_period`) BUCKETS 20;
```

- **`pipeline_name` 列【已确认】**：由 ETL 随行带入，所有接口直接取表内列，无需 JOIN 运行事实表。
- **不新建每日汇总表**：区块 6/7/8/9 的每日统计粒度为"天"，直接查 `_5m` 表按天聚合（`_5m` 含 `pipeline_name`，且口径与小时表一致；小时表无 pipeline_name，不使用）。

### 2.2 时刻维表与 5 分钟切片的生成方式

新建**1 分钟粒度通用时刻维表 `sdi_base_time`**（全天 1440 行），5 分钟切片从中筛选 `MINUTE(time) % 5 = 0` 的时刻获得（00/05/10/.../55，共 288 个/天）。相比单建 5 分钟表，1 分钟粒度更通用，后续 `sdi_base_time2m` 的消费方也可统一切换到本表。

**初始化 SQL（一次性执行，全量插入 1440 行）**：

```sql
INSERT INTO sdi_base_time(`time`)
SELECT SEC_TO_TIME(number)
FROM numbers("number" = "1440");
```

ETL 的切片生成：日期表 CROSS JOIN 时刻表 + 5 分钟过滤，结构与现有小时表 ETL 一致：

```sql
-- 5分钟切片 = sdi_base_date × sdi_base_time 中分钟数为5的倍数的时刻
FROM sdi_base_date d
CROSS JOIN sdi_base_time t
WHERE MINUTE(t.`time`) % 5 = 0
```

备选方案（不建维表）：ETL 内直接用 `numbers` TVF 按任务生成切片序列 `FROM_UNIXTIME(FLOOR(UNIX_TIMESTAMP(job_start_time)/300)*300) + INTERVAL number*5 MINUTE`，再过滤超出 `job_end_time` 的部分。缺点是切片随任务生成、无法独立按时间补数重跑，不采用。

### 2.3 清洗（ETL）逻辑

与现有小时表 ETL 同源，仅两处变化：**切片维表换 `sdi_base_time` 并按 5 分钟过滤**；**增补 `pipeline_name` 列随行写入**。

```sql
-- ① 5分钟切片：与现有 time_slots CTE 结构一致，换 1 分钟时刻维表 + 5 分钟过滤
with time_slots_5m AS (
    SELECT
        CONCAT(d.`date`, ' ', t.`time`) AS slot_start,
        DATE_ADD(CONCAT(d.`date`, ' ', t.`time`), INTERVAL 5 MINUTE) AS slot_end
    FROM sdi_base_date d
    CROSS JOIN sdi_base_time t
    WHERE MINUTE(t.`time`) % 5 = 0    -- 原小时表：sdi_base_time2m WHERE time LIKE '%:00:00'
      AND d.`date` >= DATE_FORMAT(DATE_SUB(CURRENT_DATE(), INTERVAL 1 MONTH), '%Y-%m-%d')
),

-- ② 三平台 NPU 任务 UNION：与现有 npu_use CTE 一致（codearts/gitcode/github 三段），各段 SELECT 增补 pipeline_name 列
npu_use AS ( ... 原样 + pipeline_name ... ),

-- ③ 任务与切片求交，计算切片内排队/运行秒数：与现有 run_ratio CTE 一致
run_ratio AS (
    SELECT ...,
        GREATEST(0, TIMESTAMPDIFF(SECOND, GREATEST(t.slot_start, u.job_start_time),
                 LEAST(t.slot_end, u.job_run_start_time))) AS job_current_slot_pending_seconds,
        GREATEST(0, TIMESTAMPDIFF(SECOND, GREATEST(t.slot_start, u.job_run_start_time),
                 LEAST(t.slot_end, u.job_end_time))) AS job_current_slot_running_seconds,
        TIMESTAMPDIFF(SECOND, job_run_start_time, job_end_time) AS job_duration
    FROM npu_use u
    JOIN time_slots_5m t
      ON t.slot_end > u.job_start_time AND t.slot_start < u.job_end_time
)

-- ④ 写入 5 分钟明细表：卡时按切片内运行时长比例分摊（分摊公式在 5 分钟粒度同样成立）
INSERT INTO dwr_rd_efc_resource_npu_detail_5m
SELECT platform, pipeline_id, pipeline_name, pipeline_run_id, job_id, slot_start,
       job_name, job_type, job_start_time, job_run_start_time, job_end_time,
       job_pending_duration,
       npu_second * job_current_slot_running_seconds / job_duration,
       server_ip,
       job_current_slot_pending_seconds,
       job_current_slot_running_seconds
FROM run_ratio;

-- ⑤ 聚合到服务器×5分钟表
INSERT INTO dm_rd_efc_server_assign_resource_5m
SELECT
    slot_time,
    server_ip,
    SUM(CAST(assign_npu_second AS DOUBLE)) / 3600 AS assign_npu_hours,
    COUNT(CASE WHEN job_current_slot_running_seconds > 0 THEN 1 END) AS run_job_num,
    COUNT(CASE WHEN job_current_slot_pending_seconds > 0 THEN 1 END) AS pending_job_num
FROM dwr_rd_efc_resource_npu_detail_5m
WHERE server_ip IS NOT NULL
GROUP BY slot_time, server_ip;
```

> 注：run_job_num / pending_job_num 的统计条件以 running / pending_seconds 判定（小时表 ETL 已修正，两表口径保持一致）。

## 3. 术语与核心口径

| 术语 | 口径定义 |
|------|---------|
| 时间窗口 | `startTime` / `endTime` 均向下取整到 5 分钟；每日接口按天 |
| 时间切片（slot） | 5 分钟粒度，对应 `_5m` 表 `slot_time` / `statistic_period`；每日接口同样查 `_5m` 表按天聚合 |
| 使用率（占用） | `SUM(assign_npu_hours) / (SUM(total_npu_num) / 12)` 按切片；即分配率口径，单机单切片 = `assign_npu_hours × 12 / total_npu_num` |
| 使用率上限 | 计算结果超过 100% 时截断为 100%（沿用现有分配率 cap 规则） |
| 排队/运行任务数（某切片） | 该切片上 `job_current_slot_pending_seconds > 0` / `job_current_slot_running_seconds > 0` 的去重任务数 |
| 排队时长（分钟） | `job_pending_duration / 60`（任务总排队时长，非切片内排队时长） |
| 卡时 | `SUM(assign_npu_second) / 3600` |
| 排队 P90（分钟） | job 级样本：每 job 取全表切片行 `MAX(job_pending_duration)`（各切片行值可能不一致，取终态值），按 job 起始日归组，统计全部任务；样本值与查询窗口无关（PERCENTILE 不可先聚合再合并） |
| 流水线类型（platform） | `codearts` / `gitcode` / `github` |

### 接口 1：KPI 卡组（`/common/card` + category `ops-npu-usage-summary`）

一次请求返回全部资源池的"排队卡 + 使用率卡"，映射到通用 `CardResp`：

```java
// Req：OpsNpuUsageSummaryCardReq extends CardReq + projectId/resourcePoolIds
// Handler：OpsNpuUsageSummaryCardService implements CardService<OpsNpuUsageSummaryCardReq>，委托 NpuUsageService

// CardResp.cards —— 每池拆为多个 CardItem：
// 排队卡（每池 1 项）：name=池名, metric="queueTask", value=queueCount, unit="个", sparkline=窗口内每切片排队任务数
// 使用率卡（每池 3 项）：metric="usageRate" value=usageRate(%)；metric="usedCards" value=已用卡数 unit="张"；
//                      metric="freeCards" value=空闲卡数 unit="张"
```

- **告警展示【已确认】**：高保真排队卡"告警阈值 20"为前端展示逻辑（queueCount ≥ 20 时红色告警态），后端只返回 queueCount，不返回告警标志。
- 排队 KPI：`detail_5m` JOIN 维表按池聚合，每切片排队任务数；最新切片取窗口内 `MAX(slot_time)`。
- 使用率 KPI：`assign_5m` JOIN 维表，`SUM(assign_npu_hours)` 按池聚合，×12/切片数折算卡数；总卡数从静态维表取；usageRate cap 100%。

### 接口 1b：资源池使用率明细（`/common/detail` + category `ops-npu-pool-usage-detail`）

使用率卡下钻数据。此前复用的资源运营看板 `ops-resource-pool-detail` 总卡时口径为宽表 `dm_rd_efc_server_resource_hour` 行级 `actual_total_npu_hour` 兜底，与使用率卡"静态维表总卡数 × 窗口小时数"不一致，故新增本接口。

```java
// Req：OpsNpuPoolUsageDetailReq extends DetailReq + projectId/resourcePoolId（单选，与资源池明细接口一致）
// Handler：OpsNpuPoolUsageDetailService implements DetailService，委托 NpuUsageService

// Resp：OpsNpuPoolUsageDetailResp —— 每行一个池位置行 (resource_pool_id, location)：
// resourcePoolId/resourcePoolName/location/allocRate/projectNames(chips)/machines
// MachineDetail：ip/totalNpuHours/assignNpuHours/allocRate（少使用卡时相关字段）
```

- **结构与资源运营看板资源池明细一致**（位置行 + 项目 chips + 机器级明细，同一池跨云上/实验室拆两行、机器按自身 location 挂行），少使用卡时相关字段（无 `usedNpuHours`、无使用卡时口径的率）。
- **口径与使用率卡一致**（新增机器行 SQL `queryPoolUsageMachines`：静态维表机器骨架 LEFT JOIN `assign_5m` 窗口聚合）：
  - 机器总卡时 = 机器卡数（静态维表 `actual_npu_num`，(pool_id, server_ip) 机器级去重）× 窗口小时数（窗口切片数/12）
  - 机器分配卡时 = 窗口内 `SUM(assign_npu_hours)`；机器分配率 = 分配/总 × 100，cap 100%
  - 池级分配率 = Σ分配 cap Σ总 / Σ总 × 100（分子 cap 与卡片同口径）
  - 项目 chips 查 `dwi_rd_efc_project_resource_pool_relation` 去重项目名
- 窗口上限与卡片一致 72h；池总数不超过 50，全量不分页（`page/pageSize` 忽略，PageResult 包装兼容框架）。
- 排序：Java 层排序，白名单 `alloc_rate`/`resource_pool_name`（snake_case，与资源池明细接口一致），`sortRule` 默认 desc；无 sortField 时默认按池ID+位置升序，兜底按池ID保证稳定。

### 接口 2：趋势分析（`/common/chart` + category `ops-npu-usage-trend`）

映射到通用 `ChartResp`（title + xAxis + series）：

```java
// xAxis：5分钟刻度 'yyyy-MM-dd HH:mm'
// series[0]：name="使用率(%)", data=每切片使用率，cap 100%
// series[1]：name="排队任务数", data=每切片排队任务数
// 双 Y 轴由前端渲染决定，后端不感知
```

- 每切片排队任务数：`detail_5m` 按 `slot_time` 统计 `pending_seconds>0` 去重任务数。
- 每切片使用率：`assign_5m` 按 `statistic_period` 求 `SUM(assign_npu_hours)`；分母 = 窗口内机器 `SUM(total_npu_num)`（静态维表）/ 12。
- Service 层补全缺失切片（补 0），刻度生成参照 `buildRunWindowLabels` 改为 5 分钟步进；最高点高亮由前端计算。
- 72h 窗口 ≈ 864 个切片，返回体量可控。

### 接口 3：热力图 `POST /npu-usage/heatmap`（独立接口）

固定 5 分钟粒度。二维矩阵（机器×时间）+ 每格任务名 tooltip，无法映射到 ChartResp 的 xAxis+series 结构，做独立接口。

**入参**：

```java
public class NpuUsageHeatmapReq extends TimeReq {
    private Integer projectId;
    private List<Long> resourcePoolIds;
    private String generation;   // 卡型筛选，可选
}
```

**出参**：

```java
public class NpuUsageHeatmapResp {
    private List<MachineRow> machines;

    public static class MachineRow {
        private String serverIp;
        private String resourcePoolName;
        private String generation;
        private Integer totalNpuNum;
        private List<HeatCell> cells;
    }

    public static class HeatCell {
        private String slotTime;
        private Double usageRate;      // assign_npu_hours×12/total_npu_num，cap 100%
        private Boolean fault;         // 预留，恒 false
        private List<String> jobs;      // 该机该切片运行中任务名（tooltip）
    }
}
```

- **故障态【已确认】**：目前获取不到故障机器数据，`fault` 恒 false 预留，本期不实现。
- 机器骨架：静态维表（池/卡型筛选后），不按时间过滤。
- 单元格值：`assign_5m` 按 `(server_ip, statistic_period)` 取 `assign_npu_hours × 12 / total_npu_num`。
- jobs：`detail_5m` 查该 `(server_ip, slot_time)` 上 `running_seconds>0` 的 DISTINCT `job_name`（沿用现有 `queryHeatmapJobs` 模式换表）。
- 机器行排序：资源池 → 卡型 → server_ip。
- **窗口上限 24h**【已确认】（后端校验），24h × 12 = 288 列，前端横向滚动展示。

### 接口 4：任务明细抽屉（`/common/detail` + 两个 category）

支撑三类点击：趋势图数据点（全量机器+某切片）、热力图单元格（单机器+某切片）、热力图机器名（单机器×整个窗口）。抽屉"排队/运行"两个 tab 各注册一个分页 category：

| category | 入参（继承 DetailReq 扩展） | 返回 |
|----------|---------------------------|------|
| `ops-npu-slot-queue-detail` | `slotTime`（可选）、`serverIp`（可选）+ 公共时间窗 | 排队任务分页列表 |
| `ops-npu-slot-running-detail` | 同上 | 运行任务分页列表 |

```java
public class OpsNpuSlotTaskDetailReq extends DetailReq {
    private String slotTime;   // 指定 5 分钟切片（趋势点/热力图格子点击）
    private String serverIp;   // 指定机器（热力图点击）
    private String platform;   // 平台过滤（每日分层抽屉流水线行下钻传入）
    private String pipelineId; // 流水线过滤（每日分层抽屉流水线行下钻传入）
}

public class OpsNpuSlotTaskResp extends DetailResp {
    private String platform;
    private String pipelineName;   // 直接取 _5m 表 pipeline_name 列
    private String jobName;
    private Double queueMinutes;  // job_pending_duration/60（任务自身完整排队时长，不按窗口截断）
    private Double runMinutes;    // job 级总运行时长/60（任务自身完整运行时长，不按窗口/切片截断）
    private String serverIp;
    private String jobUrl;        // 任务跳转链接，SQL 按平台拼接（见下）
}
```

- KPI 数字（使用率/排队数/运行数）前端在点击时已从趋势/热力图数据获得，无需后端重复返回。
- `slotTime` 非空：查该切片 `pending_seconds>0` / `running_seconds>0` 的任务；`serverIp` 非空时追加过滤。
- `slotTime` 为空且 `serverIp` 非空（机器行点击）：窗口内该机器全部切片任务去重（job 级）。
- `platform` / `pipelineId` 非空时追加过滤（每日分层抽屉流水线行下钻场景，`pipelineId` 取 daily-drill 返回值，避免流水线改名/同名导致偏差）。

**jobUrl 拼接规则**：`querySlotTasks` LEFT JOIN `dm_rd_efc_project_pipeline_relation`（按 `pipeline_id` 去重取 `project_id` / `repo_url`），SQL 内按平台拼接：

| platform | 规则 |
|----------|------|
| codearts | `https://www.openlibing.com/apps/pipelineDetail?projectId={project_id}&pipelineId={pipeline_id}&pipelineRunId={pipeline_run_id}`（不带 jobRunId） |
| gitcode / github | `repo_url` 去 `.git` 后接 `/actions/runs/{pipeline_run_id}/job/{job_id}` |

关联不到 `project_id` / `repo_url` 时 `jobUrl` 为 null（前端隐藏跳转入口）。

### 接口 6：每日消耗总卡时（`/common/chart` + category `ops-npu-daily-card-hours`，查 `_5m` 表）

```java
// series[0]：name="总卡时", data=每日 SUM(assign_npu_second)/3600
// series[1]：name="P90 卡时", data=run 级卡时样本的 P90
```

**口径**：run 级卡时样本 = 每 `(platform, pipeline_id, pipeline_run_id)` 的**全表完整** `SUM(assign_npu_second)/3600`（先全表按 run 聚合拿完整卡时，不做窗口过滤，避免跨窗口 run 被截断），按 run 起始日归组，样本值与查询窗口无关；P90 对该样本集合计算。

### 接口 7：每日使用 NPU 流水线平均卡时（`/common/chart` + category `ops-npu-daily-pipeline-card-hours`，查 `_5m` 表）

```java
// series[0]：name="平均卡时", data=每日流水线卡时集合的平均
// series[1]：name="P90 卡时", data=该集合的 PERCENTILE(0.9)
```

**口径**：流水线级样本 = **每日每** `(platform, pipeline_id)` 的**当日**卡时合计（按切片归属日 + 流水线分组，单日样本自包含，同一日数据与查询窗口无关），avg = 当日集合平均，P90 = 当日集合的 `PERCENTILE(0.9)`。

### 接口 8：每日分层汇总（抽屉） `POST /npu-usage/daily-drill`（独立接口，查 `_5m` 表）

点击每日图表数据点，展示当日按 codearts/gitcode/github 分层汇总 + 流水线分组明细。platform→pipeline 层级树不适合分页框架，做独立接口。

**入参**：`date`（yyyy-MM-dd）+ `projectId`（可选）

**出参**：

```java
public class NpuUsageDailyDrillResp {
    private Integer totalTasks;
    private Double avgQueueMinutes;
    private Double p90QueueMinutes;
    private List<PlatformSummary> platforms;   // codearts/gitcode/github → 流水线两级

    public static class PlatformSummary {
        private String platform;
        private Integer taskCount;
        private Double avgQueueMinutes;
        private Double totalCardHours;
        private List<PipelineSummary> pipelines;
    }

    public static class PipelineSummary {
        private String pipelineId;    // 流水线ID，流水线行下钻切片任务明细时传参
        private String pipelineName;
        private Integer taskCount;
        private Double avgQueueMinutes;
        private Double cardHours;
    }
}
```

- `_5m` 表 `DATE(slot_time)=date` 过滤，platform / pipeline 两级聚合（`pipeline_name` 直接取表内列）。不做分页（抽屉全量，每日任务量千级以内）。
- `p90QueueMinutes`：run 级排队样本（job 级样本再按 run 取 MAX）按 **run 起始日**归组后取 P90；`avgQueueMinutes` 同样取 run 级样本均值（同源同归日）；`totalTasks` 仍按切片归属日（job 级去重，与图任务总数一致）；`platforms[]/pipelines[]` 内的 `avgQueueMinutes` 为 job 级样本（切片归属日）。
- 流水线行下钻：前端点击流水线行调 `/common/detail`（`ops-npu-slot-queue-detail` / `ops-npu-slot-running-detail`），传当日 `00:00:00 ~ 23:59:59` 窗口 + `platform` + `pipelineId`；注意排队/运行明细按状态过滤，同一任务当天既排队又运行会出现在两个 tab，两 tab 条数之和可能大于 `taskCount`。

## 5. 关键技术方案

| 项 | 方案 |
|----|------|
| 新增文件 | `NpuUsageController`（仅 heatmap/daily-drill 两个接口）、`NpuUsageService`（app.service.ops，承载全部业务逻辑，被 card/chart/detail handler 委托）、`NpuUsageMapper` + XML、1 个 Card Req + CardService 实现、4 个 Chart Req + ChartService 实现、2 个 Detail Req/Resp/DetailService 实现 |
| 现有文件改动 | 仅"注册类"纯新增：`CardReq`/`ChartReq`/`DetailReq` 各追加 @JsonSubTypes 行，`CardCommonEnum`/`ChartCommonEnum`/`DetailCommonEnum` 各追加枚举；其余现有类与 SQL 零改动 |
| 率值精度 | SQL 层 0-1 小数，Service 层 `NumberUtil.roundDecimal(v*100)`；cap 100% |
| 刻度/日期补齐 | 5 分钟步进刻度生成（参照 `buildRunWindowLabels`，Java 侧窗口取整：`floorTo5Min`/`ceilTo5Min`）；每日接口沿用 `DateUtil.splitTime` |
| CAST 处理 | `assign_npu_second` 均 `CAST AS DOUBLE` + `IFNULL(...,0)` |
| 排序 | 抽屉列表排序字段走 `SortFieldValidator` 白名单 |

## 6. 测试要点

- Service 单测：5 分钟窗口取整、切片补 0、使用率 cap 100%、空窗口、项目/池过滤组合、热力图窗口 >24h 报参数错误。
- Mapper SQL：与 Doris 实际数据核对排队/运行去重口径、P90 口径与现有看板一致。
- 回归：现有接口与 SQL 零改动；重点回归 `/common/detail`、`/common/card`、`/common/chart` 多态路由（确认新增 @JsonSubTypes 不影响既有 category 反序列化）。
