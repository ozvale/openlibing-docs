> 后端 commit：`713f8938`（申请卡数）/ `b1b48add`（等待卡数口径修正）/ `672c960c`（新增接口）/ `f499cc46`（使用卡数改取运行任务真实申请卡数）/ `0e23ebaf`（三条曲线统一数据源，总卡数 = 使用卡数 + 等待卡数）/ `4e52b6de`（总卡数改回机器物理卡数口径，使用/等待去掉互斥归类）/ `06ac35d6`（申请卡数统一改取 5m 明细表 `total_npu`，明细 `applyNpuNum` 与卡数趋势同源），openlibing-ops 分支 `usage_analyse_1030`
> 关联 Issue：[#300](https://gitcode.com/openlibing/openlibing-ops/issues/300)（父需求 [#208](https://gitcode.com/openlibing/openlibing-ops/issues/208) 第三点「使用率页面」）

## 1. 接口

| 项 | 值 |
|------|------|
| 路径 | `POST /common/chart`（网关前缀 `/gateway/openlibing-ops`） |
| Content-Type | `application/json` |
| 用途 | 「卡数趋势」单张图：总卡数 / 使用卡数 / 等待卡数三条曲线 |

与「趋势分析」走同一个通用图表接口，仅 `category` 不同；请求/响应结构与既有 `ops-npu-usage-trend` 完全一致。

## 2. 请求

```json
{
  "category": "ops-npu-usage-card-trend",
  "startTime": "2026-09-02 00:00:00",
  "endTime": "2026-09-04 23:55:00",
  "projectId": 123,
  "resourcePoolIds": [1, 2]
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `category` | string | 是 | 固定 `ops-npu-usage-card-trend` |
| `startTime` | string | 是 | `yyyy-MM-dd HH:mm:ss` |
| `endTime` | string | 是 | `yyyy-MM-dd HH:mm:ss`，与 `startTime` 间隔 **≤ 72 小时** |
| `projectId` | number | 否 | 项目 ID，为空统计全部 |
| `resourcePoolIds` | number[] | 否 | 资源池多选，为空统计全部 |

## 3. 响应

```json
{
  "code": 200,
  "messageCn": "成功",
  "messageEn": "success",
  "data": {
    "title": "流水线NPU卡数趋势",
    "xAxis": [
      "2026-09-02 00:00",
      "2026-09-02 00:05",
      "2026-09-02 00:10",
      "2026-09-02 00:15",
      "2026-09-02 00:20"
    ],
    "series": [
      { "name": "总卡数", "data": [1316.0, 1316.0, 1316.0, 1316.0, 1316.0] },
      { "name": "使用卡数", "data": [474.0, 503.0, 433.0, 455.0, 424.0] },
      { "name": "等待卡数", "data": [3118.0, 3242.0, 3321.0, 3315.0, 3395.0] }
    ]
  }
}
```

（以上为 2026-09-02 00:00~00:20 的返回样例：`总卡数` 取所选资源池的**机器物理卡数**，窗口内恒定为一条水平线（此池实测 1316）；`使用卡数` / `等待卡数` 为**上一版互斥口径**的实测值，当前口径已去掉互斥归类，边界切片「既排队又运行」的任务会在两条曲线各计一次，实际值略高于此例，待重启实测后刷新）

### 结构说明

- `data.xAxis`：时间切片标签，格式 `yyyy-MM-dd HH:mm`，**粒度固定 5 分钟**，无数据的切片也会占位
- `data.series`：**固定 3 条、顺序固定**，按下标取值即可，不要按 `name` 匹配（见下）
- `series[i].data`：长度与 `xAxis` 严格一致，**无 null**，无数据补 `0`，可直接喂给 ECharts

| 下标 | `name` | 单位 | 口径 |
|------|------|------|------|
| 0 | 总卡数 | 张 | 所选资源池的**机器物理卡数**：静态维表 `sdi_rd_efc_server_machine_hidevlab` 按 `server_ip` 机器级去重后 `SUM(actual_npu_num)`（一卡多代已折算）；**窗口内恒定**，图上是一条水平线；与「使用率」分母同源。**与使用卡数 / 等待卡数不是同一口径**，恒等式 `总卡数 = 使用卡数 + 等待卡数` 不成立 |
| 1 | 使用卡数 | 张 | 该切片**有运行秒数**的任务（`job_current_slot_running_seconds > 0`）的申请卡数之和；申请卡数直读 5m 明细表 `dwr_rd_efc_resource_npu_detail_5m.total_npu`（先按 `(platform, job_id, server_ip)` 取 `MAX` 消切片，再按 `(platform, job_id)` 求和得 job 总申请卡数）；**不按机器容量封顶**（申请值可大于总卡数）；与「运行任务明细抽屉」的申请卡数同源同口径 |
| 2 | 等待卡数 | 张 | 该切片**有等待秒数**的任务（`job_current_slot_pending_seconds > 0`）的申请卡数之和，即队列需求，数值上属数千量级。申请卡数算法与使用卡数完全一致（同 5m 明细表 `total_npu` 的 job 级两层聚合）；与「排队任务明细抽屉」的申请卡数同源，且**同一切片的取值与查询窗口无关** |

> **边界切片会重复计数**：同一任务在同一 5 分钟切片内可能既有等待秒数又有运行秒数（实测 00:05 切片有 15 个此类任务），此时它会同时计入使用卡数与等待卡数。因此 `使用卡数 + 等待卡数` 不是该切片活跃任务的申请卡数总和，两条曲线也不是同源同集合的互斥切分。

## 4. 前端接入要点

1. **双 Y 轴**：等待卡数（约 3100~3400）量级最大且持续高于另两条；总卡数（此池实测 1316，窗口内水平线）与使用卡数（约 420~500）都属百千量级，可共用一个轴，但使用卡数只有总卡数约三分之一的高度；建议**等待卡数单独一个轴**（`yAxisIndex: 1`），总卡数与使用卡数共用左轴——与卡片初版设计一致（总卡数在左轴作容量参照线）。若更在意使用卡数的可读性，也可改为让使用卡数单独占一个轴。
2. **配色建议**：总卡数灰蓝 `#64748b`、使用卡数紫 `#7c3aed`、等待卡数橙 `#f97316`（等待卡数可加半透明面积区分）。
3. **右轴不画网格线**：左轴保留网格作为主参照，避免两套网格造成读数混乱。
4. **不要读两条轴的交叉点**：左右轴量纲不同，交叉点无业务含义；务必用 axis 触发的 tooltip 同时展示三条曲线的真实数值。
5. **下钻**：点击曲线上任一点 → 用该点对应的 `xAxis[dataIndex]` 拼成 `slotTime`（`yyyy-MM-dd HH:mm:00`）打开时段任务明细抽屉，行为与「趋势分析」一致。
6. **缩放**：图表内的 `dataZoom` 是前端本地缩放，不会触发重新请求；只有页面级筛选（项目 / 资源池 / 时间范围）变化才重新请求。

## 5. 约束与注意事项

- **时间窗口超过 72 小时会报错**，前端需在筛选处限制，或对报错做提示兜底
- **三条曲线时间轴一致、口径不一致**：都基于 `dwr_rd_efc_resource_npu_detail_5m` 的同一条 5 分钟切片时间轴，任务集合都是该切片**活跃任务 = 等待任务 ∪ 运行任务**（`job_current_slot_pending_seconds > 0 OR job_current_slot_running_seconds > 0`）；但总卡数是**机器物理卡数**口径，使用卡数 / 等待卡数是**任务申请卡数**口径
- **不存在 `总卡数 = 使用卡数 + 等待卡数`**：总卡数来自静态维表（容量），使用 / 等待来自 5m 明细表的任务申请卡数（需求）。两者量级关系是「需求 vs 容量」，使用卡数、等待卡数均可大于总卡数
- **边界切片重复计数**：同一 (切片, 任务) 若同时有等待与运行秒数，会在使用卡数、等待卡数中各计一次，因此 `使用卡数 + 等待卡数` 也不是该切片活跃任务的申请卡数总和
- **总卡数是容量参照线**：窗口内恒定（此池实测 1316），与同页 KPI 卡、热力图口径一致
- 等待卡数是**队列需求**，数值上属数千量级，可远超机器容量
- 使用卡数 / 等待卡数取**5m 明细表**口径（`dwr_rd_efc_resource_npu_detail_5m.total_npu`，按 `platform + job_id` 取 job 级常量，明细表不做时间过滤），两者**同源同算法**（都是 job 级申请卡数两层聚合），归属只看该切片是否有运行 / 等待秒数；因此**同一切片的取值不随查询窗口变化**。原先「窗口越短、等待卡数偏低」的偏差已消除（`06ac35d6` 起明细抽屉与趋势共用同一取数）
- **与明细抽屉逐点对齐的前提**：明细返回的是窗口内 **job 级去重**集合，不带 `slotTime` 时一个 job 只出现一次、跨多个切片合并，不能与单切片趋势值直接相加比对；要对账须带精确 `slotTime`（如 `2026-09-15 18:45:00`），此时 `使用卡数 = 该切片运行任务明细的 applyNpuNum 之和`、`等待卡数 = 该切片排队任务明细的 applyNpuNum 之和`
- **总卡数与「使用率」分母同源，但 `使用卡数 ÷ 总卡数 ≠ 使用率`**：使用率为分配卡时口径（`Σ assign_npu_hours / (Σ total_npu_num / 12)`），使用卡数则是任务申请卡数口径
- 接口耗时参考：本地实测 457~1008ms（申请卡数改取 5m 明细表后为 690ms），与同页其它曲线同量级。若你在 Doris 控制台里量到「4 秒」，那是控制台固定开销（`SELECT 1` 同样是 4 秒），与接口无关

## 6. 关联改动：任务明细下钻新增「申请卡数」

同一需求（#300）的「点击下钻时，job 任务增加使用卡数的数据展示」对应**切片任务明细接口新增响应字段 `applyNpuNum`**，后端 commit `713f8938`，**前端需要适配**。

| 项 | 值 |
|------|------|
| 路径 | `POST /common/detail`（网关前缀 `/gateway/openlibing-ops`） |
| category | `ops-npu-slot-queue-detail`（排队 tab）/ `ops-npu-slot-running-detail`（运行 tab） |
| 用途 | 点击卡数趋势 / 趋势分析 / 热力图后打开的任务明细抽屉 |

### 请求

在原有 `category` / `startTime` / `endTime` 基础上，按点击来源传（均为可选）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `slotTime` | string | 5 分钟切片 `yyyy-MM-dd HH:mm`，趋势点 / 热力图格子点击时传 |
| `serverIp` | string | 机器 IP，热力图机器行点击时传 |
| `projectId` | number | 项目 ID，为空统计全部 |
| `resourcePoolIds` | number[] | 资源池多选，为空统计全部 |
| `platform` / `pipelineId` | string | 每日分层抽屉下钻时传，为空统计全部 |

### 响应

`data.records[]` 为**按资源池分组**的 `OpsNpuSlotTaskGroupResp`（含 `resourcePoolId` / `resourcePoolName` / `records[]`），分组内每个任务记录**新增字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `applyNpuNum` | number \| null | **任务实际申请卡数**。取 5m 明细表 `dwr_rd_efc_resource_npu_detail_5m.total_npu`：先按 `(platform, job_id, server_ip)` 取 `MAX` 消掉切片维度，再按 `(platform, job_id)` 求和得到该 job 的总申请卡数，最后四舍五入取整；明细表无该任务行时为空（`06ac35d6` 起替代原「任务事实表 NPU 总量 ÷ 运行时长，下限 1，codearts 整点 ÷ 3600」算法） |

### 前端适配要点

1. 任务明细表新增「申请卡数」列，直接取 `applyNpuNum`。
2. `applyNpuNum` 可能为 `null`（该任务在 5m 明细表无对应行，如 github / gitcode 目前 `total_npu` 未清洗到该表），展示用 `--` 占位，不要按 0 处理。
3. 与卡数趋势的「使用卡数 / 等待卡数」**同源同口径**（都是 5m 明细表 `total_npu` 的 job 级两层聚合），同一 (切片, 任务) 两处取值一致。
