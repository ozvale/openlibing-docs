# Nightly 流水线新旧切换历史数据合并方案对比

- 关联 Issue：https://gitcode.com/openlibing/openlibing-ops/issues/289
- 目标仓库：`openlibing-ops`、`openlibing-ops-web`、`openlibing-docs`
- 涉及数据层：Doris、DolphinScheduler
- 文档状态：方案对比，待评审
- 编写日期：2026-10-26

---

## 1. 需求白话版

### 1.1 切换前

某条 Nightly 流水线叫 `X`，`pipeline_id = A`。它每天正常跑，看板上能看到 `X` 的执行次数、成功率、时长、版本可用度等历史数据。

### 1.2 切换后

为了切 pytest：

- 旧流水线 `A` 改名为 `old_X`；
- 新流水线改名为 `X`，`pipeline_id = B`；
- 新流水线在正式切换前，已经用 `X` 这个名字跑过一段时间 pytest 调试。

### 1.3 看板现在的问题

看板按 `pipeline_id` 统计，于是：

1. 旧流水线 `A` 被当成 `old_X` 或直接判成 `OTHER`，历史数据从 Nightly 看板消失；
2. 新流水线 `B` 从第一次调试开始的数据全部被算成正式 Nightly 数据；
3. 看板上看起来像 `X` 的历史被清空，然后突然出现一段调试数据。

### 1.4 期望效果

对业务来说，`X` 还是同一条流水线，只是中间换了 ID。看板应该表现为：

- 切换前的数据来自旧流水线 `A`；
- 切换后的数据来自新流水线 `B`；
- 新流水线 `B` 在切换前的 pytest 调试运行不计入正式 Nightly 指标；
- 日期范围跨切换点时，一条逻辑流水线 `X` 的曲线是连续的；
- 点开明细时，旧运行和新运行都能看到，且跳转链接仍然指向实际运行的流水线。

涉及页面：

- Nightly 流水线看板（图表、汇总、明细、下钻）；
- 工程能力运营看板（Nightly 明细、资源环境 Nightly、主表 Nightly 指标）；
- 开源项目运营看板（Nightly 汇总、Nightly 明细，与 Nightly 看板共用后端口径）。

---

## 2. 关键难点

不管选哪个方案，都要回答下面几个问题：

1. **怎么知道旧 ID 和新 ID 是同一条流水线？**
   - 目前唯一稳定线索是名称：旧名称 = `old_` + 新名称。
2. **怎么知道哪一天算切换完成？**
   - 当前业务确认的口径是：旧流水线最后一次运行时间。
3. **怎么区分新流水线的调试运行和正式运行？**
   - 切换时间之前的运行视为调试，之后视为正式。
4. **怎么保证汇总指标准确？**
   - 执行次数、构建数可以相加；
   - 成功率、P50/P90/P95、版本可用度、最新用例不能简单相加或平均，必须按逻辑流水线重新计算。
5. **怎么保证下钻和跳转链接不坏？**
   - 明细行最好保留实际 `pipeline_id`，逻辑 ID 只用于分组和筛选。

## 3. 候选方案

### 方案 A：Issue 原方案 —— 增量刷新 + 按 pipelineName 汇聚

> Issue 原文写的是“Nightly 计算任务从每次全部刷新，改成只刷新当天数据”；你补充为“只更新最近两个小时”。两者本质都是把全量刷新改成增量刷新，下面按“最近两小时”描述。

**做法（白话）**

- DWR/DM 计算任务不再每次把所有历史数据重算一遍，只算最近两小时的数据；
- 历史数据保持当时写入的 `pipeline_name` 和 `pipeline_id`，不再被全量刷新覆盖；
- 看板计算时不再按 `pipeline_id` 分组，而是按 `pipeline_name` 分组，这样旧名称 `X` 和新名称 `X` 的数据会汇聚到一起。

**优点**

- 不新增映射表，数据结构改动小；
- 后端分组条件从 `pipeline_id` 改成 `pipeline_name`，看起来改动直接；
- 历史数据不重刷，理论上可以保留旧流水线当时的名称。

**缺点和风险**

- **不能排除新流水线的调试数据**。新流水线调试时名称已经是 `X`，按名称汇聚会把调试数据一起算进去。
- 旧流水线改名后，如果有任何任务重刷到它的历史行，名称会变成 `old_X`，又会和新名称 `X` 分开。
- 流水线名称不唯一，不同项目、不同平台可能重名，必须同时按 `project_id + platform + pipeline_name` 分组，否则会串数据。
- `relation` 生成任务仍然只认 `nightly-ci-version%` 等名称，`old_X` 会被判成 `OTHER`，还需要同步改 relation 规则。
- 两小时增量刷新需要可靠的水位线和补数机制，迟到数据、重跑、失败重试都可能造成漏数或重复。
- 明细下钻仍然需要知道实际 `pipeline_id`；只按名称查会把旧、新两条流水线的运行混在一起，且无法精确控制“切换前用旧、切换后用新”。

**结论**

- 实现看起来简单，但不能解决“排除调试数据”和“名称重名/改名”问题。
- 不建议作为最终方案，只能作为辅助思路。

### 方案 B：映射表 + 查询门面（你刚才想的方案）

**做法（白话）**

- 建一张映射表，里面存“逻辑流水线 → 所有实际 `pipeline_id`”的完整对应关系，同时记录每个实际 ID 的有效时间范围：
  - 旧 ID `A`：有效到切换时间；
  - 新 ID `B`：从切换时间之后开始有效。
- 查询前先加一个“门面”：
  1. 根据用户选的逻辑流水线，去映射表查出所有实际 `pipeline_id`；
  2. 把这些 ID 传给现有的查询；
  3. 查询结果再在门面里合并，对前端仍然返回一条逻辑流水线。
- 这样现有看板 SQL 和前端尽量不动，主要新增“ID 解析 + 结果合并”的门面层。

**优点**

- 不重刷历史数据，事实表和 DM 表保留真实 `pipeline_id`；
- 映射关系集中管理，以后再有流水线切换，只加映射数据；
- 明细、下钻、跳转链接可以拿到实际 `pipeline_id`，链接不容易坏；
- 对“列表 + 明细”类查询比较友好；
- 如果只统计执行次数、构建数这类可加指标，门面合并很简单。

**缺点和风险**

- **现有聚合 SQL 是按 `pipeline_id` 分组的，门面拿到的是一批已经聚合过的行。**
  - 执行次数、构建数可以相加；
  - 成功率可以拿通过数/总数重新算；
  - 但 P50/P90/P95、最大值、最小值、平均值、版本可用度、最新一次用例，**不能靠两行聚合结果直接合并**，否则结果会失真。
- 要保证这些指标准确，门面要么重新查原始运行明细，要么还是得改聚合 SQL，让它按逻辑流水线分组。
- 现有接口大多只接受一个 `pipelineId`，门面要支持“一个逻辑 ID 对应多个实际 ID”，接口参数和返回结构需要适配。
- 前端表格的 `row-key`、下钻参数、导出逻辑都默认一条记录一个 ID，需要确认是否能接受门面重写后的 ID。
- 工程能力主表和资源环境如果读的是预聚合表，门面帮不上忙，预聚合任务仍然要改。

**结论**

- 这个方案适合做“ID 解析层”和“明细/列表入口”，是一个很好的基础组件。
- 但**单独靠门面不能保证所有指标准确**，尤其是 Nightly 看板里的分位数、版本可用度、最新用例。
- 推荐把它作为方案 C 或 D 的一部分，而不是单独承担全部合并逻辑。

### 方案 C：映射表 + 各看板 SQL 内部归属

**做法（白话）**

- 建映射表，记录旧 ID、新 ID、切换时间。
- 每个 Nightly 相关 SQL 里先做一步“归属”：
  - 旧 ID 的运行全部算到新 ID；
  - 新 ID 只保留切换时间之后的运行；
  - 然后按逻辑 ID 分组、聚合。
- 前端拿到的就是一条逻辑流水线，明细下钻也按逻辑 ID 展开成“旧 ID 全部 + 新 ID 切换后”。

**优点**

- 所有指标都能按正确口径重新计算，包括 P50/P90/P95、成功率、版本可用度、最新用例；
- 不需要重刷历史数据，事实表保留真实 ID，明细跳转可以继续用实际 ID；
- 前端基本不用改；
- 口径统一，容易解释和验收。

**缺点和风险**

- 需要改的 SQL 文件比较多，而且多个 Mapper 会出现相似的归属逻辑；
- 改动面大，回归测试范围大；
- SQL 变复杂，性能需要验证；
- 工程能力预聚合任务仍然要同步改，否则主表指标还是旧口径。

**结论**

- 准确性最好、可控性较好，是“稳妥实现”的方案。
- 缺点是改动量中等偏大。

### 方案 D：映射表 + 数据库视图

**做法（白话）**

- 建映射表；
- 在 Doris 里建几个视图，例如：
  - “归属后的 Nightly 运行视图”；
  - “归属后的 Nightly 日汇总视图”；
  - “归属后的 Nightly 用例日汇总视图”；
  - “归属后的运行统一视图（资源消耗用）”。
- 视图内部统一处理旧 ID 归到新 ID、切换前调试数据排除。
- 看板 SQL 只需要把原来查的表名换成视图，逻辑集中在一个地方。

**优点**

- 归属逻辑只写一次，所有看板共用，口径最统一；
- 各看板 SQL 改动小，主要是换表名；
- 不重刷历史数据；
- 未来新增看板或新查询可以直接复用视图。

**缺点和风险**

- 需要 DBA 建视图，属于数据库对象变更；
- Doris 视图是内联展开，复杂视图可能影响查询性能，需要压测；
- 出问题时排查链路比直接 SQL 更长；
- 映射表维护、切换时间口径仍然要处理好。

**结论**

- 如果 DBA 能接受视图，这是“改动可控 + 口径统一”最好的方案。
- 如果不能用视图，就退回方案 C。

---

### 方案 E：在 ETL 里直接把旧 ID 归一成新 ID

**做法（白话）**

- DWR/DM 任务在读数据时就把旧流水线的 `pipeline_id` 改成新流水线 ID，名称也改成新名称；
- 下游看板完全不用感知新旧切换，直接按 `pipeline_id` 查就是合并后的数据。

**优点**

- 下游 SQL 基本不用改；
- 查询性能最好，因为数据已经是一条流水线；
- 口径最统一。

**缺点和风险**

- 丢失真实旧流水线 ID，明细跳转链接可能指向错误的流水线；
- 需要重刷历史数据，或者至少回填历史归属；
- 切换时间、调试数据排除逻辑全部压到 ETL，出错后影响面大；
- 以后映射关系调整需要重跑历史；
- 审计和问题定位变难，无法区分某条运行到底来自旧流水线还是新流水线。

**结论**

- 下游最省事，但数据血缘损失大、回刷风险高。
- 除非业务明确不关心旧流水线 ID 和跳转，否则不推荐。

---

### 方案 F：事实表/DM 表增加 logical_pipeline_id 字段

**做法（白话）**

- 在 DWR 事实表和 DM 日表里新增“逻辑流水线 ID / 逻辑流水线名称”字段；
- ETL 写入时同时保留真实 `pipeline_id` 和逻辑 ID；
- 看板按逻辑 ID 分组，明细跳转用真实 ID。

**优点**

- 下游查询简单且准确；
- 真实 ID 保留，跳转和审计不受影响；
- 查询时不需要额外 join 映射表，性能好；
- 长期看是最干净的数据模型。

**缺点和风险**

- 需要改多张表结构，属于数据库结构变更；
- 历史数据需要回填或重新计算；
- ETL 任务改动大；
- 工程能力资源消耗用的是运行统一表，不只 Nightly 事实表，需要一起评估。

**结论**

- 长期最优，但初期投入最大。
- 适合作为后续数据模型演进方向，不建议作为本次“快速修复”方案。

---

### 方案 G：只改 relation / 维度层，让维度表带逻辑 ID

**做法（白话）**

- 不建独立映射表，而是在 `dm_rd_efc_project_pipeline_relation` 或类似维表里增加“逻辑流水线 ID / 逻辑流水线名称”；
- 旧流水线在维表里也指向新逻辑 ID；
- 看板继续通过 relation 关联，按逻辑 ID 聚合。

**优点**

- relation 本来就被很多查询使用，改动入口相对集中；
- 不需要改事实表结构；
- 可以顺便解决旧流水线被判成 `OTHER` 的问题。

**缺点和风险**

- relation 是每天重新生成的，切换时间、旧 ID 映射需要额外持久化，最后还是要一张映射表；
- 不是所有查询都经过 relation，例如部分 DM 查询和图表查询仍然要改；
- 旧流水线是否保留、是否重复成两行，需要额外规则。

**结论**

- 可以作为方案 C/D 的补充，把 relation 也带上逻辑 ID。
- 单独用不够。

---

### 方案 H：不建表，查询时动态推导映射

**做法（白话）**

- 不建映射表，每个查询里自己从运行表或 relation 里推导：
  - 找 `old_` 开头的流水线；
  - 去掉前缀找同名新流水线；
  - 取旧流水线最后运行时间作为切换时间；
  - 在 SQL 里现场归属。

**优点**

- 不需要改数据库、不需要维护映射数据；
- 映射永远按当前数据推导，不会出现映射表过期；
- 适合临时验证和小范围试点。

**缺点和风险**

- 复杂 SQL 在每个 Mapper 重复，维护成本高；
- 旧流水线如果后续还有偶发运行，切换时间会漂移；
- 名称重名、多次改名、异常映射很难处理；
- 查询性能差，每次都要扫运行表推导；
- 各看板口径容易不一致。

**结论**

- 不建议作为生产方案，只适合做一次性数据核对。

---

### 方案 I：如果现有维表已有逻辑分组字段，直接按它聚合

**做法（白话）**

- 检查 `sdi_version_pipeline_base_info` 里的 `group_id` 是否本来就是“同一条逻辑流水线”的分组标识；
- 如果新旧流水线共享同一个 `group_id`，看板直接按 `group_id` 聚合即可，不需要新表。

**优点**

- 改动最小；
- 不需要新增映射表；
- 如果数据质量可靠，口径天然统一。

**缺点和风险**

- 当前代码里没有看到 `group_id` 被当作“新旧流水线逻辑分组”使用；
- 需要先查数据确认新旧流水线是否真的共享 `group_id`；
- 即使共享，也仍然需要切换时间来判断调试数据；
- 依赖人工维护的数据质量，风险不可控。

**结论**

- 需要数据确认。
- 如果确认可用，可以作为低成本方案；否则不纳入主方案。

## 5. 推荐结论

### 5.1 首选

**方案 D：映射表 + 数据库视图。**

理由：

- 映射关系集中管理，后续再切换只加数据；
- 归属逻辑写在视图里，所有看板口径统一；
- 各看板 SQL 只需要换表名，改动比方案 C 小；
- 历史数据不用重刷，真实 `pipeline_id` 保留，明细跳转不受影响；
- 分位数、版本可用度、最新用例都能在视图里按逻辑流水线重新算。

前提：DBA 接受新增视图，且视图性能压测通过。

### 5.2 次选

**方案 C：映射表 + 各看板 SQL 内部归属。**

如果 DBA 不接受视图，就用方案 C。它和 D 的差别只是归属逻辑写在每个 Mapper 里，准确性一样，但 SQL 改动更多。

### 5.3 你提出的方案 B 怎么用

方案 B 的“门面”思想有价值，建议保留：

- 用门面统一解析“逻辑流水线 → 实际 pipeline_id 列表”；
- 明细、下钻、列表入口优先走门面；
- 聚合指标仍然需要 SQL 或视图按逻辑 ID 重新计算，不能只靠门面合并聚合结果。

可以理解为：**B 做入口，C 或 D 做聚合口径**。

### 5.4 不推荐

- 方案 A：解决不了调试数据排除和名称重名问题；
- 方案 E：丢失旧 ID、需要回刷、跳转链接会坏；
- 方案 H：SQL 重复、性能差、切换时间会漂移。

### 5.5 长期演进

如果后续 Nightly 数据模型还要继续演进，可以考虑方案 F：在事实表和 DM 表增加逻辑流水线字段，把归属固化成数据资产。但它需要改表结构和回填历史，适合单独排期。

## 6. 还需要确认的问题

1. 映射表里除了旧 ID、新 ID、切换时间，是否还需要保存“逻辑流水线名称”和“平台/项目”？建议保存，否则查询时还要回查 relation。
2. 切换时间是否允许人工修正？如果旧流水线切换后还有偶发运行，自动推导的“最后一次运行时间”会漂移，建议首次写入后冻结，异常由人工修。
3. 切换当天如果旧流水线和新流水线都跑了正式运行，这一天算旧还是算新？当前建议：事实表按精确时间过滤；日汇总按“切换日归旧、次日归新”处理，避免重复计天。
4. 是否接受新增 Doris 视图？如果不接受，方案 D 退化为方案 C。
5. `sdi_version_pipeline_base_info.group_id` 是否已经有“逻辑流水线分组”的含义？需要查一次数据确认；如果有，可以进一步简化方案 I。
