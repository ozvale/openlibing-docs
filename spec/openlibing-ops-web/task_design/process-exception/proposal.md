# 版本可用度备案（process-exception）— 需求提案

> 目标仓：`openlibing-ops-web` ｜ 模块：`src/views/process-exception/`
> 配套文档：[design.md](./design.md) ｜ [tasks.md](./tasks.md)

## 1. 背景与问题

### 1.1 业务背景

版本发布前，部分不达标项需要在限定范围内申请例外备案。审批通过后，该范围内的不达标项在版本可用度统计中按例外处理，不再阻断发布。例外是否成立取决于「组织 / 项目 + 例外场景 / 子场景 + Nightly 流水线 + 有效期」的组合，不同组合对应不同的审批决策路径。

### 1.2 现有问题

| 问题                                          | 影响                                                 |
| --------------------------------------------- | ---------------------------------------------------- |
| 申请、审批、结论全部在线下（邮件 / 群聊）流转 | 无统一入口，审批链不透明，新成员不知道找谁           |
| 决策路径靠人记或文档维护                      | 组织调整、场景新增后容易走错审批人或漏审             |
| 申请状态无法自助查询                          | 申请人反复催问，审批人无法批量处理待办               |
| 历史结论无系统留痕                            | 版本复盘、审计时难以追溯「何时、谁批、批了什么范围」 |
| 有效期与范围无结构化约束                      | 容易出现超范围、超期备案                             |

### 1.3 目标

1. 把例外备案的申请、审批、查询、路径维护全部线上化。
2. 决策路径可按「组织 / 项目 + 场景 / 子场景」配置，并由系统按申请内容自动匹配。
3. 全过程留痕：审批记录、跟踪进展、审批结果可查。
4. 待办集中处理，待办数量在页签上可见。
5. 申请与审批动作严格受后端 `actions` 控制，前端不自行推断权限。

### 1.4 成功判定（定性）

- 申请人可在单一入口完成「新建 → 跟踪 → 撤回 / 重提」闭环。
- 审批人可在待办页签看到全部待办，并在一处完成同意 / 拒绝 / 转移。
- 管理员可自助维护路径，路径变更后新申请立即按新路径匹配。
- 任一历史申请都能按关键字、项目、场景、时间、状态检索到，并查看完整审批轨迹。

## 2. 用户与角色

| 角色       | 说明                          | 关键诉求                                   | 权限来源                                            |
| ---------- | ----------------------------- | ------------------------------------------ | --------------------------------------------------- |
| 申请人     | 发起例外备案的研发 / 项目成员 | 快速新建、保存草稿、跟踪进度、撤回重提     | 登录即可                                            |
| 审批人     | 决策路径节点上配置的人员      | 集中看待办、查看上下文、同意 / 拒绝 / 转移 | 后端 `actions.canApprove / canReject / canTransfer` |
| 路径管理员 | 维护例外决策路径的人员        | 按组织 / 项目 / 场景维护节点与审批人       | 权限点 `ops_filing_path`                            |
| 查询者     | 需要了解备案情况的成员        | 按条件查询全员申请                         | 登录即可（例外查询页签）                            |

说明：

- 同一用户可同时具备多个角色；审批权限不由前端角色判断，统一以后端返回的 `actions` 为准。
- 「例外查询」为全员可见；「例外决策路径配置」仅对具备 `ops_filing_path` 的用户展示。

## 3. 术语

| 术语      | 含义                                                                         |
| --------- | ---------------------------------------------------------------------------- |
| 例外备案  | 在限定范围与有效期内，对不达标项申请豁免的业务单据                           |
| 决策路径  | 一组有序审批节点的模板，按「组织/项目 + 场景/子场景」匹配                    |
| 决策节点  | 路径中的一个审批环节，包含角色名、审批人配置方式、候选人                     |
| 归属类型  | `PROJECT` 项目级、`PRODUCT` 组织级、`ALL` 全部级，决定路径匹配范围           |
| 分配方式  | `single` 指定单个审批人、`multi` 配置多个审批人、`roleOnly` 申请人提交时自选 |
| `actions` | 后端下发的可执行动作集合，前端据此决定按钮显隐与可用性                       |
| 待办总数  | 当前用户待审批的申请数量，展示在「待我审批」页签角标                         |

| ---- | --------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| US-1 | 申请人          | 我想按项目 / 流水线 / 场景填写例外范围与有效期，保存草稿或直接提交，以便不达标项不被阻断 | 提交后可在「我的申请」看到状态为「备案中」                             |

| US-3 | 审批人          | 我想集中看到待我审批的单据，并同意、拒绝或转给更合适的人                                 | 待办列表与角标一致，动作后列表刷新                                     |
| US-4 | 审批人 / 查询者 | 我想按项目、场景、时间、状态检索历史备案，并查看审批结论                                 | 历史审批与例外查询可命中目标单据                                       |
| US-5 | 路径管理员      | 我想为不同组织 / 项目 / 场景配置不同审批链，组织调整后能自助修改                         | 路径保存后新申请按新路径匹配                                           |
| US-6 | 申请人          | 我想把某一单的详情链接发给同事一起看                                                     | 详情可复制链接（仅在不可编辑时展示入口）                               |

## 5. 功能需求

### 5.1 页面入口与页签

单一入口 `/process-exception/:projectId?`，页签顺序固定：

| 页签             | 可见性                                 | 职责                         |
| ---------------- | -------------------------------------- | ---------------------------- |
| 例外决策路径配置 | 仅 `ops_filing_path`                   | 路径列表、新增 / 编辑 / 删除 |
| 我的申请         | 登录即可：新建、编辑、撤回、删除、跟踪 | 申请人主入口                 |
| 待我审批         | 登录即可                               | 审批人待办列表               |
| 历史审批         | 登录即可                               | 我已处理的审批记录           |
| 例外查询         | 登录即可                               | 全员申请查询                 |

要求：

- 默认进入「我的申请」。
- 支持 `?tab=<tab>` 指定初始页签；无权限时回退默认页签。
- 支持 `?id=<applicationId>` 直接打开详情；打开后从 URL 移除 `id`。
- 页签切换保留各页筛选条件（KeepAlive），重新激活时刷新数据。

### 5.2 我的申请

列表需求：

- 列：申请编号、当前处理人、状态、标题、申请人、申请时间、组织/项目、例外场景、例外子场景、Nightly 流水线。
- 申请编号可点击进入详情。
- 状态筛选包含草稿；可按关键字、标题、项目、流水线、场景、子场景、申请日期区间筛选。
- 分页默认 20 条/页。

操作需求：

| 操作     | 入口        | 规则                                       |
| -------- | ----------- | ------------------------------------------ |
| 新建     | 工具行      | 无项目上下文时提示并终止                   |
| 编辑     | 行内        | 仅 `actions.canEdit`                       |
| 撤回     | 行内 / 批量 | 仅 `actions.canWithdraw`；需二次确认       |
| 删除     | 行内 / 批量 | 仅 `actions.canDelete`；需二次确认；软删除 |
| 查看详情 | 申请编号    | 始终可进入，详情内按钮受 `actions` 控制    |

批量规则：

- 勾选列仅对 `canWithdraw || canDelete` 的行可勾选。
- 批量撤回只处理 `canWithdraw` 的行；批量删除只处理 `canDelete` 的行。
- 删除接口返回部分失败时，必须逐条展示「申请编号 + 失败原因」。
- 批量撤回部分失败时，提示失败数量并刷新列表。

### 5.3 新建 / 编辑例外申请

表单字段：

| 字段           | 类型       | 必填       | 规则                                              |
| -------------- | ---------- | ---------- | ------------------------------------------------- |
| 组织 / 项目    | 只读展示   | 是         | 由项目上下文或路由 `projectId` 决定               |
| Nightly 流水线 | 下拉       | 是         | 按项目加载；外部指定时锁定                        |
| 例外场景       | 下拉       | 是         | 选项带归属类型，决定路径匹配的归属级别            |
| 例外子场景     | 下拉       | 是         | 随场景联动                                        |
| 标题           | 输入       | 是         | ≤100 字，展示字数统计                             |
| 例外时间       | 日期区间   | 是         | 结束 ≥ 开始；跨度 ≤365 天；不可选今天 +365 天之后 |
| 例外说明       | 富文本     | 是         | 纯文本 ≤20000 字                                  |
| 节点审批人     | 按节点配置 | 提交时必填 | 每个节点必须能解析出审批人                        |

业务要求：

- 新建时若无法获取项目上下文，直接提示并终止，不打开空表单。
- 归属类型（决定组织/项目范围）、场景、子场景与组织/项目共同匹配决策路径；流水线仅用于展示与筛选，不参与路径匹配。未匹配到路径时展示提示并禁止提交。
- 节点审批人控件由路径节点的分配方式决定：
  - `single`：默认唯一候选人，不可修改。
  - `multi`：从候选人中选择。
  - `roleOnly`：申请人自选平台并搜索用户。
- 支持「保存草稿」与「提交」；草稿不校验必填，提交需完整校验。
- 编辑草稿后可再次保存或提交；编辑已提交单据的规则由 `actions.canEdit` 决定。
- 保存或提交成功后关闭抽屉并刷新当前列表。

### 5.4 待我审批

- 列表列：通用列 + 例外时间（开始 ~ 结束）。
- 筛选：不含状态字段，其余与查询口径一致。
- 不提供工具行与操作列，审批动作统一在详情完成。
- 页签角标展示待办总数；超过 99 显示 `99+`；0 时不展示。
- 审批动作完成或页面重新激活时，角标与列表同步刷新。

### 5.5 历史审批

- 列表列：通用列 + 审批完成时间 + 我的审批结果。
- 我的审批结果：`同意`（绿色）/ `拒绝`（红色）；无结果时展示空值占位。
- 状态筛选不含草稿。
- 仅查看，不提供写操作。

### 5.6 例外查询

- 列表列与「我的申请」一致（不含操作列）。
- 可查询全员申请；状态筛选不含草稿。
- 用于版本复盘、审计与跨团队查询。

### 5.7 详情

信息分区：

| 分区     | 内容                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------- |
| 审批流程 | 申请人 + 各审批节点，展示已同意 / 审批中 / 待审批 / 已拒绝                                                    |
| 基本信息 | 标题、编号、状态、组织/项目、场景归属、场景、子场景、流水线、开始时间、结束时间、申请人、当前处理人、申请时间 |
| 例外说明 | 富文本内容，超长内部滚动                                                                                      |
| 审批记录 | 审批环节、结论、意见、审批人、时间                                                                            |
| 跟踪进展 | 跟踪节点、操作类型、进展描述、操作人、时间                                                                    |

动作需求：

| 动作     | 展示条件      | 交互要求                       |
| -------- | ------------- | ------------------------------ |
| 编辑     | `canEdit`     | 打开编辑抽屉并回填             |
| 撤回     | `canWithdraw` | 二次确认后撤回                 |
| 删除     | `canDelete`   | 二次确认后软删除，成功关闭详情 |
| 拒绝     | `canReject`   | 弹出意见框，意见必填           |
| 同意     | `canApprove`  | 弹出意见框，意见选填           |
| 转移     | `canTransfer` | 选择平台、搜索用户、填写原因   |
| 复制链接 | `!canEdit`    | 复制详情链接并提示             |

- 任一动作执行期间必须防重复提交。
- 动作成功后重新加载详情，并刷新背后的列表与待办角标。

### 5.8 审批动作细则

- 同意 / 拒绝：弹窗需说明动作后果（同意后流转下一节点或生效；拒绝后单据退回，申请人可修改重提）。
- 拒绝意见必填，同意意见选填；意见长度 ≤200 字。
- 转移：平台、目标用户、转移原因均必填；原因 ≤200 字。
- 转移目标用户通过远程搜索选择；切换平台需清空已选用户与候选。
- 弹窗关闭后再次打开应重置上次输入。

### 5.9 例外决策路径配置

列表：

- 列：组织/项目、例外场景、例外子场景、决策节点。
- 组织 / 项目为空时展示「全部组织 / 全部项目」。
- 节点流展示角色与候选人；候选人超过 2 个时展示 `+N`，悬浮查看全部；`roleOnly` 节点展示「申请人提交时自选」。
- 操作：编辑、删除。

路径表单：

| 字段       | 必填      | 规则                                         |
| ---------- | --------- | -------------------------------------------- |
| 组织       | 是        | 含「全部」(0)                                |
| 项目       | 是        | 组织为「全部」时禁用并提交 0；否则按组织加载 |
| 例外场景   | 是        | ≤64 字                                       |
| 例外子场景 | 是        | ≤64 字                                       |
| 决策节点   | 至少 1 个 | 1~10 个；顺序即审批顺序                      |

节点规则：

- 每个节点包含角色/职责、审批人配置方式、候选人。
- 分配方式为 `roleOnly` 时不配置候选人（由申请人提交时自选）。
- 单节点候选人 ≤50；同一人员在同节点内不可重复，跨节点也不可重复。
- 候选人超过 1 人时，分配方式下拉整体禁用（避免 multi 被改为 single 造成数据不一致）。
- 分配方式为 `single` 且已有候选人时，平台、用户与添加按钮禁用；`multi` 可继续添加候选人。
- 保存时按当前节点顺序重排序号。
- 删除路径后，新建申请不应再匹配到该路径。

### 5.10 字典与级联

- 组织 → 项目：项目随组织加载；组织为「全部」时项目固定为 0。
- 项目 → 流水线 / 场景：未选项目时两者禁用。
- 场景 → 子场景：未选场景时子场景禁用。
- 项目变更清空流水线与场景、子场景；场景变更清空子场景。
- 列表筛选与新建表单使用同一套字典缓存；路径变更后场景字典需失效重取。

### 5.11 链接分享

- 详情在不可编辑状态下提供「复制链接」。
- 链接需指向该申请详情；当前生成规则与路由存在偏差，需在联调阶段确认最终路径（见第 12 节）。

## 6. 业务规则

| 编号  | 规则                                                                             |
| ----- | -------------------------------------------------------------------------------- |
| BR-01 | 前端不自行判断审批权限，按钮显隐与可用性以后端 `actions` 为准                    |
| BR-02 | 决策路径按 `productId + projectId + scene + subScene` 唯一匹配，且排除已删除路径 |
| BR-03 | 例外时间跨度不得超过 365 天，结束日期不得早于开始日期                            |
| BR-04 | 路径节点 1~10 个；单节点候选人 ≤50；同一人员不得跨节点重复                       |
| BR-05 | 删除申请与删除路径均为软删除                                                     |
| BR-06 | 草稿仅申请人可见；待办、历史、例外查询均不包含草稿                               |
| BR-07 | 归属类型由场景决定：项目级 / 组织级 / 全部级，决定路径匹配范围                   |
| BR-08 | 待办角标口径与待办分页接口 `total` 一致，超过 99 显示 `99+`                      |
| BR-09 | 审批动作成功后必须刷新详情、列表与角标，三者口径一致                             |
| BR-10 | 未匹配到决策路径的申请不得提交                                                   |
| BR-11 | 所有含富文本的详情内容渲染前需净化，避免脚本注入                                 |
| BR-12 | 申请说明、审批意见、转移原因均需限制长度并展示字数                               |

## 7. 状态模型

| 状态        | 含义   | 主要入口                     | 可执行动作（以后端 actions 为准） |
| ----------- | ------ | ---------------------------- | --------------------------------- |
| `draft`     | 草稿   | 我的申请                     | 编辑、删除、提交                  |
| `filing`    | 备案中 | 我的申请、待我审批           | 撤回、同意、拒绝、转移            |
| `approved`  | 已备案 | 我的申请、历史审批、例外查询 | 查看、删除（若后端允许）          |
| `returned`  | 已退回 | 我的申请、历史审批           | 编辑后重新提交、删除              |
| `withdrawn` | 已撤回 | 我的申请、历史审批           | 编辑后重新提交、删除              |

状态流转：

```text
draft ──submit──▶ filing ──approve(末节点)──▶ approved
                   │  │
                   │  └──reject──▶ returned ──submit──▶ filing
                   └──withdraw──▶ withdrawn ──submit──▶ filing
```

> 动作均以后端 `actions` 为准；列表页不提供写操作，审批与写操作统一在详情内完成。历史审批、例外查询仅查看。

## 8. 非功能需求

| 类别     | 要求                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------ |
| 性能     | 页签切换不重复请求静态字典；列表分页 20 条；字典按项目缓存                                       |
| 体验     | 页签 KeepAlive 保留筛选；抽屉关闭即重置；动作有 loading 与防重复                                 |
| 兼容     | 沿用项目 Element Plus 与 Tailwind 体系；不引入新 UI 库                                           |
| 安全     | 不本地存储敏感信息；富文本渲染前净化；权限点仅用于页签可见性                                     |
| 可维护   | 筛选/列配置化；单文件 ≤400 行；接口与类型集中管理                                                |
| 可观测   | 错误统一由 HTTP 拦截器提示；关键动作保留成功提示                                                 |
| 可访问性 | 表单 label 使用 `label-position="top"`；按钮具备明确文案；表格操作可键盘触达（依赖 EP 默认能力） |

## 9. 本期不做

- 独立详情路由：统一使用侧滑抽屉。
- 设计稿顶部 header、角色手动切换、暗色主题。
- 修改 `management` 模块、顶层 tabList 或公共 `base-table` 组件。

- 移动端适配。

## 12. 风险与待确认

| 项             | 说明                                                                          | 处理建议                               |
| -------------- | ----------------------------------------------------------------------------- | -------------------------------------- |
| 复制链接路径   | 生成 `/apps/processException`，与路由 `/process-exception/:projectId?` 不一致 | 联调确认网关前缀后统一                 |
| 转移不能选自己 | 弹窗文案声明，前端未校验                                                      | 确认后端是否已拦截；未拦截则前端补     |
| 新建提交语义   | 新建依赖 `create` 的 `draft:false`；编辑需 `update` + `submit`                | 与后端确认是否统一                     |
| 待办平台参数   | 前端未传 `platform`                                                           | 与后端联调确认                         |
| 路径匹配上限   | 拉取 100 条后前端匹配，路径过多可能漏配                                       | 后续推动后端按项目查询                 |
| 页签未回写 URL | 刷新回到默认页签                                                              | 如需分享能力再补                       |
| 无自动化测试   | 关键纯逻辑未覆盖                                                              | 补单测覆盖状态推导、路径匹配、参数转换 |
