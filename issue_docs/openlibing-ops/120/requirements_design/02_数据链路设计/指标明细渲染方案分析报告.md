# 指标明细页渲染方案分析报告

> 日期：2026-09-24
> 背景：18 个开源合规指标需要前端明细展示，因每个指标明细结构不同，最初计划用 Freemarker 后端组装 HTML 返回前端，但担心安全风险。
> 结论先行：**放弃 18 个 Freemarker 模板方案，采用"统一展示契约（JSON）+ 18 个后端组装器 + 1 个 Vue 通用渲染组件"方案**，Freemarker 保留为离线场景的降级备选（如需使用必须落实安全基线）。

---

## 一、原始诉求与约束

| 诉求                     | 说明                                                            |
| ------------------------ | --------------------------------------------------------------- |
| 不做 18 个固定前端页面   | 18 个指标每个明细结构不同，逐页开发成本高，希望依靠 AI 快速生成 |
| 担心 Freemarker 安全风险 | 后端组装模板返回 HTML 存在 SSTI / XSS 顾虑                      |
| 业界现状顾虑             | 大量项目在用 Freemarker，是否"人人都在用"就代表安全             |

## 二、Freemarker 安全风险查证结论

### 2.1 风险是真的，但根源是"纪律"不是"工具"

Freemarker 的安全风险核心是 **SSTI（服务端模板注入）**，典型攻击链：

```ftl
<#assign ex="freemarker.template.utility.Execute"?new()>${ex("rm -rf /")}
```

`?new` 内建可实例化 `Execute` / `ObjectConstructor` / `JythonRuntime` 等危险类，直接 RCE。

**但所有著名事故都不是"用了 Freemarker"，而是违反了以下纪律之一：**

1. **用户输入进入模板内容**（JeecgBoot 积木报表 RCE：接口把用户传入的 SQL 参数直接交给 Freemarker 处理）
2. **配置裸奔**（未设置 `SAFER_RESOLVER`，`?new` / `?api` / `?eval` 可加载任意类）
3. **模板名 / `<#include>` 路径拼接用户参数**（路径穿越 + 任意模板执行）

### 2.2 安全基线（若使用 Freemarker 必须落实）

```java
Configuration cfg = new Configuration(Configuration.VERSION_2_3_32);
cfg.setNewBuiltinClassResolver(TemplateClassResolver.ALLOWS_NOTHING_RESOLVER); // 禁 ?new
cfg.setAPIBuiltinEnabled(false);       // 禁 ?api（2.3.22+ 默认已禁，显式声明防误开）
cfg.setClassicCompatible(false);
cfg.setOutputFormat(HTMLOutputFormat.INSTANCE);  // ${} 默认 HTML 转义防 XSS
// 模板名只允许白名单映射，禁止拼接任何请求参数
```

代码评审清单追加两条：模板内容永远不含用户输入；`<#include>` 路径永远不拼接。

**结论：Freemarker 的 SSTI 风险可通过配置控制，安全不是否决它的主因；真正的否决理由见第三节。**

## 三、原型实证：18 个页面 = 18 份数据 + 1 套渲染逻辑

对 `docs/0912/明细数据设计freemarker模版/` 下 17 个可交互原型做了机械比对：

| 检验项                     | 结果                                                                                                                               |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 17 个文件 `<style>` 字节数 | **全部 9223 字节，逐字节相同**                                                                                                     |
| 渲染函数 `build(m, host)`  | 17 个文件**签名一致**；抽查 MAINTAINED 与 LICENSE 两个业务差异最大的指标，**均为精确 10032 字节**                                  |
| 生成的 DOM 类名序列        | **逐项完全一致**：`mi-head（分数头）→ mi-stats（键值汇总）→ mi-crit（不满足卡片）→ mi-tabs + mi-table（明细表）→ mi-pager（分页）` |
| 数据契约（MODELS）         | 17 个文件结构一致：`indicator / repo / summary / failItems / groups`                                                               |
| 列定义与跳转链接           | 均为后端下发数据（原型注释原话：`列定义（来自后端 scan_groups[].columns）`、`跳转链接由后端下发 cells[].href（模板不拼 URL）`）    |

**结论：设计师已经把 18 个明细页收敛成"一套版式 + 一套数据契约"，页面看起来不同，是因为喂进去的数据不同，不是结构不同。** 这套原型天然就是为"通用渲染器"设计的，18 个 Freemarker 模板方案等于把已经统一的渲染逻辑再复制 18 份。

## 四、两层模型：分歧的澄清

讨论中确认双方观点实际互补，需区分两层：

### 4.1 领域数据模型（18 套，各不相同，全部保留）

每个指标的业务字段确实完全不同，例如：

- A 指标（文件扫描）：扫描的文件名 list、扫描文件数、通过数、未通过数
- B 指标（配置检查）：配置 list、每项是否合格、合格数量
- VULNS：CVE 编号、严重度、计划完成时间、状态、扣分
- MAINTAINED：commit SHA、message、作者、issue 数……

**这 18 套领域模型一个都不消灭，全部保留在后端。**

### 4.2 展示契约（1 套，原型已定义）

```
indicator: { name, title, category, weight, score, status, level, scanTime, naReason, failEmptyText, dataNote }
summary:   [ { label, value, level } ]                                          // 指标特有的键值卡
failItems: [ { title, fields[{label,value,level}], reason, formula, deduct } ] // 不满足卡片区
groups:    [ { key, label, columns[{label,key}], rows[{ cells[{text,href,level}], searchText }] } ] // tab 明细表
```

### 4.3 两层的衔接：组装器（18 份差异化代码）

每个指标一个组装器，把领域模型翻译成展示契约槽位——这就是"18 个指标各不相同"的落点，也是 AI 批量生成的最佳目标：

```java
// A 指标组装器（文件扫描）
summary: [ {label:"扫描文件数", value:"42"},
           {label:"通过", value:"40", level:"success"},
           {label:"未通过", value:"2", level:"error"} ]
groups:  [ {label:"文件明细", columns:[{文件名},{结果},{原因}],
            rows:[{cells:[{text:"pom.xml"},{text:"未通过",level:"error"},…]}]} ]

// B 指标组装器（配置检查）—— 同一批槽位，喂不同数据
summary: [ {label:"配置项总数", value:"12"},
           {label:"合格", value:"9", level:"success"},
           {label:"不合格", value:"3", level:"error"} ]
groups:  [ {label:"配置明细", columns:[{配置项},{是否合格},{说明}], …} ]
```

类比：`el-table` 组件只有一份，却能支撑全公司所有列表页——每页传自己的 `columns + rows`。前端组件不认识"文件"也不认识"配置"，只认识"键值卡"和"表格"。

## 五、方案对比

| 维度                          | 方案一：18 个 Freemarker 模板                  | 方案二：1 契约 + 18 组装器 + 1 前端组件 |
| ----------------------------- | ---------------------------------------------- | --------------------------------------- |
| 18 套领域差异                 | 表达在 18 个 ftl 文件里                        | 表达在 18 个 Java 组装器里（量一样）    |
| 版式骨架（约 600 行 × 17 份） | 复制 18 份                                     | 1 份                                    |
| 改版式 / 换设计               | 改 18 个文件                                   | 改 1 处                                 |
| 新增指标                      | 再复制 600 行骨架                              | AI 生成 1 个几十行的组装器              |
| 字段拼错（`${v.cveId}`）      | 运行时白屏，18 个都要点开验                    | Java 编译期报错，可单测                 |
| XSS 转义审计                  | 18 个模板逐个审计 `${}`                        | 1 个渲染点统一转义                      |
| SSTI                          | 需配置护栏 + 长期纪律维持                      | 无模板引擎，风险不存在                  |
| 交互（搜索/排序/分页）        | 原型的 JS 交互在静态片段里丢失，需另行注入脚本 | 原型 JS 逻辑直接改 computed 复用        |
| AI 生成质量                   | 高相似度复制，易遗漏                           | 机械映射，可编译验证                    |

## 六、前端（Vue）实现建议

**不使用 v-html，采用数据驱动渲染**（`{{ }}` 插值 + `:href` 绑定）：

| 风险                                        | v-html 方案                    | 数据驱动方案                                                               |
| ------------------------------------------- | ------------------------------ | -------------------------------------------------------------------------- |
| `cell.text` 藏 `<script>` / `<img onerror>` | 直接执行，v-html 绕过 Vue 转义 | `{{ }}` 自动转义，天然免疫                                                 |
| `href="javascript:alert(1)"`                | 原样渲染可点击                 | Vue 3 对 `:href` 绑定 `javascript:` URL 直接拦截（Vue 2 需后端白名单兜底） |

前端结构：1 个 `MetricDetail.vue` 组件（把原型 `build()` 翻译成模板，DOM 序列已提取，翻译为机械活），搜索/排序/分页改为 computed，18 个指标零前端差异代码。个别指标未来若有真正装不下的个性需求（如需画图表），契约预留 `customType` 扩展位单独写组件。

### 后端唯一剩余安全点：`cells[].href` 白名单

`text` 靠框架转义即可，但 `href` 属性转义挡不住 `javascript:` 协议，后端组装时需校验：

```java
private static final Pattern ALLOWED_HREF =
    Pattern.compile("^https://([\\w.-]+\\.)?gitcode\\.com/");

// 不匹配白名单 → 只下发 text、不下发 href
```

## 七、Freemarker 的去留

| 场景                            | 处置                                                                                     |
| ------------------------------- | ---------------------------------------------------------------------------------------- |
| 前端指标明细展示（本需求）      | **不用 Freemarker**，走 JSON 契约                                                        |
| 未来离线报告 / 邮件推送指标详情 | 允许降级使用 **1 个** Freemarker 模板渲染同一份 VO（不是 18 个），必须落实第二节安全基线 |
| 若坚持后端出 HTML + 前端 v-html | 前端需 DOMPurify 二次净化，交互能力受限，**不推荐**                                      |
