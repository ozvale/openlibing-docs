# 指标 15 安全策略：联系链接（contact link）判定规则研究报告

> 研究对象：`SECURITY_POLICY` 三项加分中的「联系链接 +6」
> 方法：逐个读取本地 `_test_repos/` 下全部 48 个 SECURITY.md（43 个仓），结合脚本规则、design 口径、社区豁免文件交叉核对；不使用全文正则统计代替人工阅读。
> 结论状态：仅研究，未修改任何代码。

---

## 一、结论先行

1. **现行规则确有问题，但问题主要在「判定依据」而非「分数结果」**：`CONTACT_RE` 中 `https?://` 命中即算，导致 36/38 个仓的 `link=True` 中，绝大多数是靠「公网地址声明」表里的**构建依赖下载链接**撑起来的，而不是任何上报渠道。
2. **邮箱分支在真实样本中彻底失效**：48 个文件 **0 条** email / mailto 命中，+6 分完全由 http 决定。
3. **31 个 CANN 模板仓「结果是对的，理由是错的」**：它们的 `## 漏洞机制说明` 均指向 `cann/community/security/security.md`，该页正文含 `mailto:security@cann.osinfra.cn`——确实存在可用上报渠道，但当前脚本命中的是表里的 `makeself-release-*.tar.gz`，不是这个策略页。
4. **真正的误判发生在没有漏洞章节的仓**：[402170](https://gitcode.com/cann/pto-isa)（英文 PTO Tile Library，全文无漏洞章节）仅凭 3 条构建依赖 URL 拿到 **9 分**；而 [405133](https://gitcode.com/cann/its-matrix-computation)（写了完整的漏洞报告机制，只有定性渠道描述、无字面链接）只得 **4 分**。这才是规则需要修的地方。
5. **建议口径**：从「全文正则找 http」改为「**按 Markdown 章节 + 链接锚文本 + URL 语义三元组判定上报渠道**」，并显式排除代码围栏内命令、`公网地址声明` / `Public Network Addresses` 表格、文档 / 镜像 / 依赖下载类 URL。

## 二、现行规则原文

**脚本**：`security_file_scan.py` 第 211-219 行、第 1886-1918 行。

```python
CONTACT_RE = re.compile(r'(mailto:|[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}|https?://)')
link = bool(CONTACT_RE.search(content))          # 全文任意位置、任意 URL
score = (1 if disclosure else 0) + (6 if link else 0) + (3 if free_text else 0)
```

**设计口径**：`design.md` §5.15 明确写了「联系链接（正则匹配邮箱 `user@domain` / `mailto:` 或 `https://` URL）」——所以这是**设计原意**，不是实现走样。但该设计在做「是否有查找表单 / 联系方式」的可执行性验证时，缺了两个前提：URL 属于哪个章节、锚文本说什么。

**前端文案**：`2026-09-23_安全合规评分看板接口模版SQL/detail-conf-init-v2.sql` 第 139 行，卡片标签「联系链接」，未满足原因「SECURITY.md 中未检出联系链接，+6 未得分」——需随规则一起修改。

## 六、建议的新判定规则

### 6.1 核心原则（三条）

1. **链接是否计分，由「它属于哪个章节 + 锚文本说什么 + 它指向什么」共同决定，不由 URL 本身决定。**
   - 反例：`| 依赖 | ... | <https://gitcode.com/cann-src-third-party/json/...include.zip> |` 无锚文本、位于 `公网地址声明` 表内 → 排除。
   - 正例：`[漏洞管理](https://gitcode.com/cann/community/blob/master/security/security.md)` 位于 `## 漏洞机制说明`、锚文本含「漏洞」、目标页含 mailto → 计入。
2. **先做 Markdown 结构解析，再做语义判定**：剥离代码围栏 / 行内代码 → 按标题切章节 → 章节内分离表格行与正文 → 逐链接取（章节标题，锚文本，目标 URL）三元组。
3. **邮箱优先、文字渠道次之、策略页链接再次之**，且全部落到可审计的明细字段，前端能解释为什么给分。

### 6.2 排除清单（硬规则，优先于任何命中）

| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |

## 七、连带发现（需单独决策，但影响同一指标）

1. **候选路径漏掉 legal 目录**：`security_file_scan.py` 第 212 行只认 4 个固定路径（`.gitcode/SECURITY.md`、`SECURITY.md`、`docs/SECURITY.md`、`security.md`），5 个 MindStudio 仓的 `docs/zh|en/legal/SECURITY.md` 被整体判 0。

3. **detail_json 缺少证据字段**：现在只有 `link: true` / `false`，无法回答「凭什么算联系链接」。这正是本次误判长期未被发现的根因——建议按 6.4 补齐 `link_tier` / `link_evidence` / `link_excluded`。
4. **前端 / 明细配置需同步**：卡片标签「联系链接」、`failItems.reason`「未检出联系链接」、`rule.brief` 都要改成「上报联系方式」，否则规则改了而界面解释没变，会再次出现「卡片说明与扣分矛盾」的老问题。
