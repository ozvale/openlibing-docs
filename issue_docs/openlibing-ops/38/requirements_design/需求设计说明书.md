## 1. 需求背景

开源项目运营总览（`category=project`）是项目维度的汇总看板，其数据来源于 dolphinscheduler 定时任务将代码仓级数据（`dm_rd_efc_repo_sum_pipeline_statistics_day`）汇总到项目级表（`dwi_project_statistics`）。

当前项目汇总看板与代码仓级 PR 门禁看板（`category=repo-pr-pipeline`）在列展示上存在较大差异，主要体现在：

1. **PR 流水线时长**：项目看板仅展示"PR流水线最长时长"，缺少各子阶段的平均时长（E2E/构建/代码检查/测试）
2. **PR 资源总消耗**：项目看板完全没有 NPU（卡时）和 Memory（GB\*h）指标
3. **版本级流水线运营**：缺少 P0 测试用例通过率和版本可用度指标

## 3. 需求拆解与实现方案

### 3.1 需求项 1：PR 流水线平均时长 — 前端展示对齐

**结论：无需后端改动，仅需前端展示**

当前 `dwi_project_statistics` 表和 `DwiProjectStatistics` model 已包含以下字段：
- `avg_access_duration` → 门禁E2E执行平均时长
- `avg_build_duration` → 编译任务平均时长
- `avg_dt_duration` → 测试任务平均时长
- `avg_check_duration` → 代码检查平均时长

`ProjectDetailResp` 也已映射并返回：
- `avgAccessDuration` → 门禁E2E执行平均时长（min）
- `avgBuildDuration` → 编译任务平均时长（min）
- `avgDtDuration` → 测试任务平均时长（min）
- `avgCheckDuration` → 代码检查平均时长（min）

**这些字段接口已返回，只需前端在"PR流水线最长时长"列下展开子列展示即可。**

### 3.2 需求项 2：新增 PR 资源总消耗（NPU 卡时 / Memory GB\*h / vCPU 核时）

**需要改动**：SQL 汇总脚本 + DORIS 表 + Java Model + Mapper + Resp

#### 3.2.1 数据源确认

`dm_rd_efc_repo_sum_pipeline_statistics_day` 表中已有：
- `npu_second` (String) — NPU 卡秒
- `memory_second` (String) — Memory 秒
- `cpu_second` (String) — CPU 秒

代码仓级 Mapper `DmRdEfcRepoSumPipelineStatisticsDayMapper.xml` 的 `baseQueryRepoStatistics` SQL 已做 `sum(cast(npu_second as double))` 聚合。

#### 3.2.2 汇总逻辑

在 dolphinscheduler 的 `sql.sql` 中，`project_pr_pipeline` CTE 当前从 `dm_rd_efc_repo_sum_pipeline_statistics_day` 汇总 PR 数据，但**未包含** npu_second / memory_second / cpu_second。

需要修改 `project_pr_pipeline` CTE，增加：
```sql
sum(cast(rpp.npu_second as double)) as npu_second,
sum(cast(rpp.memory_second as double)) as memory_second,
sum(cast(rpp.cpu_second as double)) as cpu_second
```

#### 3.2.3 DORIS 表结构变更

`dwi_project_statistics` 表需新增列：
```sql
ALTER TABLE dwi_project_statistics ADD COLUMN `npu_second` DOUBLE COMMENT 'PR资源总消耗-NPU(卡秒)';
ALTER TABLE dwi_project_statistics ADD COLUMN `memory_second` DOUBLE COMMENT 'PR资源总消耗-Memory(秒)';
ALTER TABLE dwi_project_statistics ADD COLUMN `cpu_second` DOUBLE COMMENT 'PR资源总消耗-vCPU(秒)';
```

> **注意**：DORIS UNIQUE KEY 表支持 ADD COLUMN，但需确认该表是否在 DORIS 2.0+ 版本（支持 light schema change）。如果 DORIS 版本不支持在线加列，需重建表。

#### 3.2.4 Java 代码改动

| 文件 | 改动 |
|------|------|
| `DwiProjectStatistics.java` | 新增 `npuSecond`、`memorySecond`、`cpuSecond` 字段 + SORT_FIELD_MAPPING |
| `DwiProjectStatisticsMapper.xml` | resultMap 新增映射 + dashboard_common_sql 新增 SUM 聚合 |
| `ProjectDetailResp.java` | 新增 `npuSecond`、`memorySecond`、`cpuSecond` 字段 + ExcelProperty + 构造函数赋值 |
| `CommonMetricConf` 数据库 | 新增指标列配置记录（big_category='project'） |

#### 3.2.5 单位换算

与代码仓级看板保持一致：
- NPU：`npu_second / 3600` → 卡时
- Memory：`memory_second / 3600` → GB\*h
- vCPU：`cpu_second / 3600` → 核时

换算逻辑在 `ProjectDetailResp` 构造函数中通过 `NumberUtil.div(xxx, 3600, 2)` 实现。

### 3.3 需求项 3：版本级流水线运营 — P0 测试用例通过率 + 版本可用度

**需要改动**：SQL 汇总脚本 + DORIS 表 + Java Model + Mapper + Resp

#### 3.3.1 数据源分析

通过分析 `nightly-dashboard` 的实现（`NightlyPipelineDashboardMapper.xml` 和 `DwiVersionPipelineInfoMapper.xml`），确认了两个指标的计算逻辑：

**版本可用度**：
- 数据源表：`dm_rd_efc_build_dim_nightly_pipeline_day`
- 详情计算逻辑（`NightlyPipelineDashboardMapper.xml` 的 `versionAvailabilityStatsCTE`）：
  ```sql
  -- 先 DISTINCT 去重（避免一天多次运行被重复计算），再按 pipeline_id 聚合
  -- isAllDay=1 时仅统计工作日
  version_availability_stats AS (
      SELECT
          pipeline_id,
          COUNT(DISTINCT pipeline_run_endtime) AS total_days,
          SUM(CASE WHEN is_version_available = 1 THEN 1 ELSE 0 END) AS available_days
      FROM (
          SELECT DISTINCT
              dm.pipeline_id,
              dm.pipeline_run_endtime,
              dm.is_version_available
          FROM dm_rd_efc_build_dim_nightly_pipeline_day dm
          LEFT JOIN dim_holiday h ON dm.pipeline_run_endtime = h.holiday_date
          WHERE dm.pipeline_run_endtime >= #{req.startDate}
            AND dm.pipeline_run_endtime <= #{req.endDate}
            AND (#{req.isAllDay} = 0
                 OR (h.holiday_date IS NULL AND WEEKDAY(dm.pipeline_run_endtime) < 5)
                 OR (h.holiday_date IS NOT NULL AND h.is_off_day = 0))
      ) t
      GROUP BY pipeline_id
  )
  ```
- **核心公式**：`available_days / total_days * 100`，其中 `total_days = COUNT(DISTINCT pipeline_run_endtime)`，`available_days = SUM(is_version_available=1)`
- **粒度**：流水线级别，每条流水线一个值
- **节假日**：项目汇总使用 **isAllDay=1（仅工作日）**，与详情页"工作日"选项一致

**P0 测试用例通过率**：
- 数据源表：`dm_rd_efc_build_dim_test_case_nightly_pipeline_day`
- 详情计算逻辑（`NightlyPipelineDashboardMapper.xml` 的 `latestTestCaseCTE`）：
  ```sql
  -- 取每个 pipeline 最新一次运行（ROW_NUMBER + rn=1），不过滤节假日
  latest_test_case AS (
      SELECT ... FROM (
          SELECT ...,
              ROW_NUMBER() OVER (PARTITION BY pipeline_id ORDER BY pipeline_run_endtime DESC) AS rn
          FROM dm_rd_efc_build_dim_test_case_nightly_pipeline_day dr
          LEFT JOIN dim_holiday h ON DATE(dr.pipeline_run_endtime) = h.holiday_date
          WHERE dr.pipeline_run_endtime >= #{req.startDate}
            AND dr.pipeline_run_endtime <= #{req.endDate}
            AND <holidayFilterCondition />
      ) t WHERE rn = 1
  )
  ```
- **核心公式**：取最新一次运行的 `case_pass_rate_p0 * 100`
- **粒度**：流水线级别，每条流水线一个值
- **节假日**：项目汇总 **不过滤节假日**，取最新执行结果即可

#### 3.3.2 一致性分析（核心）

> **用户要求**：项目汇总数据结果需要与详情一致，不能出现里外不一致情况。

**分析路径**：详情是流水线级别，项目汇总是项目级别。一致性意味着：**从详情页看到的所有流水线数据，按相同逻辑聚合到项目级后，应等于项目汇总看板展示的值**。

##### 版本可用度 — 一致性分析

**详情计算**（流水线级，isAllDay=1 仅工作日）：
```
Pipeline A: available_days=20, total_days=22 (工作日天数) → 20/22 = 90.91%
Pipeline B: available_days=18, total_days=22 (工作日天数) → 18/22 = 81.82%
```

**项目汇总**（项目级）需要确定聚合方式：

| 方案 | 公式 | 示例结果 | 与详情一致性 |
|------|------|---------|-------------|
| A. 加权平均 | `SUM(available) / SUM(total) * 100` | (20+18)/(22+22) = 86.36% | ✅ 可从详情反推 |
| B. 简单平均 | `AVG(各流水线可用度)` | (90.91+81.82)/2 = 86.36% | ❌ 权重不同时不等 |

**结论**：方案 A（加权平均）保证一致性。与现有 `version_access_success_count / version_access_count` 汇总方式一致。

**一致性保证条件**：
1. 定时任务 CTE 必须使用与详情相同的源表 `dm_rd_efc_build_dim_nightly_pipeline_day`
2. 定时任务 CTE 必须使用**相同的去重逻辑**：先 `SELECT DISTINCT` 去重（pipeline_id + pipeline_run_endtime + is_version_available），再按 pipeline_id 聚合
3. 定时任务 CTE 必须使用**相同的节假日过滤**：`LEFT JOIN dim_holiday`，过滤条件为仅工作日（isAllDay=1）
4. `dwi_project_statistics` 存储中间值（available_days + total_days），查询时 `SUM` 聚合后计算比率
5. 仅存储工作日过滤后的值（不存全量）

**一致性验证公式**：
```
项目汇总可用度 = SUM(所有流水线 available_days) / SUM(所有流水线 total_days) * 100
             = SUM(详情中每条流水线的 available_days) / SUM(详情中每条流水线的 total_days) * 100
             ✅ 一致（前提：详情页选择"工作日"选项）
```

##### P0 测试用例通过率 — 一致性分析

**详情计算**（流水线级）：
```
Pipeline A: 最新运行 → case_run_pass_count_p0=80, case_total_count_p0=100 → 80%
Pipeline B: 最新运行 → case_run_pass_count_p0=45, case_total_count_p0=50  → 90%
```

**⚠️ 关键问题**：P0 通过率是**快照值**（取最新一次运行），不是累计值。项目级汇总需要将多条流水线的最新运行数据聚合。

**方案对比**：

| 方案 | 项目级公式 | 示例结果 | 与详情一致性 |
|------|-----------|---------|-------------|
| A. 加权平均（按用例数） | `SUM(pass_p0) / SUM(total_p0) * 100` | (80+45)/(100+50) = 83.33% | ✅ 可从详情反推 |
| B. 简单平均 | `AVG(各流水线 P0 通过率)` | (80+90)/2 = 85% | ❌ 权重不同时不等 |
| C. 取项目最新运行 | 取项目下所有流水线最新一次运行 | 需要定义"项目最新" | ❌ 语义不明确 |

**结论**：方案 A（加权平均）保证一致性。用 `case_run_pass_count_p0` 和 `case_total_count_p0` 做加权。

**⚠️ 一致性风险点 — P0 通过率的"最新运行"语义**：

详情中，每条流水线独立取最新运行。项目汇总需要将各流水线的最新运行数据求和。关键问题是：**定时任务每天汇总时，如何保证存储的 P0 数据是各流水线的最新运行？**

**分析**：
- `dwi_project_statistics` 按天存储，每天一行（project_id + data_time + pipeline_status）
- 定时任务在 T 日执行时，对每条流水线取截至 T 日的最新运行 P0 数据，然后按项目求和
- 项目汇总查询时，取日期范围内**最后一天**的 P0 数据（而非 SUM 跨天）

**一致性验证**：
```
T 日定时任务：
  Pipeline A 最新运行 → pass=80, total=100
  Pipeline B 最新运行 → pass=45, total=50
  → dwi_project_statistics[T日].p0_case_pass_count = 125, p0_case_total_count = 150

项目汇总查询（startDate ~ endDate）：
  取 endDate 对应行的 p0 数据 → 125/150 = 83.33%

详情查询（startDate ~ endDate）：
  Pipeline A: 最新运行 pass=80, total=100 → 80%
  Pipeline B: 最新运行 pass=45, total=50  → 90%
  加权: (80+45)/(100+50) = 83.33%
  ✅ 一致
```

**⚠️ 残留风险**：如果某流水线在 endDate 之后、定时任务执行之前又有新运行，项目汇总会包含该新运行的数据，而详情查询（使用用户指定的 endDate）不会包含。但此场景属于"数据时间窗口"差异，与现有版本成功率等指标的处理方式一致，可接受。

#### 3.3.3 版本可用度 — 项目级汇总逻辑

在 `sql.sql` 中新增 CTE `project_nightly_availability`：

```sql
project_nightly_availability AS (
    SELECT
        ri.project_id,
        ri.open_source,
        t.pipeline_run_endtime AS data_time,
        SUM(CASE WHEN t.is_version_available = 1 THEN 1 ELSE 0 END) AS version_available_days,
        COUNT(DISTINCT t.pipeline_run_endtime) AS version_total_days
    FROM sdi_repo_info ri
    JOIN sdi_version_pipeline_base_info vp ON ri.project_id = vp.project_id
    JOIN (
        SELECT DISTINCT
            dm.pipeline_id,
            dm.pipeline_run_endtime,
            dm.is_version_available
        FROM dm_rd_efc_build_dim_nightly_pipeline_day dm
        LEFT JOIN dim_holiday h ON dm.pipeline_run_endtime = h.holiday_date
        WHERE (h.holiday_date IS NULL AND WEEKDAY(dm.pipeline_run_endtime) < 5)
           OR (h.holiday_date IS NOT NULL AND h.is_off_day = 0)
    ) t ON vp.pipeline_id = t.pipeline_id
    GROUP BY ri.project_id, ri.open_source, t.pipeline_run_endtime
)
```

> **关键设计说明**：
> - 使用 `SELECT DISTINCT` 去重（pipeline_id + pipeline_run_endtime + is_version_available），与详情 `NightlyPipelineDashboardMapper` 的 `versionAvailabilityStatsCTE` 逻辑一致，避免一天多次运行被重复计算
> - 关联 `dim_holiday` 表，**仅保留工作日**（isAllDay=1 语义），与详情页"工作日"选项一致
> - 工作日过滤条件：不在节假日表且周一至周五，或在节假日表但 `is_off_day=0`（调休工作日）
> - `version_total_days` 使用 `COUNT(DISTINCT pipeline_run_endtime)` 而非 `COUNT(*)`，与详情逻辑一致

在 `dwi_project_statistics` 中存储两个中间值：
- `version_available_days` (INT) — 版本可用天数（仅工作日，所有流水线 is_version_available=1 之和）
- `version_total_days` (INT) — 版本总工作日天数（仅工作日，所有流水线去重后的天数之和）

查询时在 `DwiProjectStatisticsMapper.xml` 的 `dashboard_common_sql` 中计算：
```sql
SUM(version_available_days) / NULLIF(SUM(version_total_days), 0) * 100 AS version_availability_rate
```

**一致性保证**：SUM 聚合是可加的，`SUM(A.available + B.available) / SUM(A.total + B.total)` 等价于分别计算 A 和 B 的 available/total 后加权平均。

#### 3.3.4 P0 测试用例通过率 — 项目级汇总逻辑

P0 通过率是**快照值**，需要特殊处理。**不过滤节假日**，取最新执行结果。

在 `sql.sql` 中新增 CTE `project_nightly_testcase_p0`：

```sql
project_nightly_testcase_p0 AS (
    SELECT
        ri.project_id,
        ri.open_source,
        dmpd.pipeline_run_endtime AS data_time,
        SUM(dmpd.case_run_pass_count_p0) AS p0_case_pass_count,
        SUM(dmpd.case_total_count_p0) AS p0_case_total_count
    FROM sdi_repo_info ri
    JOIN sdi_version_pipeline_base_info vp ON ri.project_id = vp.project_id
    JOIN (
        SELECT
            pipeline_id,
            pipeline_run_endtime,
            case_run_pass_count_p0,
            case_total_count_p0
        FROM (
            SELECT
                pipeline_id,
                pipeline_run_endtime,
                case_run_pass_count_p0,
                case_total_count_p0,
                ROW_NUMBER() OVER (
                    PARTITION BY pipeline_id
                    ORDER BY pipeline_run_endtime DESC
                ) AS rn
            FROM dm_rd_efc_build_dim_test_case_nightly_pipeline_day
        ) ranked
        WHERE rn = 1
    ) dmpd ON vp.pipeline_id = dmpd.pipeline_id
    GROUP BY ri.project_id, ri.open_source, dmpd.pipeline_run_endtime
)
```

> **关键设计说明**：
> - P0 取最新执行结果，**不过滤节假日**（与详情页 isAllDay=0 时的逻辑一致）
> - `ROW_NUMBER() OVER (PARTITION BY pipeline_id ORDER BY pipeline_run_endtime DESC) rn=1` 取每条流水线最新一次运行
> - 按项目 SUM 各流水线的 pass/total，实现加权平均

在 `dwi_project_statistics` 中存储两个中间值：
- `p0_case_pass_count` (INT) — P0用例通过数（各流水线最新运行之和）
- `p0_case_total_count` (INT) — P0用例总数（各流水线最新运行之和）

**⚠️ 查询时聚合方式不同于版本可用度**：P0 是快照值，不能 SUM 跨天。需要取**日期范围内最后一天**的值：

```sql
-- 在 dashboard_common_sql 的 ranked_data CTE 中新增排名
ROW_NUMBER() OVER (PARTITION BY project_id
    ORDER BY data_time DESC) AS p0_rank

-- 在 SELECT 中取最后一天的 P0 数据
MAX(CASE WHEN p0_rank = 1 THEN p0_case_pass_count END) AS p0_case_pass_count,
MAX(CASE WHEN p0_rank = 1 THEN p0_case_total_count END) AS p0_case_total_count
```

查询后计算：`p0_case_pass_count / NULLIF(p0_case_total_count, 0) * 100`

**一致性保证**：
1. 定时任务每天取各流水线最新运行 → 与详情 `ROW_NUMBER ... ORDER BY pipeline_run_endtime DESC, rn=1` 逻辑一致
2. 按项目 SUM 各流水线的 pass/total → 与详情加权平均一致
3. 查询取最后一天的值 → 代表截至查询时间范围的最新快照

#### 3.3.5 DORIS 表结构变更


#### 3.3.7 一致性对照表

| 指标 | 详情计算（流水线级） | 项目汇总计算（项目级） | 节假日 | 一致性 |
|------|---------------------|----------------------|--------|--------|
| 版本可用度 | `available_days/total_days * 100`（去重+仅工作日）per pipeline | `SUM(available_days)/SUM(total_days) * 100` across pipelines | 仅工作日 | ✅ 加权平均，详情选"工作日"时一致 |
| P0通过率 | `case_pass_rate_p0 * 100` from latest run per pipeline | `SUM(pass_p0)/SUM(total_p0) * 100` from latest run across pipelines | 不过滤 | ✅ 加权平均，与详情 isAllDay=0 一致 |
| 版本成功率(已有) | `access_success_count/access_count * 100` per pipeline | `SUM(success)/SUM(count) * 100` across pipelines | — | ✅ 同模式 |

#### 3.3.8 节假日问题

- **版本可用度**：使用 **isAllDay=1（仅工作日）**，定时任务 CTE 中关联 `dim_holiday` 表过滤非工作日。详情页有"全部/工作日"切换按钮，项目汇总与详情"工作日"选项一致。
- **P0 测试用例通过率**：**不过滤节假日**，取最新执行结果即可。与详情页 isAllDay=0 时的逻辑一致。
- **存储策略**：`dwi_project_statistics` 仅存储工作日过滤后的版本可用度数据，不存全量。

## 6. 验收标准

1. 调用 `/openlibing-ops/manage/common/detail` 接口（`category=project`），响应中包含 `npuSecond`、`memorySecond`、`cpuSecond` 字段且值正确
2. NPU 单位为卡时（npu_second / 3600），Memory 单位为 GB\*h（memory_second / 3600），vCPU 单位为核时（cpu_second / 3600）
3. 项目级 NPU/Memory 值 = 该项目下所有代码仓对应值之和
4. 响应中包含 `versionAvailabilityRate`（版本可用度百分比）和 `p0CasePassRate`（P0测试用例通过率百分比）
5. 版本可用度 = 项目下所有流水线可用天数之和 / 总工作日天数之和 × 100%（加权平均，仅工作日，与详情"工作日"选项一致）
6. P0 测试用例通过率 = 项目下所有流水线最新运行的 P0 通过数之和 / P0 总数之和 × 100%（加权平均，不过滤节假日，与详情 isAllDay=0 一致）
7. **一致性验证**：对同一项目同一时间范围，项目汇总的版本可用度应等于详情页选择"工作日"后各流水线数据按加权平均聚合的结果；P0 通过率应等于详情页 isAllDay=0 时各流水线数据按加权平均聚合的结果
8. Excel 导出包含新增的资源消耗列、版本可用度、P0通过率列
9. 前端可在"PR门禁"分组下展示 PR 流水线 E2E/构建/代码检查/测试 平均时长子列
10. 新增指标支持排序
