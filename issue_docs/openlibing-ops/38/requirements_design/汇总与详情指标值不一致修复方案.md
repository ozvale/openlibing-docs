## 1. 现象

调用同一项目（MindIE，projectId=300036）同一时间范围（2026-05-09 ~ 2026-06-08）的两个接口：

| 指标 | 详情接口（nightly-dashboard） | 汇总接口（project） | 倍数 |
|------|------------------------------|---------------------|------|
| 版本可用度 | 每条流水线 ~10% | 项目维度 80% 多 | ≈ 8~9 倍 |
| P0 用例通过数 | 多条流水线累加 ≈ 118 | 1062 | ≈ 9 倍 |

用户已用本地服务 `https://localhost:8098/common/detail` 复现。

---

## 2. 根因分析

### 2.1 主因：`sdi_repo_info` 引起的笛卡尔积导致指标 N 倍膨胀

**两个事实**：

| 表 | 一行代表 | 一个 project 下的行数 |
|---|---|---|
| `sdi_repo_info` | 仓库 | **N**（项目下有 N 个代码仓） |
| `sdi_version_pipeline_base_info` | 项目 ↔ 流水线 关联 | **M**（项目下有 M 条流水线） |

`sql.sql` 中 `project_nightly_availability` 和 `project_nightly_testcase_p0` 两个 CTE 的写法：

```sql
-- 现状（sql.sql 第 247~303 行）
project_nightly_availability AS (
    SELECT
        ri.project_id,
        ri.open_source,
        t.data_time,
        SUM(CASE WHEN t.is_version_available = 1 THEN 1 ELSE 0 END) AS version_available_days,
        COUNT(DISTINCT t.pipeline_id) AS version_total_days
    FROM sdi_repo_info ri
    JOIN sdi_version_pipeline_base_info vp ON ri.project_id = vp.project_id
    JOIN (...) t ON vp.pipeline_id = t.pipeline_id
    GROUP BY ri.project_id, ri.open_source, t.data_time
),
project_nightly_testcase_p0 AS (
    SELECT
        ri.project_id,
        ri.open_source,
        ranked.data_time,
        SUM(ranked.case_run_pass_count_p0) AS p0_case_pass_count,
        SUM(ranked.case_run_count_p0)  AS p0_case_run_count
    FROM sdi_repo_info ri
    JOIN sdi_version_pipeline_base_info vp ON ri.project_id = vp.project_id
    JOIN (...) ranked ON ranked.pipeline_id = vp.pipeline_id
    GROUP BY ri.project_id, ri.open_source, ranked.data_time
)
```

**问题推导**：

1. `sdi_repo_info ri`：N 行
2. `JOIN sdi_version_pipeline_base_info vp ON ri.project_id = vp.project_id`：**N × M 行**（每个仓库 × 每条流水线）
3. `JOIN (...) t / ranked`：再放大 K 倍（每天的明细行）
4. `SUM(...)`：把 (data_time, pipeline_id) 的指标**按 N 倍累加**
5. `GROUP BY (project, open_source, data_time)`：**无法消除 N 倍复制**，因为 SUM 已经把每行的指标都加进去了

**对两个指标的具体影响**：

| 指标 | 写库字段 | N 倍复制位置 | 结果 |
|------|---------|-------------|------|
| 版本可用度 | `version_available_days` | 分子 SUM 不去重 | **分子被放大 N 倍** |
| 版本可用度 | `version_total_days` | 分母 `COUNT(DISTINCT pipeline_id)` 去重 | 分母不变 |
| P0 通过率 | `p0_case_pass_count` | SUM 不去重 | **通过数被放大 N 倍** |
| P0 通过率 | `p0_case_run_count` | SUM 不去重 | **执行数被放大 N 倍** |

**理论推导**：

- 详情接口（`NightlyPipelineDashboardMapper.xml` 第 299 行）**直接从 `sdi_version_pipeline_base_info` 起表**，不经过 `sdi_repo_info`，所以是单条 pipeline 一个值，没有 N 倍问题
- 汇总接口的可写库结果 = 详情各 pipeline 真实值 × **N（项目下的 repo 数）**
- MindIE 项目的 N ≈ 8~9，正好对应用户看到的 8~9 倍差异

**用户实测验证**：

- 可用度：详情 ~10% × N ≈ 80% 多 → 与 8~9 倍一致
- P0 通过数：详情累加 118 × 9 ≈ 1062 → 与 9 倍一致

**核心 bug 结论**：`project_nightly_availability` 和 `project_nightly_testcase_p0` 不应该从 `sdi_repo_info` 起表；版本可用度和 P0 都是**流水线维度**的指标，不是仓库维度。

### 2.2 节假日口径：sql.sql 硬编码工作日（保留），汇总接口不支持 isAllDay 切换

**业务约束**：节假日无人维护版本可用度，统计全量日期会拉低指标，所以**可用度只统计工作日**。

**当前实现**（`sql.sql` 第 251~254 行，修复后保留）：

```sql
project_nightly_availability AS (
    ...
    JOIN (
        SELECT DISTINCT dm.pipeline_id, dm.pipeline_run_endtime AS data_time, dm.is_version_available
        FROM dm_rd_efc_build_dim_nightly_pipeline_day dm
        LEFT JOIN dim_holiday h ON dm.pipeline_run_endtime = h.holiday_date
        WHERE ((h.holiday_date IS NULL AND WEEKDAY(dm.pipeline_run_endtime) < 5)
           OR (h.holiday_date IS NOT NULL AND h.is_off_day = 0))   -- 硬编码仅工作日
        AND dm.pipeline_run_endtime IS NOT NULL
        AND dm.pipeline_run_endtime <= CURRENT_DATE()
    ) t ON vp.pipeline_id = t.pipeline_id
    ...
)
```

**设计决策**：

1. 写库时硬编码工作日过滤（节假日不参与统计），符合业务诉求"只统计工作日"
2. `dwi_project_statistics` 中**只存工作日数据**，没有节假日数据
3. 汇总接口 Java 端 `DwiProjectStatisticsMapper.xml` 的 `dashboard_common_sql` **不需要**处理 `isAllDay` 参数（前端调用汇总时直接走工作日口径）
4. **与详情接口的口径差异**：详情接口支持 `isAllDay` 动态切换（`NightlyPipelineDashboardMapper.xml` 第 218~220 行），汇总接口**仅展示工作日**——这是**有意的业务决策**，不是 bug

### 2.3 P0 数据写入逻辑一致性确认

`project_nightly_testcase_p0` CTE 中"取每条 pipeline 截至 data_time 的最新一次 P0"逻辑：

```sql
ROW_NUMBER() OVER (
    PARTITION BY dd.data_time, vp_inner.pipeline_id
    ORDER BY p0.pipeline_run_endtime DESC
) AS rn
WHERE x.rn = 1
```

与详情接口 `latestTestCaseCTE`（`NightlyPipelineDashboardMapper.xml` 第 113~117 行）的 ROW_NUMBER 语义一致（按 pipeline 分区取最新），**这部分逻辑正确**，主问题就是 N 倍累加。

## 3. 修复方案

### 3.1 修复点 1（核心，必做）：去掉 `sdi_repo_info` JOIN

将 `project_nightly_availability` 和 `project_nightly_testcase_p0` 改用 `sdi_version_pipeline_base_info` 起表，避免 N 倍笛卡尔积。

**修改文件**：`openlibing-ops/sql.sql`（DS 上执行的脚本，无需提交业务仓 PR）

**修改后的 SQL**：

```sql
-- 版本可用度（修复后）：直接从 sdi_version_pipeline_base_info 起表
project_nightly_availability AS (
    SELECT
        vp.project_id,
        'lead' AS open_source,                       -- 维度表里没有 open_source，写死 lead
        t.data_time,
        SUM(CASE WHEN t.is_version_available = 1 THEN 1 ELSE 0 END) AS version_available_days,
        COUNT(DISTINCT t.pipeline_id) AS version_total_days
    FROM sdi_version_pipeline_base_info vp
    JOIN (
        SELECT DISTINCT
            dm.pipeline_id,
            dm.pipeline_run_endtime AS data_time,
            dm.is_version_available
        FROM dm_rd_efc_build_dim_nightly_pipeline_day dm
        LEFT JOIN dim_holiday h ON dm.pipeline_run_endtime = h.holiday_date
        WHERE ((h.holiday_date IS NULL AND WEEKDAY(dm.pipeline_run_endtime) < 5)
           OR (h.holiday_date IS NOT NULL AND h.is_off_day = 0))
           AND dm.pipeline_run_endtime IS NOT NULL
           AND dm.pipeline_run_endtime <= CURRENT_DATE()
    ) t ON vp.pipeline_id = t.pipeline_id
    GROUP BY vp.project_id, t.data_time
),

-- P0 测试用例（修复后）：直接从 sdi_version_pipeline_base_info 起表
project_nightly_testcase_p0 AS (
    SELECT
        vp.project_id,
        'lead' AS open_source,
        ranked.data_time,
        SUM(ranked.case_run_pass_count_p0) AS p0_case_pass_count,
        SUM(ranked.case_run_count_p0)      AS p0_case_run_count
    FROM sdi_version_pipeline_base_info vp
    JOIN (
        SELECT
            x.data_time,
            x.pipeline_id,
            x.case_run_pass_count_p0,
            x.case_run_count_p0
        FROM (
            SELECT
                dd.data_time,
                vp_inner.pipeline_id,
                p0.case_run_pass_count_p0,
                p0.case_run_count_p0,
                p0.pipeline_run_endtime,
                ROW_NUMBER() OVER (
                    PARTITION BY dd.data_time, vp_inner.pipeline_id
                    ORDER BY p0.pipeline_run_endtime DESC
                ) AS rn
            FROM (
                SELECT DISTINCT pipeline_run_endtime AS data_time
                FROM dm_rd_efc_build_dim_nightly_pipeline_day
                WHERE pipeline_run_endtime IS NOT NULL
                  AND pipeline_run_endtime <= CURRENT_DATE()
            ) dd
            CROSS JOIN sdi_version_pipeline_base_info vp_inner
            LEFT JOIN dm_rd_efc_build_dim_test_case_nightly_pipeline_day p0
                ON p0.pipeline_id = vp_inner.pipeline_id
                AND p0.pipeline_run_endtime <= dd.data_time
        ) x
        WHERE x.rn = 1
    ) ranked ON ranked.pipeline_id = vp.pipeline_id
    GROUP BY vp.project_id, ranked.data_time
)
```

**关键改动**：

1. 主表从 `sdi_repo_info` 改为 `sdi_version_pipeline_base_info`（M 行而非 N 行）
2. 显式写死 `open_source = 'lead'`（版本流水线和 P0 都属于 lead 维度，与 `project_version` CTE 保持一致；原写法通过 `JOIN sdi_repo_info` 隐式带出 open_source）
3. `GROUP BY` 中去掉 `open_source` 字段（已写死）

**修复效果**：

- 写入 `version_available_days` 不再被 N 倍累加 → 汇总接口的 `version_availability_rate` 等于详情各 pipeline 率的加权平均（按总天数加权）
- 写入 `p0_case_pass_count` 不再被 N 倍累加 → 汇总接口的 `p0_case_pass_count` 等于详情各 pipeline 最新 P0 pass 的累加

### 3.2 节假日口径说明（已确认）

**业务决策**：节假日无人维护版本可用度，统计全量日期会拉低指标，所以**可用度只统计工作日**。

- **sql.sql 写库时硬编码工作日过滤**（已保留）：`project_nightly_availability` CTE 的 dim_holiday + WEEKDAY 过滤保持不变
- **P0 写库时不过滤节假日**：P0 是"取截至当天最新一次 run"快照型指标，节假日无影响
- **汇总接口 Java 端不处理 isAllDay**：与写库口径保持一致，"汇总只展示工作日"
- **与详情接口的口径差异**：详情接口支持 isAllDay 切换；汇总接口仅工作日——这是**有意的业务决策**

### 3.3 修复点 2：汇总接口 Java 端校验与详情同源

**目的**：修复后人工跑 SQL 校验汇总接口的 `p0_case_pass_count` 与详情接口"各 pipeline 最新 P0 pass 之和"完全一致。

**校验 SQL**（在 dwi 库手动跑一次）：

```sql
-- 详情口径：各 pipeline 最新 P0 pass 之和
SELECT
    sdi.project_id,
    SUM(lt.case_run_pass_count_p0) AS detail_p0_pass
FROM sdi_version_pipeline_base_info sdi
LEFT JOIN (
    SELECT pipeline_id, case_run_pass_count_p0
    FROM (
        SELECT pipeline_id, case_run_pass_count_p0,
            ROW_NUMBER() OVER (PARTITION BY pipeline_id ORDER BY pipeline_run_endtime DESC) AS rn
        FROM dm_rd_efc_build_dim_test_case_nightly_pipeline_day
        WHERE pipeline_run_endtime BETWEEN '2026-05-09' AND '2026-06-08'
    ) t WHERE rn = 1
) lt ON sdi.pipeline_id = lt.pipeline_id
WHERE sdi.project_id = 300036
GROUP BY sdi.project_id;

-- 汇总口径：最近一天 dwi_project_statistics 中的 p0_case_pass_count
SELECT project_id, p0_case_pass_count
FROM dwi_project_statistics
WHERE project_id = 300036
  AND open_source = 'lead'
  AND data_time = '2026-06-08'
  AND pipeline_status = 'ALL_PIPELINE_STATUS';
```

**期望**：修复后两个查询结果**相等**（均为 118 级别，而非 1062）。

### 4.3 回归风险

| 维度 | 风险 | 缓解 |
|------|------|------|
| P0 取数逻辑 | 改 `sdi_repo_info` 起表为 `sdi_version_pipeline_base_info` 起表后，维度表字段 `open_source` 缺失，写死 'lead' | 现状其他 CTE（如 `project_version`）也是写死 'lead'，保持一致 |

## 6. 结论与下一步

**结论**：本次问题由 sql.sql 中两个 CTE 从 `sdi_repo_info`（仓库表）起表 JOIN `sdi_version_pipeline_base_info`（项目-流水线表）引入 N 倍笛卡尔积，导致指标被项目下 repo 数倍放大。MindIE 项目 N≈8~9，与用户实测 8~9 倍差异吻合。

**修复路径**：

1. **sql.sql 修复（已完成）**：
   - `project_nightly_availability` CTE 改用 `sdi_version_pipeline_base_info` 起表，`open_source` 写死 `'lead'`
   - `project_nightly_testcase_p0` CTE 同样改用 `sdi_version_pipeline_base_info` 起表
   - 工作日过滤**保留**（节假日不参与统计，符合业务诉求"节假日无人维护可用度"）
   - P0 不过滤节假日
2. **业务仓 PR**：**无需**修改 Java/MyBatis（汇总接口查询逻辑不变，写库数据修对后自动正确）
3. **业务仓 docs 归档**：本修复方案文档已在 `openlibing-docs/issue_docs/openlibing-ops/38/requirements_design/汇总与详情指标值不一致修复方案.md`（用户之前要求"先在 IDE 看方案"）
4. **DS 执行**：在 dolphinscheduler 上重跑 sql.sql（建议 `truncate table dwi_project_statistics;` 后重跑）
5. **验收**：用本地服务 `https://localhost:8098/common/detail` 分别调汇总和详情接口对比 MindIE（projectId=300036）的可用度和 P0，数值应**接近一致**

**注意**：sql.sql 按用户要求**不提交业务仓**（DS 上执行的脚本，git 历史无需追溯）。本修复方案文档作为 Issue38 的补充说明留在 openlibing-docs 仓。
