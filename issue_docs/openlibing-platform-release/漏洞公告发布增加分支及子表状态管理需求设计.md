## 2. 需求场景说明

> 发布漏洞信息时，CVE Manager 的接口传参由「仓库列表」升级为「仓库→分支」映射，每个仓库需要单独记录分支与推送状态。原主表只存一条整体状态，无法表达「部分仓库成功、部分仓库失败」的中间态，重试时也无法只针对失败仓库重发。本次调整新增子表按仓库粒度记录推送状态，主表汇总子表结果，支持部分成功重试与详情查询。

## 3. 需求验收标准

> 1. 推送漏洞公告时，请求体 `repos` 字段为 `Map<仓库名, 分支名>`，与 CVE Manager 新接口对齐。
> 2. 每个仓库的推送状态（待发布/发布中/成功/失败）、失败原因、重试次数在子表独立记录。
> 3. 部分仓库成功时主表为「部分成功」，重试时只重发失败仓库，已成功仓库不重复推送且主表保留。
> 4. 发布详情返回每个仓库的分支、推送状态、失败原因、重试次数；仅成功仓库返回完整链接。
> 5. CVE Manager 响应 `data.success` 为 null 时不抛 NPE，按失败处理。

## 4. 需求设计与分解

| 功能点 | 描述 | 涉及对象 |
|--------|------|---------|
| 接口传参调整 | `repos` 从 `List<String>` 改为 `Map<String,String>`（仓库→分支） | ReleaseVulnerabilityBulletinDTO |
| 子表新增 | 按仓库粒度记录分支、推送状态、失败原因、重试次数 | release_vulnerability_bulletin_repo |
| 主子表状态联动 | 主表状态由子表汇总得出（成功/部分成功/失败） | VulnerabilityBulletinStatusEnum |
| 部分成功重试 | 重试时过滤已成功仓库，只重发失败仓库，主表 repos 保留成功仓库 | ReleaseVulnerabilityBulletinServiceImpl |
| 响应解析健壮性 | 对 `data.success`/`data.failed` 做 null 检查，避免 NPE | applyCveManagerResult |
| 详情查询 | 详情按主表当前 repos 过滤子表，返回每仓库状态明细，仅成功返回链接 | ReleaseBaseServiceImpl |

### 4.1 核心逻辑方案

#### 4.1.1 架构设计

- **DTO 层**：`ReleaseVulnerabilityBulletinDTO` 的 `repos` 由 `List<String>` 改为 `Map<String,String>`。
- **主表**：`release_vulnerability_bulletin` 的 `repos` 字段存当前请求的 `repo→branch` 快照（重试时被覆盖为「已成功 + 本次重发」的合集）。
- **子表**：`release_vulnerability_bulletin_repo` 按仓库粒度记录分支、推送状态、失败原因、重试次数。
- **异步推送**：`CompletableFuture.runAsync` 推送 CVE Manager，解析响应后更新子表每个 repo 状态，再汇总主表状态。
- **状态枚举**：`VulnerabilityBulletinStatusEnum` 新增 `PARTIAL_SUCCESS(2,"部分成功")`，主表/子表共用 `WAIT/FAIL/PUBLISHING/PUBLISHED`，`EXECUTING/PARTIAL_SUCCESS` 仅主表。

#### 4.1.2 数据库设计

**子表名：release_vulnerability_bulletin_repo**

| 字段名 | 数据类型 | 约束 | 描述 |
|--------|----------|------|------|
| id | INT(32) | PRIMARY KEY, AUTO_INCREMENT | 主键ID |
| bulletin_id | INT(32) | NOT NULL, INDEX | 关联主表漏洞公告ID |
| repo | VARCHAR(255) | NOT NULL | 仓库名 |
| branch | VARCHAR(255) | - | 分支名 |
| push_status | TINYINT(1) | NOT NULL | 推送状态（0待发布/3失败/4发布中/5成功） |
| fail_reason | VARCHAR(500) | - | 失败原因（成功时为空） |
| retry_count | INT(11) | DEFAULT 0 | 重试次数 |
| del_flag | TINYINT(1) | - | 删除标识 |
| creator_id | VARCHAR(64) | - | 创建人ID |
| creator_name | VARCHAR(255) | - | 创建人名称 |
| updater_id | VARCHAR(64) | - | 更新人ID |
| updater_name | VARCHAR(255) | - | 更新人名称 |
| create_time | DATETIME | - | 创建时间 |
| update_time | DATETIME | - | 更新时间 |

**主表 repos 字段语义变更**：`release_vulnerability_bulletin.repos` 由 JSON 数组改为 JSON 对象（`{"repo":"branch"}`），作为当前有效仓库集合快照。

#### 4.1.3 状态枚举设计

```
WAIT(0, "待发布")              // 主表/子表共用
EXECUTING(1, "执行中")          // 仅主表，历史状态保留
PARTIAL_SUCCESS(2, "部分成功")   // 仅主表，子表无此状态
FAIL(3, "发布失败")              // 主表/子表共用，子表语义为单仓库失败
PUBLISHING(4, "发布中")         // 主表/子表共用
PUBLISHED(5, "发布成功")        // 主表/子表共用，子表语义为单仓库成功
```

**主表状态汇总规则**（由子表结果计算）：
- 全部成功 → `PUBLISHED`
- 全部失败 → `FAIL`
- 成功与失败并存 → `PARTIAL_SUCCESS`

#### 4.1.4 核心流程

**推送流程（pushVulnerabilityBulletin）**：
1. 查询主表是否已存在（按 reviewId）。
2. 若存在（重试场景）：
   - 查询子表中已成功（`PUBLISHED=5`）的 `repo→branch`。
   - 从本次请求过滤掉已成功 repo，得到待重发集合。
   - 若待重发为空，主表状态置 `PUBLISHED`，repos 保留成功仓库，直接返回。
   - 否则主表 repos = 已成功 repo + 本次重发 repo，状态置 `WAIT`，异步推送待重发集合。
3. 若不存在（新建场景）：插入主表，repos = 本次请求，状态置 `WAIT`，异步推送全部 repo。
4. 子表 upsert：新建场景直接 insert；重试场景已存在的 repo 更新（branch 重置、状态重置、retryCount+1），不存在的 insert。

**异步推送流程（pushToCveManager）**：
1. 主表、子表状态置 `PUBLISHING`。
2. 构造请求体 `{"fixed_product":"xxx","repos":{"repo":"branch"}}` POST 到 CVE Manager。
3. 响应成功（HTTP 2xx）调用 `applyCveManagerResult` 解析；失败则子表全部置 `FAIL`、主表置 `FAIL`。
4. `applyCveManagerResult` 解析 `data.success`/`data.failed`，对 null 做防御，逐个 repo 更新子表状态，最后汇总主表状态。

**详情查询流程（ReleaseBaseServiceImpl）**：
1. 主表 repos 解析为 `repo→branch` Map，得到有效仓库集合。
2. 查询子表该 bulletinId 全部记录，按有效仓库集合过滤（剔除历史遗留）。
3. 映射为 `ReleaseVulnerabilityBulletinRepoStatusVo` 列表，仅 `PUBLISHED` 状态的 repo 填充完整链接（`ATOM_GIT_PREFIX + repo`），失败 repo 不返回链接。
4. 填充 `pushStatusName` 中文描述。

#### 4.1.5 异常处理

| 异常类型 | 触发条件 | 处理方式 |
|---------|---------|---------|
| 响应为 null | HttpRequestUtil 返回 null | 子表全部置 FAIL，主表置 FAIL |
| HTTP 非 2xx | CVE Manager 返回错误码 | 子表全部置 FAIL（原因含 http code），主表置 FAIL |
| IO 异常 | 读取响应体失败 | 子表全部置 FAIL（原因含 e.getMessage），主表置 FAIL |
| 解析异常 | `data.success` 为 null 或 JSON 格式错误 | 子表全部置 FAIL（原因含 parse response error），主表置 FAIL |
| 单仓库无结果 | repo 不在 success 也不在 failed | 该 repo 置 FAIL，原因 "no result in cve manager response" |
